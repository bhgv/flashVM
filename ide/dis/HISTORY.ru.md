# Undo/Redo с проверкой ревизии

[English](HISTORY.md) · [Протокол](PROTOCOL.ru.md) ·
[Код](idecore.b) · [Пример](examples/history/README.ru.md) ·
[Ошибки компилятора](../../fir/v1/doc/SOURCE_DIAGNOSTICS.ru.md)

IDE 0.4.0 добавляет Undo и Redo после Find. Значения прежних операций и поля
Request/Reply сохранены. Пересоберите ядро и клиентов с одинаковым idecore.m.
Все изменения идут через типизированный канал; приватные Document/History
не выдаются наружу. Это сервис текста, не файловая система и не GUI.

## Поведение

Undo восстанавливает предыдущий текст, помещая текущий в Redo; Redo выполняет
обратный переход. Успех увеличивает ревизию ровно на 1. Старый номер не оживает:
Open first → ревизия 1; Replace second → 2; Undo first → 3; Redo second → 4.
После Undo запрос с expected=2 получает Conflict, хотя такой текст уже существовал.
Номера действуют на протяжении всей жизни сервиса.

Настоящая правка Replace помещает старый текст в Undo и очищает Redo.
Пустая по эффекту правка, отклонённый запрос, Find/Locate/Offset и MarkSaved
Redo не сбрасывают. MarkSaved также не сбрасывает Undo. Пустой текст допустим.
Open/Close очищают обе стороны: история не переходит через закрытие документа.
Shutdown завершает владельца после ответа; GC освобождает корни по правилам
runtime, когда процессы больше не удерживают их.

Saved остаётся номером подтверждённого внешнего сохранения. Undo/Redo его
не меняют, даже если восстановленные буквы совпадают с ранее сохранёнными.
Признак изменений консервативен: revision != saved. После настоящего сохранения
клиент подтверждает текущую ревизию MarkSaved. Равенство строк не является
подтверждением записи файла.

first/last/text у Undo/Redo игнорируются. Ответ содержит полный снимок, исходный
ID и offset/line/column=-1. Порядок отказов:

1. nil reply игнорируется; отрицательный ID даёт Invalid.
2. Неизвестная операция — Unknown; неверный expected — Conflict.
3. Закрытый документ — Closed.
4. Пустая нужная сторона истории — NotFound, даже на предельной ревизии.
5. Непустая история на MaxRevision — RevisionLimit.

Отказ не меняет текст, revision, saved и стеки. Предельная ревизия не
переполняется; неудавшийся Undo не извлекает запись. Владелец блокируется на
ответе, поэтому вызывающий обязан его принять. Отмены, подписок и replay cache нет.

## Лимиты

Общие для Undo+Redo пределы: 64 снимка и 1048576 символов суммы их длин.
Пустой снимок занимает запись. Текущий документ отдельно ограничен 1048576
символами. Списки хранят новые снимки впереди; перед публикацией подготовлены
новый текст и ограниченная кандидатная History.

При переходе сначала извлекается источник и добавляется обратный снимок в
назначение. При превышении лимита удаляются дальние записи источника, затем
дальние записи назначения. Для Replace источник пуст, назначение — Undo,
а Redo сброшен. Ближайший обратный снимок сохраняется, когда помещается в лимит.
Если в тестовой/изменённой конфигурации старый текст больше лимита истории,
его вытеснение не отменяет допустимую правку.

Это лимит логических символов/записей, не измеренных байтов кучи. Текущий текст,
представления строк, узлы, сохранённые клиентом Reply и временные аллокации имеют
отдельную жизнь. Старые ответы сохраняют текст. Runtime/allocation traps не
перехватываются; атомарность при таких traps не обещана. Пересборка списков
квадратична по ограниченному числу записей, максимум 65 кандидатных элементов.
Сумма длин при штатных пределах помещается в signed int.

## Запуск и проверки

С нативными Limbo/emu/module SDK из [первых шагов](../../README-FIRSTSTEPS.md):

```sh
python3 build-menu.py --projects ide --tests --demo history
```

Пример печатает восстановление first с revision=3/saved=1 и ветку third с
revision=6/saved=1. CTest требует успешный exit и PASS в двух режимах reference
emu. Сами режимы не доказывают вход в новый нативный JIT.

history_test.b проверяет Unicode, stale/nil запросы, no-op/отказы, saved,
ветвление, старые Reply, сессии, 65 правок и 64 шага Undo/Redo. historylimits_test.b
собирает неизменённый production-код с приватными пределами 3 записи/6 символов:
точные границы, приоритет вытеснения источника, пустые/крупные снимки.
revision_test.b использует MaxRevision=4 для проверки терминального отказа.
Тестовые лимиты никогда не устанавливаются как продукт.

Установка по-прежнему включает только idecore.dis, idecore.sbl, idecore.m.
Ограничение внешней VM в [REFERENCE_RUNTIME.md](REFERENCE_RUNTIME.md) сохранено.
Нет импорта/исправления этой VM, встраивания Dis в FlashVM, приёмки целевых JIT
или готового отладчика. История только в памяти, без persistence, coalescing,
многодокументного менеджера и протокола восстановления после нехватки памяти.
