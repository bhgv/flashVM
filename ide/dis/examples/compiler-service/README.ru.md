# Пример нативной сборки с билетом и ревизией

[English](README.md) · [Полный контракт](../../../COMPILER-SERVICE.ru.md) · [Прокомментированный код](main.b)

Настоящий Dis entry открывает логический документ, получает реальную ревизию,
отправляет оптимизированную Limbo→Dis сборку через idecompiler, читает принятую
копию артефакта и подтверждает завершение worker и workspace. Каждая непустая
строка исходника прокомментирована. UI/Draw/Tk не загружаются, внешние компиляторы
не запускаются, автоматического исполнения результата нет. Исходник вычисляет
6×7; отдельная приёмка действительно исполняет созданные артефакты.

В каталоге установленного включённого пакета:

```sh
./disvm --jit --stats --quantum 1 ./compiler-service.dis
./disvm --no-jit --stats --quantum 1 ./compiler-service.dis
```

Ожидается PASS compiler tutorial: revision=ok artifact=ok shutdown=ok.
NATIVE-MODULES.txt должен содержать Fircompiler=ON. При OFF модуль worker
остаётся переносимым, но start возвращает nil; успешная сборка не выдумывается.
Нативный вызов последовательный/блокирующий, отмены нет. Графические панели и
итоговые карты debugger PC этим примером не реализуются.

compiler-service-check.dis — отдельная приёмка 24 артефактов AS1/2/3/Limbo.
Она явно сохраняет результаты через Sys.create в текущий каталог: запускайте
её в пустом временном каталоге. check.py сравнивает байты/debug с CLI и исполняет
Dis/SWF на машине разработчика; развёрнутому worker Python не нужен. client.c
заново линкует независимую C99-библиотеку и проверяет 24 успеха, 32 чистых отказа,
восстановление после ошибки и повторное освобождение.

Reply.status относится к workspace, compiler — к нативной стадии. Debug
возвращается только после принятого успеха. Байты получаются отдельным запросом
Artifact; native pointers не передаются, предыдущий успешный результат не
выдаётся за неудачную новую сборку.
