# Загрузка опубликованной библиотеки Dis через Styx

[English](STYX.md) · [Исходник клиента](styx-client.b) · [Маршрут Styx](../../native/terminal/SCALAR-ROUTE.ru.md) · [API транспорта](../../module/STYXSCALAR-CALL.ru.md)

[Пример файла функции](../../native/terminal/SCALAR-FUNCTION.ru.md) показывает вызов через файл экспорта с нативным обработчиком.

Клиент подключает исходный `compute.m`, загружает `Compute` по обычному
пути VFS и вызывает `compute`. Публикатор может разместить по этому пути
сгенерированный адаптер Dis. Адаптер открывает файлы, отправляет запрос
записью и получает ответ чтением. Для каждого направления выдаётся своя
проекция файла `.unibus`.

## Подготовка и проверка публикации

Соберите [нативный SDK Styx](../../native/README.md) с поддержкой VFS, а также
[совпадающие по исходникам runtime и Limbo bootstrap](../../runtime/README.md)
с генератором CMake Unix Makefiles. В SDK соберите `terminal-scalar-route`.
Из корня репозитория запустите драйвер, подставив три пути к своим сборкам.

```sh
python3 disVM/native/terminal/tests/scalar/guest.py \
  build/scalar-runtime/disvm \
  build/scalar-runtime/bootstrap/limbo-bootstrap build/scalar-sdk
```

Драйвер собирает клиент и через `dvm_module_publish_scalar` привязывает
исходный узел и профиль к `implementation.dis`. Клиентский адаптер не
собирается. До старта клиента драйвер монтирует файлы запроса и ответа.
Две исходные сессии Styx работают на одном двустороннем соединении. Тестовый
владелец проверяет запрос и пишет ответ до подтверждения записи запроса.
Драйвер создаёт свежую пару файлов для каждого случая, проверяет ровно один
вызов владельца и завершает обе сессии после остановки DisVM. Ожидаемый
вывод содержит `PASS Styx Compute value`, `error` и `missing`
в интерпретаторе и JIT.

[Команда генератора](../../../compiler/limbo/frontend/REMOTE-OWNER.ru.md)
получает пути и теги при публикации. Для каждой пары нужно выдать свежий
приёмник ответа и допускать один незавершённый вызов. В первом тесте работает метод на C. Пример ниже
загружает и вызывает исходную реализацию в отдельном DisVM.

В тесте с двумя DisVM клиент после первой загрузки перекрывает `/scalar`
пустым каталогом. Оба экземпляра, загруженные до и после привязки, обращаются
к владельцу через файлы, закреплённые при публикации. Последний вызов идёт
через второй экземпляр и проверяет, что владелец сохранил состояние.

## Запуск владельца в отдельном DisVM

Обе стороны используют совместимый профиль из исходного `.m`. Владелец
запускает общий [scalarowner.dis](../../runtime/SCALAR-OWNER-SERVICE.ru.md).
Хост передаёт ему через `Launchcontext` путь реализации, имя экспорта,
пути запроса и ответа и два тега.

Владельцу выдайте приёмник запросов на чтение и файл ответов клиента на
запись. Клиенту выдайте собственный приёмник ответов на чтение и файл запросов
владельца на запись. Имена путей могут совпадать в обоих пространствах, хотя
стороны имеют разные права. Теги запроса и ответа должны совпадать с обеих
сторон. Владелец загружает реализацию один раз, читает запросы и отправляет значения
или записи об ошибках.

```sh
python3 disVM/native/terminal/tests/scalar/owner_guest.py \
  build/scalar-runtime/disvm \
  build/scalar-runtime/bootstrap/limbo-bootstrap build/scalar-sdk
```

Тест поднимает два отдельных процесса DisVM с разными корнями VFS на сессиях
Styx через TCP на loopback. Владелец загружает `implementation.dis`. Тот загружает
[privatevalue.dis](privatevalue.b) и через него читает локальный
`provider-secret`. В корне клиента есть одноимённый файл с другим значением.
Успешный вызов возвращает 142, а вызов с -1 получает запись об ошибке.
Удаление зависимости у владельца также даёт ошибку, хотя у клиента эта
библиотека есть. Все три сценария выполняются с JIT и без него. Старт владельца задержан до готовности
пути запроса, чтобы клиенту пришлось ждать ответ. После каждого сценария тест
закрывает обе сессии и дожидается обоих процессов.

В [последовательной сессии](../../native/terminal/SCALAR-SESSION.ru.md) один
экземпляр возвращает 142, затем ошибку и затем 144. Последнее число подтверждает,
что модуль у владельца сохранил состояние после ошибки. Произвольному удалённому
`.dis` по-прежнему нужна публикация адаптера или поиск владельца в runtime.

В тесте с двумя DisVM сервер владельца отдаёт настоящий `implementation.dis`
через [Styx](../../native/terminal/UNIBUS-SERVER-FILE.ru.md). Клиент монтирует
исходный файл и `.unibus` с одной сессии, связывает исходный узел с локальным
адаптером и проверяет чтение исходных байтов через тот же путь, что и `load`.

## Возврат полей из исходного Dis

Та же команда `owner_guest.py` компилирует [общий интерфейс](ref.m),
[клиента](styx-ref-owner.b) и [реализацию провайдера](ref-owner.b).
Клиент выполняет обычный `load Refexample "/peer/mounted/ref.dis"`
и вызывает `revise`. В кортеж результата входят счётчик вызовов владельца
и исходное поле `big`. Провайдер меняет оба поля, и клиент проверяет значения
через вторую ссылку на свой объект. Он также проверяет, что исключение после
записей у провайдера сохраняет поля клиента, что аргумент `nil` отклоняется
локально и что следующий вызов видит счётчик того же экземпляра модуля.
В обоих режимах ожидается `PASS mounted original ref Dis`. Драйвер завершает
оба процесса VM и удаляет их временные корни.

## Вызов с тремя аргументами

Команда `owner_guest.py` также компилирует [blend.m](blend.m) вместе с
[клиентом](styx-list-owner.b) и [исходным провайдером](blend-owner.b).
Клиент загружает `/peer/mounted/blend.dis` и вызывает
`blend(40, (-2, min), max)`. Провайдер получает три аргумента и складывает
два узких и два широких значения. Клиент присваивает вложенный результат
в `(count, (narrow, wide))` и проверяет `(1, (38, -1))`. Hosted-компилятор добавляет
[разрешённые типы](../../../tools/limbo-bootstrap/STYX-TYPE-TABLE.ru.md)
в образ владельца. Драйвер сверяет их через `.interface` и проверяет
отказ загрузчика на копии с изменённой сигнатурой в таблице типов. Нулевой первый
аргумент вызывает исключение. Следующий успешный вызов подтверждает,
что исходный экземпляр сохранил счётчик. С JIT и без JIT ожидается
`PASS mounted original argument list Dis`.

## Передача одного объекта в два аргумента ref

Та же команда `owner_guest.py` компилирует [ref.m](ref.m) вместе с
[клиентом](styx-refpair-owner.b) и [исходным владельцем](refpair-owner.b).
Клиент загружает `/peer/mounted/refpair.dis` и вызывает `exchange` с одним
объектом в обеих позициях. Владелец увеличивает `narrow` первого аргумента
на два, читает через второй и увеличивает второй ещё на три. Начальное
значение 7 становится 12 в одном объекте. Второй вызов передаёт два объекта
с одинаковыми полями и проверяет независимые изменения. Последующие
вызовы проверяют сохранение полей при исключении, локальный отказ при
`nil` и сохранение счётчика владельца. В последнем вызове два тестовых
маркера позволяют потоку клиента изменить второй объект после получения
снимков владельцем. Проверка подтверждает, что при конфликте сохраняются
локальная правка, первый объект и предыдущие значения результата.
Драйвер передаёт маркеры и удаляет временные корни. В обоих режимах ожидается
`PASS mounted original ref pair Dis`.

## Профиль фактического экспорта владельца

Команда `owner_guest.py` также запускает
[styx-loaded-profile.b](styx-loaded-profile.b) с
[другой исходной реализацией](blend-scalar-owner.b). Обе реализации
экспортируют `blend` с разными компилированными сигнатурами. Владелец
связывает вторую через
[общий сервис](../../runtime/SCALAR-OWNER-SERVICE.ru.md#профиль-из-исходного-load).
Первая попытка клиента загрузить трёхаргументный интерфейс возвращает
nil. По тому же пути VFS клиент загружает фактический интерфейс
`fn(int): int` и получает 42 от `blend(40)`. В режимах с JIT и без JIT
ожидается `PASS Styx profile from loaded export`.

## Загрузка шести экспортов с общим состоянием

Запустите ту же команду `owner_guest.py`. Она собирает
[интерфейс](loaded-set.m), [владельца](loaded-set-owner.b) и
[клиента](styx-loaded-set.b). Владелец публикует выбранные имена
из одного исходного образа. Клиент делает обычный `load`
`/peer/mounted/set.dis` с полным интерфейсом и с одним экспортом.
Вызовы чередуют `int`, `big`, кортеж, один `ref`, вложенный список
аргументов и две ссылки на один объект. Оба импорта видят общий счётчик,
в том числе после исключения владельца. Во втором прогоне запрашивается
отсутствующий экспорт, и клиент проверяет отказ даже для корректной
части интерфейса. Драйвер закрывает каналы и удаляет временные каталоги.
В обоих режимах просмотрите `PASS mounted loaded export set shares state`
и `PASS loaded export set refused as a whole`.
