# Загрузка опубликованной библиотеки Dis через Styx

[English](STYX.md) · [Исходник клиента](styx-client.b) · [Маршрут Styx](../../native/terminal/SCALAR-ROUTE.ru.md) · [API транспорта](../../module/STYXSCALAR-CALL.ru.md)

[Пример файла функции](../../native/terminal/SCALAR-FUNCTION.ru.md) показывает вызов через файл экспорта с нативным обработчиком.

Клиент подключает исходный `compute.m`, загружает `Compute` по обычному
пути VFS и вызывает `compute`. Публикатор может разместить по этому пути
сгенерированный адаптер Dis. Адаптер открывает файлы, отправляет запрос
записью и получает ответ чтением. Для каждого направления выдаётся своя
проекция файла `.unibus`.

## Подготовка и проверка публикации

Соберите [нативный SDK Styx](../../native/README.md) с поддержкой VFS, а также
[совпадающие по исходникам runtime и Limbo bootstrap](../../runtime/README.md)
с генератором CMake Unix Makefiles. В SDK соберите `terminal-scalar-route`.
Из корня репозитория запустите драйвер, подставив три пути к своим сборкам.

```sh
python3 disVM/native/terminal/tests/scalar/guest.py \
  build/scalar-runtime/disvm \
  build/scalar-runtime/bootstrap/limbo-bootstrap build/scalar-sdk
```

Драйвер собирает клиент и через `dvm_module_publish_scalar` привязывает
исходный узел и профиль к `implementation.dis`. Клиентский адаптер не
собирается. До старта клиента драйвер монтирует файлы запроса и ответа.
Две исходные сессии Styx работают на одном двустороннем соединении. Тестовый
владелец проверяет запрос и пишет ответ до подтверждения записи запроса.
Драйвер создаёт свежую пару файлов для каждого случая, проверяет ровно один
вызов владельца и завершает обе сессии после остановки DisVM. Ожидаемый
вывод содержит `PASS Styx Compute value`, `error` и `missing`
в интерпретаторе и JIT.

[Команда генератора](../../../compiler/limbo/frontend/REMOTE-OWNER.ru.md)
получает пути и теги при публикации. Для каждой пары нужно выдать свежий
приёмник ответа и допускать один незавершённый вызов. В первом тесте работает метод на C. Пример ниже
загружает и вызывает исходную реализацию в отдельном DisVM.

В тесте с двумя DisVM клиент после первой загрузки перекрывает `/scalar`
пустым каталогом. Оба экземпляра, загруженные до и после привязки, обращаются
к владельцу через файлы, закреплённые при публикации. Последний вызов идёт
через второй экземпляр и проверяет, что владелец сохранил состояние.

## Запуск владельца в отдельном DisVM

Обе стороны используют совместимый профиль из исходного `.m`. Владелец
запускает общий [scalarowner.dis](../../runtime/SCALAR-OWNER-SERVICE.ru.md).
Хост передаёт ему через `Launchcontext` путь реализации, имя экспорта,
пути запроса и ответа и два тега.

Владельцу выдайте приёмник запросов на чтение и файл ответов клиента на
запись. Клиенту выдайте собственный приёмник ответов на чтение и файл запросов
владельца на запись. Имена путей могут совпадать в обоих пространствах, хотя
стороны имеют разные права. Теги запроса и ответа должны совпадать с обеих
сторон. Владелец загружает реализацию один раз, читает запросы и отправляет значения
или записи об ошибках.

```sh
python3 disVM/native/terminal/tests/scalar/owner_guest.py \
  build/scalar-runtime/disvm \
  build/scalar-runtime/bootstrap/limbo-bootstrap build/scalar-sdk
```

Тест поднимает два отдельных процесса DisVM с разными корнями VFS на сессиях
Styx через TCP на loopback. Владелец загружает `implementation.dis`. Тот загружает
[privatevalue.dis](privatevalue.b) и через него читает локальный
`provider-secret`. В корне клиента есть одноимённый файл с другим значением.
Успешный вызов возвращает 142, а вызов с -1 получает запись об ошибке.
Удаление зависимости у владельца также даёт ошибку, хотя у клиента эта
библиотека есть. Все три сценария выполняются с JIT и без него. Старт владельца задержан до готовности
пути запроса, чтобы клиенту пришлось ждать ответ. После каждого сценария тест
закрывает обе сессии и дожидается обоих процессов.

В [последовательной сессии](../../native/terminal/SCALAR-SESSION.ru.md) один
экземпляр возвращает 142, затем ошибку и затем 144. Последнее число подтверждает,
что модуль у владельца сохранил состояние после ошибки. Произвольному удалённому
`.dis` по-прежнему нужна публикация адаптера или поиск владельца в runtime.

В тесте с двумя DisVM сервер владельца отдаёт настоящий `implementation.dis`
через [Styx](../../native/terminal/UNIBUS-SERVER-FILE.ru.md). Клиент монтирует
исходный файл и `.unibus` с одной сессии, связывает исходный узел с локальным
адаптером и проверяет чтение исходных байтов через тот же путь, что и `load`.

## Возврат полей из исходного Dis

Та же команда `owner_guest.py` компилирует [общий интерфейс](ref.m),
[клиента](styx-ref-owner.b) и [реализацию провайдера](ref-owner.b).
Клиент выполняет обычный `load Refexample "/peer/mounted/ref.dis"`
и вызывает `revise`. В кортеж результата входят счётчик вызовов владельца
и исходное поле `big`. Провайдер меняет оба поля, и клиент проверяет значения
через вторую ссылку на свой объект. Он также проверяет, что исключение после
записей у провайдера сохраняет поля клиента, что аргумент `nil` отклоняется
локально и что следующий вызов видит счётчик того же экземпляра модуля.
В обоих режимах ожидается `PASS mounted original ref Dis`. Драйвер завершает
оба процесса VM и удаляет их временные корни.

## Вызов с тремя аргументами

Команда `owner_guest.py` также компилирует [blend.m](blend.m) вместе с
[клиентом](styx-list-owner.b) и [исходным провайдером](blend-owner.b).
Клиент загружает `/peer/mounted/blend.dis` и вызывает
`blend(40, (-2, min), max)`. Провайдер получает три аргумента и складывает
два узких и два широких значения. Клиент присваивает вложенный результат
в `(count, (narrow, wide))` и проверяет `(1, (38, -1))`. Hosted-компилятор добавляет
[разрешённые типы](../../../tools/limbo-bootstrap/STYX-TYPE-TABLE.ru.md)
в образ владельца. Драйвер сверяет их через `.interface` и проверяет
отказ загрузчика на копии с изменённой сигнатурой в таблице типов. Затем
драйвер меняет тип локального импорта, сохраняя его сигнатуру. Обычный
`load` отклоняет профиль, несмотря на совпадение имени и сигнатуры.
Копия клиента без таблицы типов проверяет прежний путь импорта. Нулевой первый
аргумент вызывает исключение. Следующий успешный вызов подтверждает,
что исходный экземпляр сохранил счётчик. С JIT и без JIT ожидается
`PASS mounted original argument list Dis`.

## Передача одного объекта в два аргумента ref

Та же команда `owner_guest.py` компилирует [ref.m](ref.m) вместе с
[клиентом](styx-refpair-owner.b) и [исходным владельцем](refpair-owner.b).
Клиент загружает `/peer/mounted/refpair.dis` и вызывает `exchange` с одним
объектом в обеих позициях. Владелец увеличивает `narrow` первого аргумента
на два, читает через второй и увеличивает второй ещё на три. Начальное
значение 7 становится 12 в одном объекте. Второй вызов передаёт два объекта
с одинаковыми полями и проверяет независимые изменения. Последующие
вызовы проверяют сохранение полей при исключении, локальный отказ при
`nil` и сохранение счётчика владельца. В последнем вызове два тестовых
маркера позволяют потоку клиента изменить второй объект после получения
снимков владельцем. Проверка подтверждает, что при конфликте сохраняются
локальная правка, первый объект и предыдущие значения результата.
Драйвер передаёт маркеры и удаляет временные корни. В обоих режимах ожидается
`PASS mounted original ref pair Dis`.

## Профиль фактического экспорта владельца

Команда `owner_guest.py` также запускает
[styx-loaded-profile.b](styx-loaded-profile.b) с
[другой исходной реализацией](blend-scalar-owner.b). Обе реализации
экспортируют `blend` с разными компилированными сигнатурами. Владелец
связывает вторую через
[общий сервис](../../runtime/SCALAR-OWNER-SERVICE.ru.md#профиль-из-исходного-load).
Первая попытка клиента загрузить трёхаргументный интерфейс возвращает
nil. По тому же пути VFS клиент загружает фактический интерфейс
`fn(int): int` и получает 42 от `blend(40)`. В режимах с JIT и без JIT
ожидается `PASS Styx profile from loaded export`.

## Загрузка шести экспортов с общим состоянием

Запустите ту же команду `owner_guest.py`. Она собирает
[интерфейс](loaded-set.m), [владельца](loaded-set-owner.b) и
[клиента](styx-loaded-set.b). Владелец публикует выбранные имена
из одного исходного образа. Клиент делает обычный `load`
`/peer/mounted/set.dis` с полным интерфейсом и с одним экспортом.
Вызовы чередуют `int`, `big`, кортеж, один `ref`, вложенный список
аргументов и две ссылки на один объект. Оба импорта видят общий счётчик,
в том числе после исключения владельца. Во втором прогоне запрашивается
отсутствующий экспорт, и клиент проверяет отказ даже для корректной
части интерфейса. Драйвер закрывает каналы и удаляет временные каталоги.
В обоих режимах просмотрите `PASS mounted loaded export set shares state`
и `PASS loaded export set refused as a whole`.

## Вызов по скомпилированной схеме

Запустите ту же команду `owner_guest.py`. Она компилирует
[интерфейс](dynamic-set.m), [реализацию](dynamic-set-owner.b)
и [клиент](styx-dynamic-set.b) с `-D R`. Владелец один раз загружает
исходную реализацию. Клиент открывает `/peer/mounted/dynamic.dis`
обычным `load` Limbo и вызывает экспорты как функции модуля. Оба пути
вызова работают с одним счётчиком в VM владельца.

Клиент проверяет вызовы с нулём–четырьмя скалярными ячейками, вложенные
кортежи результата, границы знакового `big`, функцию без результата и
успешный вызов после исключения у владельца. Ожидаемая строка –
`PASS mounted dynamic scalar call layouts`. Второй образ клиента
собирается без `-D R`. Загрузка полного интерфейса отклоняется, а
фиксированный профиль `tally` загружается из того же модуля.
Тест закрывает соединения Styx и удаляет временные корни.

См. [формат обмена](../../native/terminal/SCALAR-FUNCTION.ru.md#вызов-по-скомпилированным-скалярным-типам).

## Вызов по скомпилированным типам ref

Запустите ту же команду `owner_guest.py`. Она компилирует
[интерфейс](compiled-ref.m), [исходную реализацию](compiled-ref-owner.b)
и [клиент](styx-compiled-ref.b). Клиент загружает
`/peer/mounted/compiled-ref.dis` через `load`. Вызов `bump` принимает
одну ссылку и возвращает `int`. Вызов `revise` принимает кортеж из двух
ссылок и возвращает только изменения объектов. Вызов `inspect` возвращает
кортеж, по которому клиент проверяет, указывали ли обе ссылки на один
объект у владельца.

Тест согласует параллельную правку на клиенте с обработкой запроса у
владельца через маркеры в двух временных корнях. Он проверяет, что правка
клиента сохраняется и ни в один объект изменения владельца не попадают.
Также проверяются исключение владельца, отказ на `nil` и общее состояние
модуля после отказа. Ожидаемая строка с JIT и без него –
`PASS mounted compiled ref argument layouts`. Второй образ клиента без
таблицы типов получает отказ. Тест закрывает соединения и удаляет оба корня.

См. [формат обмена](../../native/terminal/SCALAR-FUNCTION.ru.md#вызов-по-скомпилированным-типам-ref).

## Вызов через встречный маунт Styx

Та же команда `owner_guest.py` компилирует [интерфейс](scoped-calls.m),
[клиент](styx-scoped-calls.b) и [владельца](scoped-calls-owner.b).
Лаунчер поднимает прямой сервер и встречный сервер клиента на двух
каналах одного TCP-соединения. Исходный Dis провайдера обычными
операциями Sys читает `/.prog/.self/.pid`, `.vfs/env/CLIENT`,
`.var/counter` и `.fd/3`. Клиент передаёт только прикладной флаг ошибки.
По возвращённому PID он проверяет, чей контекст выбран.

У родителя и двух процессов после `spawn` разные PID и общая позиция
чтения унаследованного FD. После исключения провайдера следующий вызов
работает. Сохранённый провайдером fid после ответа больше не читается.
`update` проверяет одну ссылку, `updatepair` проверяет одинаковые и
раздельные ссылки и отказ до обратной записи. После `FORKNS` владелец
читает событие namespace из очереди вызова. После ответа из сохранённого
FD событий читаются запись завершения и EOF.
Проверка выдаёт `PASS compiled call sees scoped caller VFS, refs and Sysevents`.
Второй маунт без встречной привязки отклоняет импорт и выдаёт
`PASS scoped compiled load requires reverse mount`. Тест закрывает оба
канала и удаляет временные каталоги.

См. [настройку сервера](../../native/terminal/UNIBUS-SERVER-SCOPED-SET.ru.md).

Этот же пример читает первую запись namespace из `/.prog/.self/.sysevents`
через встречный Styx и проверяет отказ при открытии на запись.
См. [описание очереди](../../runtime/SYSTEM-EVENTS.md#встречная-очередь-событий).

До `load` клиент публикует целочисленные файлы в обоих деревьях,
`.var` и `.vfs`. Когда провайдер открывает встречный поток, клиент
через `intset` меняет `.var/live` с 41 на 65539 и через `Sys->write`
меняет `.vfs/live` с 42 на 131077. Провайдер получает отдельное
уведомление об изменении содержимого каждого дерева через тот же
открытый fid, затем читает оба четырёхбайтовых значения из `/.prog/.self`.

Провайдер проверяет пустое чтение через тот же fid перед обновлением.
Клиент также меняет третью переменную вне выданных деревьев. В очереди
появляются только два уведомления от расшаренных деревьев.

После ответа тест также проверяет отказ чтения из сохранённого fid.

Для проверки переполнения клиент делает 33 изменения, пока провайдер
не читает очередь. Провайдер получает `system 3`, перечитывает текущее
значение из `.var/live` и дочитывает уведомление, вызвавшее переполнение.
Следующее изменение снова приходит обычным уведомлением через тот же fid.

Проверка `terminal-caller-mount-cli` удерживает публикации двух PID
одновременно, пока выполняется первый вызов. У каждого потока событий
своя начальная запись namespace, даже если первый вызов уже прочитал
свою запись. Прямой диспетчер выполняет вызовы последовательно.

После возврата обоих дочерних вызовов родитель делает ещё один вызов.
Во время него провайдер проверяет отказ чтения через сохранённый fid
первого клиента и успешное чтение через fid родительского процесса.

Родитель повторяет вызов с тем же PID. Старый fid остаётся отозванным, а через новый fid чтение работает.

## Запуск через три DisVM

Выполните `ctest --test-dir <sdk-build> -R '^terminal-caller-mount-cli$' -V`
со сборками Styx SDK и DisVM с поддержкой запуска. Тест поднимает локальные TCP-соединения
и отдельные процессы DisVM. A монтирует объявленный
маршрут B, привязывает программу к `/alias.dis` и вызывает `run`.
B через [маунт библиотек](../../runtime/TERMINAL-LAUNCH-CLI.ru.md#маунт-библиотеки-styx-у-владельца)
загружает исходный экспорт Dis на C с общим интерфейсом `wide.m`.
B читает FD 0 клиента A и пишет разные сообщения в его FD 1 и FD 2.
Тест проверяет коды завершения всех трёх процессов. Ожидаемая строка
в обоих режимах VM — `PASS A-B-C Styx launch and library call`.

C публикует `wide.dis` и `managed.dis` на одной штатной двусторонней
сессии. B монтирует её через `--library-bidir-fd` и загружает модули по
обычным путям VFS. Вызов передаёт вложенные `ref` с общими ссылками
и проверяет обратную запись на B. Во время вызова C читает явно выданный
A файл VFS и пишет в FD 8, унаследованный от A. Тест сверяет итоговые байты
и общую позицию файла на A. Проверка идёт по loopback TCP на одном хосте.

В цепочке B также меняет порядок слоёв union. Один и тот же путь
`load` сначала разрешается в локальную библиотеку, а после `bind` —
в библиотеку C. B проверяет права FD 3 и читает с уже установленной
позиции. A получает результат вызова `run` через тот же fid `.unibus`. В отдельном сценарии
тест подаёт неверный ввод и проверяет получение ошибки владельца.

В проверке обрыва тест завершает B после того, как его Dis подтвердил вход в программу. A сообщает об ошибке транспорта без получения статуса завершения.

Цепочка также подключает второго библиотечного провайдера в `/other-libs`.
Оба публикуют `wide.dis`. B проверяет, что у второго счётчик начинается
заново, а у первого сохраняется состояние прежних вызовов.

### Проверка на отдельных машинах

На каждой машине запустите [run_chain.py](run_chain.py) из каталога
`disVM/examples/remote-scalar` в копии исходников.
В `DISVM` укажите исполняемый файл со Styx SDK, в `LIMBO` — компилятор
нативных ячеек этой машины. Скрипт соберёт образы для своей роли и передаст
подключённые TCP-дескрипторы штатному CLI. Используйте закрытую тестовую
сеть. В `B_ADDR` и `C_ADDR` укажите доступные адреса машин B и C.
Запустите C, дождитесь вывода адресов и запустите B. Затем запустите A,
когда B выведет адрес.

```sh
# Машина C
python3 run_chain.py --runtime "$DISVM" --limbo "$LIMBO" c \
  --listen "$C_ADDR:9031" --alternate-listen "$C_ADDR:9032"
# Машина B
python3 run_chain.py --runtime "$DISVM" --limbo "$LIMBO" b \
  --listen "$B_ADDR:9030" --library "$C_ADDR:9031" --alternate "$C_ADDR:9032"
# Машина A
python3 run_chain.py --runtime "$DISVM" --limbo "$LIMBO" a --owner "$B_ADDR:9030"
```

На основном соединении C публикует библиотеки, корневой образ
`implementation.dis` и именованный образ `programs/leaf.dis`. После
загрузки библиотек B запускает корневой образ по пути маунта, затем
именованный через `bind`. C читает свой локальный файл и выданный A файл
`.vfs`, проверяет права FD 3 и пишет в FD 1 и 2 клиента A. Записи через
унаследованные алиасы FD 7 и 8 оставляют файл A со строкой `skipABCDEF`.
Запуск с неверным аргументом возвращает B ошибку на его собственном fid.

В той же проверке A публикует живую переменную и ячейку только для чтения
в `/.var`. Сначала экспорт C меняет переменную A через B. Затем отдельная
программа C меняет её при запуске из потомка B. Явный маунт B переключает
следующий запуск на свою ячейку, а после `unmount` снова доступна
выдача A. A проверяет финальное значение. На C сохраняются права чтения
и скрыты обычные файлы B из неопубликованного дерева.

A также загружает `chain-fd.dis` на B. Эта функция загружает тот же
интерфейс с C и передаёт вызов. В аргументах два номера дескрипторов.
Первый открыт `Sys->open`, второй создан `Sys->create`. A читает
`skip` до вызова. C с той же позиции получает `live` и пишет его в выходной
файл A. Стенд монтирует постороннее дерево в `/fd` на A и проверяет через
обе библиотеки исходные режимы открытия, маркер VFS и живую переменную A.
Перед проверкой файлов A отменяет уже начатый вызов и повторяет вызов
из того же PID.

Во вложенном вызове B привязывает другой файл по своему пути
`/.prog/.self/.fd/7`. Числовой путь и уже открытый FD продолжают вести
к файлу A. B выдаёт C отдельный FD 7 только для чтения и свою переменную
в `.var`. C читает файл B и изменяет ячейку B. Выдача A сохраняется,
а следующий вызов из того же PID снова видит исходные ресурсы A.

Стенд также обменивается сообщениями с настоящим `chan of int` на A.
C открывает два номерных виртуальных файла в `.prog/<pid>/.fd`
по встречному Styx через B.
A подтверждает доставку после приёма значения через локальный `alt`
и возвращает ответ через второй конец.
См. [Vfsexport.recordpipe](../../runtime/RECORD-PIPE.ru.md).

A также отменяет ожидание после сигнала, что программа на C уже вошла
в цикл `big`. Закрытие fid идёт через B до C. Затем новый запуск и вызов
библиотеки проходят по тем же соединениям. A сверяет результаты, вывод
обоих провайдеров и позиции файлов. Все три роли выводят `PASS Styx chain`
и завершаются с кодом ноль. Второй экземпляр на C проверяет независимость
состояния двух маунтов. Для прогона с JIT добавьте
`--jit` перед именем роли на каждой машине и повторите три команды.
Роль `local` запускает ту же проверку по loopback. Она включена в CTest
сборки DisVM со Styx SDK.

В примере с контекстом клиент завершает дочерний поток после входа
владельца в функцию. Закрытие fid доходит до точки проверки отмены
на владельце. Родитель затем повторно использует то же соединение
и тот же экспорт.
