# Загрузка библиотеки Dis со строками и массивами через Styx

[English version](README.md) · [Примеры удалённого Dis](../README.ru.md)

Два процесса DisVM используют одну сессию Styx. Владелец публикует шесть экспортов
одного загруженного экземпляра [target.b](target.b). Клиент подключает
[managed.m](managed.m), загружает модуль по смонтированному пути и вызывает функции
обычным синтаксисом Limbo. Владелец строит шлюз по типам, записанным компилятором.

## Запуск

Соберите нативный SDK Styx и DisVM с этим SDK. Из корня репозитория передайте
скрипту пути к согласованным бинарникам DisVM и компилятора Limbo.

```sh
python3 disVM/examples/remote-scalar/managed-fid/run.py \
    build/scalar-runtime/disvm build/scalar-runtime/bootstrap/limbo-bootstrap
```

Скрипт компилирует образы с `-D RG`, запускает процессы в отдельных временных
каталогах, соединяет их по одному локальному TCP-соединению и удаляет временные
файлы после завершения. Оба режима должны вывести `PASS managed Styx load`.

## Как проходит вызов

1. Клиентский `load` сверяет сигнатуры и схемы из `.interface` с теми, что записал
   в импорт компилятор. Функции видны как файлы в каталоге `managed.dis`.
2. Клиент открывает fid функции и записывает одну S-запись с
   `(PID клиента, аргументы…)`. Запись может занять несколько операций Styx.
   Владелец запускает вызов, когда получает всю запись указанной длины.
3. Владелец передаёт запрос исполнителю клиента. Сгенерированный шлюз
   восстанавливает локальные аргументы и вызывает исходный экспорт через
   `mcall`. Ответ уходит через приватный маршрут этого fid.
4. Клиент читает ответ и закрывает fid. В ответе две позиции, для результата
   и обновлений ссылок. Для функции без результата первая позиция содержит `nil`.

Пример проверяет строку UTF-8, возвращённый массив байтов, вызов без результата,
исключение владельца и два параллельных вызова с записями длиннее одного
сообщения Styx. Он также передаёт один ADT через два аргумента `ref` и проверяет,
что у неизменившегося ADT на клиенте остался его исходный массив.
Затем пример меняет строку и проверяет, что массив в том же ADT сохранился.

Запрос описывает каждый ADT, отличный от `nil`, один раз. Повторные ссылки
содержат его индекс. Во второй позиции ответа идёт маска изменившихся ссылок
в развёрнутом порядке аргументов. Если владелец публикует `.ref-fields`, клиент
запрашивает дельты отдельным тегом вызова. Для каждой выбранной ссылки приходит
маска её полей и только значения, отмеченные этой маской. Кортежи разворачиваются
в порядке схемы. Пустая позиция означает, что обновлений нет. Владелец сверяет итоговые значения
полей с запросом, поэтому запись того же значения не устанавливает бит.
Клиент проверяет ответ целиком и применяет результат и обновления вместе.
При исключении обратная запись не выполняется.

Профиль поддерживает ограниченные по размеру ADT с полями из скаляров,
строк, массивов и кортежей. Обратная запись в поля объектов аргументов поддерживается для значений. Массив считается одним полем. Файл `.ref-fields` длиной в два байта объявляет
поддержку нескольких участков. Если размер кодированного массива прежний,
владелец выбирает несколько участков, когда они компактнее одной замены.
Близкие участки объединяются, если это экономит байты. Клиент сверяет порядок
и границы участков и проверяет тип восстановленного массива до обратной
записи. Файл `.ref-fields` длиной в три байта также объявляет поддержку
вставок и удалений при изменении размера. Владелец передаёт смещение, число
удаляемых байтов и вставляемые байты, если это компактнее полной записи.
Общий префикс и суффикс берутся из запроса. При обширной правке может прийти
весь массив.
Когда в вызове участвует старая сторона без поддержки дельт, каждый изменённый
ADT передаётся полным снимком.

Файл `.ref-fields` длиной в четыре байта объявляет также поддержку участков
строк UTF-8. Граница участка может проходить внутри символа. Получатель
проверяет всю восстановленную строку перед обновлением. Старые стороны
получают строковое поле целиком.

Файл `.ref-fields` длиной в пять байтов объявляет несколько замен в одном
значении. Смещения каждой замены отсчитываются от исходного значения.
После несовпадения владелец ищет совпадающий участок в пределах ограниченного
окна. Если такой ответ короче, он может сохранить длинную общую середину
между вставкой и удалённой от неё заменой. В остальных случаях используются
прежние форматы.

Файл `.ref-fields` длиной в шесть байтов разрешает 256 разных ссылок в
результате, включая ссылки из аргументов. Ранние версии допускают 16.
Пример с `bundle` заполняет таблицу ссылок и проверяет повторную ссылку на
последний объект. Лимит размера S-записи сохраняется.

Пример с вложенными значениями передаёт массив строк UTF-8 и объект `ref`
с массивом байтовых массивов и массивом кортежей. У каждого элемента своя
S-запись. Для `nil` и пустого массива используются разные записи. Ответ
возвращает массивы по значению и обновляет существующий объект `ref` клиента.
Элементы могут содержать скаляры, строки, массивы и кортежи в пределах
ограничений схемы и размера записи.

Результат может содержать значения `ref`, в том числе в кортеже. Если
владелец возвращает объект аргумента, клиент получает исходную ссылку.
Для нового объекта клиент восстанавливает поля из вложенных S-записей.
Повторные ссылки на один новый объект в ответе указывают на один объект
клиента. Индексы действуют в пределах вызова. Пример проверяет эти случаи,
компонент результата со значением `nil` и обновление исходного объекта.

Возвращаемые объекты могут содержать `ref` в полях ADT и элементах массива.
Для этих мест используется та же таблица индексов, что для аргументов и
остального результата. Определение нового объекта предшествует ссылкам
на него. Профиль принимает конечные схемы и завершённые определения.
Файл `.ref-fields` длиной в семь байтов разрешает вложенные ссылки в
аргументах. Клиент и владелец удерживают исходные объекты по индексам
запроса до конца вызова, даже если владелец удалил все ссылки на объект из
аргументов. Запрос использует тег 110 и по-прежнему передаёт PID клиента
первым в fid функции. В ответе сначала идёт результат, затем запись с
тегом 16. Каждый изменившийся объект внутри неё имеет тег 10, байт
исходного индекса и новые значения полей. Объекты перечисляются по
возрастанию индекса. Новые объекты могут определяться в результате или
в обновлениях. Клиент проверяет обе записи до применения изменённых
полей к исходным объектам. Массив верхнего уровня передаётся по значению.
Изменения объектов `ref` внутри массива записываются обратно. Сигнатура с
такими аргументами загружается при поддержке графов обеими сторонами.

В примере `changegraph` один объект передаётся через поле ADT, массив
в ADT и отдельный аргумент-массив. Владелец заменяет ссылки и затем
обновляет исходный объект. Клиент проверяет обратную запись и исходную
ссылку в результате. При исключении объекты клиента сохраняют прежние
значения.


Семибайтовое содержимое `v00008\n` выбирает тег запроса 111 и тег
списка обновлений 17 для сигнатур с вложенными ссылками. Каждое обновление
начинается с исходного индекса и ненулевой однобайтовой маски. Нулевой бит
выбирает первое нативное поле. Поля кортежей разворачиваются в порядке
объявления. После маски идут записи только выбранных полей. Ссылки используют
общую таблицу для результата и всех обновлений. Изменённые строки и массивы
передаются целиком. При прежнем содержимом `v00007\n` или старом клиенте
используются тег 110 и полные снимки изменившихся объектов. В примере
массив из 4096 байт остаётся без изменений, а функция возвращает отдельный
массив из 3000 байт. Кодирование обоих массивов превысило бы лимит ответа.
Клиент также проверяет, что сохранился исходный массив.


Перед применением графового ответа клиент проверяет исходные пути к ссылкам
под теми же блокировками, которые использует обратная запись. Если поток
клиента заменил ссылку другим объектом или значением `nil`, вызов выдаёт
`remote ref argument changed while waiting` и не применяет обновления.
Другой поток может менять данные того же объекта. Ответ владельца заменяет
только поля, которые он вернул.
