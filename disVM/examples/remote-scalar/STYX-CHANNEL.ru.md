# Передача канала Limbo через Styx

[English](STYX-CHANNEL.md) · [Руководство по загрузке библиотек](STYX.ru.md)

Обычный `load` связывает экспорт библиотеки, который принимает живой
`chan of T`. Клиент открывает файл смонтированной функции как обычно.
DisVM публикует виртуальный файл `.prog/<pid>/.unibus` во встречном
контексте Styx клиента и отправляет по одному ключу на каждый отличный от
`nil` канал. Если один канал передан дважды, провайдер получает две ссылки
на один прокси. Исходная функция Dis работает со штатными инструкциями канала.
Поток, который она запускает через `spawn`, может использовать те же прокси до
завершения вызова. Если функция возвращает выданный клиентом канал, клиент
получает исходный объект с той же очередью и буфером. Выдать канал можно
в начальных аргументах или позднее внутри сообщения.
Функция также может вернуть новый канал провайдера. Клиент работает с ним
через обычные инструкции каналов Limbo.

## Запуск примера

Соберите SDK и DisVM с его поддержкой по
[руководству по загрузке библиотек](STYX.ru.md#подготовка-и-проверка-публикации).
Из корня репозитория запустите сценарий с путями к собранным DisVM и Limbo.

```sh
python3 disVM/examples/remote-scalar/run_channel.py \
    --runtime build/scalar-runtime/disvm \
    --limbo build/scalar-runtime/bootstrap/limbo-bootstrap
```

Опция `--jit` запускает обе VM в режиме JIT. Сценарий компилирует клиент и
провайдер с `-D RG`, запускает два процесса DisVM в отдельных временных
каталогах и связывает их через TCP loopback. Он проверяет вывод
`PASS automatic Limbo channels over UniBus` и удаляет образы при выходе.

| Исходник | Что показывает |
| --- | --- |
| [Интерфейс](chain-channel.m) | Обычные типизированные параметры и канал в результате. |
| [Клиент](styx-channel-client.b) | Обычный `load`, большой кортеж, каналы внутри сообщений, отмена и повторный вызов, возврат исходных каналов. |
| [Провайдер](styx-channel-owner.b) | Штатные инструкции канала в основном потоке и в `spawn`, разреженные массивы прокси в выборе и смешанные ветки с `*`. |

Запустите [run_channel_pair.py](run_channel_pair.py) с теми же опциями, чтобы
проверить обмен между двумя потоками провайдера через один
небуферизованный прокси, пока клиент ждёт результат функции.

Запустите [run_channel_lifetime.py](run_channel_lifetime.py) с именем
сценария и теми же опциями.

```sh
python3 disVM/examples/remote-scalar/run_channel_lifetime.py mixed \
    --runtime build/scalar-runtime/disvm \
    --limbo build/scalar-runtime/bootstrap/limbo-bootstrap
```

| Сценарий | Что проверяет |
| --- | --- |
| `mixed` | Блокирующие локальные и удалённые ветки, обмен двух смешанных выборов на одной UniBus и отмену. |
| `result` | Возврат нового канала через `load`, работу после выгрузки модуля, идентичность общего канала и независимое освобождение групп. |

## Операции с каналом

VM, которая ждёт ответа функции, обслуживает запросы UniBus через очереди
исходного канала. Отправка завершается, когда получатель принял значение
или когда оно помещено в буфер. Приём берёт значение из исходного буфера
либо у ожидающего отправителя. Если во время одного вызова два потока
провайдера ждут противоположных операций на небуферизованном канале,
UniBus сначала проверяет локальных ожидающих, затем сопоставляет два fid.
Оба ответа публикуются под одной блокировкой. Неблокирующий выбор получает
ветку по умолчанию, если после этой проверки пары для него нет.

`alt` провайдера с удалёнными ветками передаёт их одним запросом и
выполняет одну. Приём из массива добавляет вариант на каждый канал,
отличный от `nil`. Возвращаются исходная ветка и индекс элемента. При
наличии ветки по умолчанию можно смешивать локальные и удалённые варианты.
VM проверяет каждый не более одного раза в случайном порядке и
останавливается на первом совпадении. Блокирующий смешанный `alt`
регистрирует локальные ветки в обычных очередях Dis и периодически снимает
их под той же блокировкой, под которой их могут выбрать другие потоки.
В это время удалённые ветки одного маршрута ждут на UniBus до 40 мс со
стороны владельца. Два таких запроса могут встретиться на одной шине.
Локальный выбор возобновляется после ответа владельца. Ветка, которая
выполнилась, определяет результат выбора.

Для каждой операции шлюз открывает новый fid на чтение и запись в
существующей встречной сессии Styx. Запрос и ответ идут через этот fid.
S-запись может занимать несколько сообщений Styx. Операция становится
видна после проверки полной записи и типов. При отмене или возврате клиент
закрывает приём запросов UniBus и отзывает выдачу. Провайдер в этот момент
отзывает маршрут в дочерних потоках. Если соединение рвётся после выполнения
операции, провайдер получает ошибку, а VM не повторяет операцию.

Кодек управляемых значений переносит числа, строки, массивы, кортежи,
поддерживаемые `ref`-значения и каналы. Обычные общие `ref`-ссылки
сохраняются внутри одного сообщения. Канал сохраняет идентичность между
сообщениями и потоками провайдера в одном вызове. Провайдер может вернуть
в сообщении выданный ему канал. UniBus проверяет каждый такой ключ и тип
по выдаче клиента до отправки.

Для нового канала провайдера клиент использует файл `.unibus` в
`mounted/<module>` на существующем соединении Styx. В результате функции
приходят непрозрачный токен группы и ключ каждого канала. Для отдельной
операции клиент открывает свой fid и передаёт токен перед S-записью.
Исходный fid функции остаётся открыт, пока жив хотя бы один прокси группы,
в том числе после выгрузки модуля. Освобождение последнего прокси закрывает
этот fid и освобождает обслуживание каналов у провайдера.

Лимит операции составляет 64 КиБ вместе с заголовками и вложенными ветками.
Каналы могут быть отдельными аргументами и результатами или входить в
массивы и кортежи. В одной области допускается до восьми разных каналов,
включая выданные внутри сообщений. В одном `alt` допускается до восьми
вариантов после разворачивания массивов. `alt`, состоящий целиком из
прокси-каналов, требует общего маршрута UniBus. Модуль может
держать до 128 активных групп возвращённых каналов. Тип элемента нового
канала провайдера должен быть свободен от вложенных каналов. Повторная
передача такого прокси в другой удалённый вызов выходит за рамки протокола.

## Записи протокола

| Тег | Запись |
| --- | --- |
| 24 | Ключ аргумента или результата как положительное 32-битное число в сетевом порядке. Тег 9 представляет `nil`. |
| 25 | Отправка с четырёхбайтовым ключом и кадром типизированного значения. Для `int` сохраняется прежняя скалярная запись. |
| 26 | Приём с четырёхбайтовым ключом. |
| 27 | Ответ для операции только с `int` в форме [скалярной записи UniBus](../../native/terminal/scalar_record.h). Ответ `alt` содержит номер ветки с единицы в старших 32 битах и биты значения в младших. Ноль означает ветку по умолчанию. |
| 28, 29 | Блокирующий выбор и выбор с веткой по умолчанию. Содержат упорядоченные записи отправки и приёма. |
| 30 | Типизированный ответ. Первый байт содержит номер ветки с единицы, ноль для выбора ветки по умолчанию или 255 при ошибке. Для выбранного приёма далее идёт один кадр значения. |
| 31 | Канал провайдера в результате функции. Содержит 16-байтовый токен группы и положительный 32-битный ключ канала в сетевом порядке. |
| 32 | Удалённые ветки смешанного выбора с ограниченным временем ожидания. Формат запроса как у тега 28, ответа как у тега 27 или 30. Если к сроку пара не нашлась, возвращается номер ветки 0. |
