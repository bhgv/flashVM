# Встраиваемый Dis: необходимые службы хоста

[English](HOST-REQUIREMENTS.md) · [Граница готовности](README.ru.md) ·
[Код IDE](../ide/dis/idecore.b)

Цель — Dis рядом с FlashVM, графика и ввод FlashVM, проверяемые интерфейсы
модулей и каналов. Отдельный Inferno `emu` нужен только для необязательного
сравнения с эталонным исполнением. Сейчас `libdisvm_core.a` ещё не является
исполняемым хостом. Ниже перечислено оставшееся, а не заявлена готовность запуска.

## Какие модули нужны текущей IDE

`ide/dis/idecore.b` включает только `idecore.m` и не загружает внешних модулей.
Сервису документов нужны настоящие планировщик Dis, `spawn`, каналы со встречей
отправителя и получателя, строки, массивы, списки, GC, исключения и загрузка модулей.

Консольные примеры и тестовые клиенты загружают `$Sys` и `idecore.dis`, используют
`Sys.print`/`sprint`. Настройка эталонной VM вызывает `Sys.open`/`write` для
`/dev/sysctl`: это управление режимом interpreter/JIT, не API виджетов IDE.
Встроенному хосту нужны собственное явное управление режимом и соответствующие
тесты. Нельзя подменить неподдерживаемый sysctl фиктивным успешным результатом.

Draw, Tk, Prefab, Keyring, оконный менеджер Inferno этим клиентам не нужны.
Графику, элементы управления и события ввода предоставляет FlashVM.

## Что ещё требуется реализовать

| Граница | Опорный код | Необходимая реализация |
| --- | --- | --- |
| Планировщик | `upstream/emu/port/dis.c`, `include/kernel.h` | очереди процессов, блокировка, отмена, блокировки хоста, пробуждение и раскрутка ошибок |
| Загрузка и встроенные модули | `libinterp/load.c`, `loader.c`, `link.c`, `runt.c` | совместимые кадры и сигнатуры, пространство имён, регистрация и вызов точки входа |
| Память и FPU | `libinterp/heap.c`, `gc.c`, `stack.c` | выделение памяти, корни GC, безопасные точки, сохранение/восстановление FPU |
| `$Sys`, файлы | `upstream/emu/port/inferno.c`, `kernel.h` | владение дескрипторами, ошибки, ограниченный ввод/вывод, форматирование и явные ошибки неподдерживаемых операций |
| SWF ↔ Dis | заголовки `.m`, генерируемые AS-заготовки | проверка сигнатур, передача значений/возможностей, корни ожидающих вызовов, отмена и кадры отладчика |
| Файловый транспорт | служба Styx/9P | точное согласование версии, tags/fids, ошибки, flush и очистка при разрыве |

Каналы Dis — типизированные очереди встречи процессов. Styx/9P — файловый
сетевой протокол, а не представление канала в байтах. Канальные сервисы можно
вывести через Styx, но сохранение исходного кода каналов само по себе не доказывает
совместимость с Plan 9/Styx. Нужны проверки обмена, отмены и ошибок для выбранной
версии протокола.

Нативные `mk`, `iyacc` и временный Limbo bootstrap используют POSIX C и не требуют
этих модулей времени исполнения. Их можно собирать до завершения встроенного хоста.
Приоритет остаётся у собственного Coco/R-компилятора Limbo → FIR.
