# GC Inferno, отдельные Fast/Cycles и точные корни

[English](GC.md) · [Общий хост](README.ru.md) ·
[API исполнителей](../include/disvm/gc_workers.h) · [Код](gc_workers.c) ·
[Безопасные точки](../include/disvm/native_world.h)

Основой остаются настоящие [`destroy`](../upstream/libinterp/heap.c) и
[`rungc`](../upstream/libinterp/gc.c) Inferno: освобождение по счётчику ссылок и
инкрементальный цветовой обход для объектов, которые RC не освобождает.
Кучу, аллокатор и представление объектов Lua в этой серии не переносим.
Цель — мало удерживаемой памяти и ограниченные порции фоновой работы, без
неподтверждённого сравнения производительности с Lua и без обещания compaction.

## Узнаваемые группы в up

[Расширенный up](native_registers.c) сохраняет имена структурных полей:

```c
/* Совместимый префикс Proc и отдельная именованная группа регистров R. */
typedef struct DVM_ExtendedUp {
    Proc Proc; /* Ошибки, текущий процесс, окружение ОС/FPU. */
    REG R;     /* Активные регистры этого нативного потока. */
} DVM_ExtendedUp;
```

Сохранённый `Prog.R` остаётся отдельным снимком. Префикс совместим; поля REG не
расплющены, не расширены и не смешаны с адресами другого размера. Настройки и
состояние GC также сгруппированы под именами `Fast` и `Cycles`: отдельные бюджеты,
callback и счётчики проходов.

## Два настоящих нативных потока

[`dvm_gc_workers_create`](../include/disvm/gc_workers.h) запускает два потока ОС
через порты FlashVM, каждый со своим контекстом сборщика. `Fast` обрабатывает
отложенные RC-освобождения, `Cycles` — порции трассировки. Запросы объединяются
во флаги, а не образуют очередь неукоренённых указателей. Без работы потоки спят
на condition variable FlashVM: постоянного сканирования кучи в простое нет.
Код использует порты Linux/Windows/macOS/Android; запуск проверен на Linux AMD64.

Перед порцией исполнитель получает исключительное право на GC-фазу, останавливает
зарегистрированные потоки в безопасных точках, публикует корни, вызывает backend
и возобновляет исполнение. Fast и Cycles не меняют одну кучу одновременно.
Инструкции вне этих фаз работают параллельно, без общей блокировки исполнения.
Если работа есть у обоих исполнителей, очередь чередуется, не позволяя одному
постоянно вытеснять другого. Это кооперативная stop-the-world координация порций,
не полностью конкурентный GC с атомарными write barrier.

Backend возвращает DONE, MORE или FAILED. MORE планирует следующую порцию;
`pause_us` задаёт необязательную паузу вне блокировок кучи/world, максимум секунду.
Начальная настраиваемая политика: Fast budget 1 без паузы, Cycles budget 1 с
1000 микросекунд между MORE-порциями. Это единицы работы, не жёсткая гарантия
времени: один `destroy` может рекурсивно освободить большой граф, а `rungc`
использует собственную адаптивную квоту. Планирование не меняет их алгоритмы.

Ошибка фиксируется, новые запросы отвергаются. Callback обязан возвращаться
обычным образом: исключения/longjmp не должны перескакивать cleanup потоков/world.
Остановка отменяет ожидающие запросы, завершает текущую порцию и join обоих
потоков. Необработанные ссылки остаются собственностью backend. Нельзя вызывать
wait_idle/destroy из callback сборщика; активный mutator должен выполнить leave,
прежде чем ждать GC, которому для завершения нужны его собственные корни.

## Сильные ссылки и циклы

Управляемые ссылки задаются картами типов/кадров, а не похожими на адрес битами.
Корни включают данные модулей, native/interpreter roots, типизированные кадры с
локальными/параметрами, сохранённые/активные регистры, ожидающие вызовы и явные
удержания хоста. Очередь RC обязана удерживать/укоренять объекты до обработки.
Сохранённые `ptradd`/`ptrdel` дают один механизм такого реестра; его изменение
также требует синхронизации с потоками и сборщиком.

Выравнивание и попадание в живой блок полезны для диагностики, но не доказывают
наличие сильной ссылки. Выровненное целое число, равное адресу объекта, не должно
удерживать мёртвый цикл. С другой стороны, настоящую mapped-ссылку могут копировать
из невыровненной записи: существующие pointer-map helpers читают через memmove.
Массивы/срезы и внешние handles следуют явным правилам метаданных/владения;
произвольный внутренний адрес нельзя угадывать как корень.

Обходим известные корни и описанные сильные поля. Недостижимые объекты можно
освобождать, даже если внутренние счётчики ссылок в цикле ненулевые. Один обход
от корней предпочтительнее отдельного обратного поиска для каждого подозрительного
указателя. Существующий цветовой/mark-протокол Inferno реализует эту основу;
эвристический сканер вместо него здесь не создаётся.

Малый объём живой памяти и физическая компактизация — разные задачи. Фрагментация,
возврат арен и перемещение относятся к аллокатору. Перемещение дополнительно
требует исправления всех корней/рёбер, внутренних ссылок, native bindings и адресов
JIT. Автоматическая релокация/компактизация этой серией не реализована.

## Проверки и оставшаяся интеграция

[`inferno_gc.py`](../tests/inferno_gc.py) исполняет настоящие тела RC/GC на
детерминированном **тестовом пуле**, не на производственном аллокаторе арен:

- каскадное RC-освобождение ациклической цепочки выполняется потоком Fast;
- недостижимые циклы собирает настоящий rungc в отдельном потоке Cycles;
- циклы, достижимые из глобальных данных или mapped-параметра стека, сохраняются;
- после удаления сильных рёбер становятся собираемыми;
- scalar, равный адресу объекта, не удерживает цикл без бита в карте;
- ожидающая RC-ссылка укоренена в настоящем pointer-root registry.

Контрольная фикстура проверяет ошибки старта/callback, чередование MORE и запрет
self-join. Совместная фикстура исполняет настоящую addw в двух потоках, пока
Fast/Cycles делают 100 stop/scan/resume. Она доказывает координацию; аллокаторная
фикстура — поведение настоящих алгоритмов. Эти границы проверки не смешиваются.

Сам исполнитель работает, но полному Dis-хосту ещё нужны производственный
аллокатор, адаптер корней, синхронизация RC/кучи в mutator-путях, hooks блокирующих
операций, владение таблицами модулей и безопасные финализаторы. Старые
`gclock`/`gcunlock` — счётчики gchalt, не межпоточные мьютексы. Они не доказывают
безопасность общей кучи. Финализаторы ресурсов/UI должны соблюдать поток владельца
и канальные правила, а не обращаться к FlashVM/отрисовке из сборщика. Перенаправление
всех `destroy` интерпретатора в настоящую отложенную очередь и полный запуск IDE
ещё не реализованы.
