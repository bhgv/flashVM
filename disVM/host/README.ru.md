# Общий хост FlashVM/Dis и эксперимент с нативными потоками

[English](README.md) · [Вход модулей](../include/disvm/module_image.h) ·
[Общие порты](../include/disvm/flashvm_host.h) · [Контекст потока](../include/disvm/native_context.h)

Загрузчик уже перенесён: `upstream/libinterp/load.c` содержит `parsemod`,
`readmod.c` — файловую обёртку Inferno. Новый [module_parse.c](module_parse.c)
передаёт байты тому же настоящему разборщику. Второго Dis-парсера здесь нет.
Ввод-вывод и нативные потоки берутся из FlashVM, без GUI и второго ОС-слоя Inferno.

## Сборка

```sh
./build-workspace.sh --projects disvm-host --tests
```

Независимая сборка с CMake 3.10+, включая toolchain Windows/macOS/Android:

```sh
mkdir -p build/disvm-host
cd build/disvm-host
cmake ../../disVM/host -DDVM_FLASHVM_SOURCE_ROOT=/absolute/path/to/flashVM/flashVM
cmake --build .
ctest --output-on-failure
```

Для Android передайте NDK toolchain в CMake: выбирается `ANDROID`, а не Linux.
Windows выбирает `windows`, macOS — `mac`, Android — `android`, Linux — `linux`.
Используются настоящие `ports/PORT/thread.c` и `channel_sync.c` FlashVM.
`ports/file_port.c` даёт бинарные файлы и переносимые пути, `ports/network/socket.c`
— POSIX/Winsock с общим дедлайном. [native_context.c](native_context.c) использует
Windows TLS либо POSIX pthread TLS.

При включении в общий CMake-проект задайте `DVM_FLASHVM_TARGET` именем уже
созданной цели FlashVM: повторно компилировать порты не потребуется. Независимая
сборка компилирует только нужные файлы портов. Канальный адаптер ссылается на
настоящие функции FlashVM; исполняемому потребителю нужна библиотека FlashVM и её
выбранные зависимости. Явный список `DVM_FLASHVM_LIBRARIES` также включает тест с
настоящим каналом. Подмены канала и скрытого поиска SDK нет.

Выбор исходников хоста предусмотрен для четырёх платформ. Проверенное исполнение
этой серии — Linux AMD64. Windows/macOS/Android ещё требуют сборок и запусков на
целевых системах. Старый ABI/заголовки самого ядра Dis — отдельная незаконченная
граница переноса: сборка этого хоста не доказывает готовность полной Windows VM.

## Единый вход байтов модуля

Функции создают собственный `DVM_ModuleImage`, независимый от куч обеих VM:

| Источник | Функция | Реализовано |
| --- | --- | --- |
| Результат компилятора IDE / память | `dvm_image_copy` | точная копия; исходный буфер можно освободить |
| Ресурс внутри исполняемого файла | `dvm_image_copy` | адрес и размер ресурса без обращения к диску |
| Диск | `dvm_image_file` | файловый порт FlashVM, собственный дескриптор закрывается |
| Сеть | `dvm_image_socket` | заимствованный сокет FlashVM с его дедлайном/отменой |
| Канал | `dvm_image_send_channel`, `dvm_image_channel` | настоящий канал FlashVM, бинарная оболочка `dis-hex:` |
| Любой источник хоста | `dvm_image_read` | callback, короткие чтения и точный размер кадра |

Максимум — 8 МиБ минус один байт, как у исходного `readmod`; квота может быть
меньше. Пустой модуль отвергается. Выход изначально `{0,0,0}`; ошибка освобождает
частичные выделения и оставляет выход пустым. `dvm_image_dispose` освобождает
буфер/имя, повторный вызов безопасен. Файлы и сокеты требуют точного размера кадра
из метаданных: последующие байты не потребляются. Адаптеры не реализуют разбор URL,
HTTP/TLS/Styx, реестр источников и поиск ресурсов исполняемого файла. Передача
встроенных байтов уже работает; полноценное пространство имён ROM ещё предстоит.

Строки FlashVM проверяются как WTF-8. Чтобы сохранить произвольный Dis, каждый
байт кодируется двумя ASCII hex-символами после `dis-hex:`. Приём проверяет
оболочку, цифры и квоту декодированных байтов, освобождает сообщение канала.
Неблокирующие операции возвращают `DVM_IMAGE_PENDING`, если очередь заполнена
или пуста. Некорректное/слишком большое принятое сообщение потребляется. Квоту
памяти закодированных сообщений нужно ограничивать отдельно на стороне отправителя.

`dvm_image_parse` требует уже инициализированного хоста Dis: типов, GC, кадров
ошибок и блокировки владельца. Результат — настоящий Module, освобождаемый через
Dis `unload`. Его нельзя передавать между кучами как значение FlashVM. Входной
образ после разбора можно освободить. Функция ещё не создаёт VM, не разрешает
импорты и не вызывает экспорт модуля.

## Нативные потоки: эксперимент

Выбранное направление — полноценные потоки ОС с отдельными регистрами, текущим
процессом и указателем рантайма; не последовательный запуск всех процессов Limbo
в одном нативном потоке. [Контекст](../include/disvm/native_context.h) выделяет
отдельную память регистров, эксклюзивно связывается с потоком через TLS и отвергает
вложенное/конкурентное связывание. Перед выходом потока обязателен unbind. Хост
должен удерживать и укоренять процесс/рантайм всё время использования; контекст
их не собирает и не освобождает. Destroy — только после остановки пользователей,
unbind и join. Принудительного убийства нативных потоков нет.

```sh
DVM_NATIVE_REGISTERS=ON ./build-workspace.sh --projects disvm --tests
```

Этот явный эксперимент генерирует только в каталоге сборки представление исходников:
обращения к глобальному `R` становятся `DVM_R`, сохранённые поля `p->R`, комментарии
и строки не меняются. Overlay получает `DVM_R` из текущего TLS-контекста. Исходные
файлы и их контрольные суммы сохранены. Доступ без контекста с памятью ровно
`sizeof(REG)` завершает процесс, вместо скрытого использования общих регистров.
Для генерации представления нужен Python.

**Изолированы регистры, но параллельный рантайм Dis ещё не завершён.** Нужны
синхронизация глобальных таблиц модулей и GC/куч, группы процессов, состояние
ошибок/FPU, регистрация нативных модулей, ожидающие вызовы, каналы и публикация JIT.
Опорные тела планировщика/ОС Inferno сохранены. Автоматический параллельный `spawn`,
готовый Dis runner, безопасная общая куча и исполнение IDE пока не реализованы.
Один TLS не делает эти пути безопасными для параллельного запуска.

## Проверки

Используются настоящие файловый, сетевой, потоковый порты и синхронизация FlashVM,
настоящий канал, копирование памяти и встроенных байтов. Два потока выполняют
4000 настоящих тел инструкции `addw`, каждый со своим REG, с барьером на каждом
шаге, без общей блокировки исполнения VM. Адаптер разбора проверяется настоящим
`parsemod` в существующей upstream-фикстуре: её явные подмены GC/JIT/аллокатора
не выдаются за полноценную VM. Исполнение на Windows/macOS/Android и полная
приёмка Dis/JIT остаются открытыми.

UBSan проходит для TLS-фикстуры инструкций и изменённых путей канальной очереди. Попытки Address/LeakSanitizer не смогли завершиться из-за ограниченного доступа к потокам через `/proc`; они не засчитываются как успешная sanitizer-приёмка.

## Расширенный up и безопасные точки GC (v0.1535)

Типизированный [dvm_native_process_create](../include/disvm/native_process.h)
теперь выделяет расширенный `up`: исходный `Proc` идёт первым полем, активный `REG`
встроен после него. `getup()` возвращает совместимый префикс Proc через того же
TLS-владельца. Регистровый адаптер получает активный REG из этого up; второго TLS
для R нет. Текущий процесс берётся непосредственно из `up->iprog`. Кадры ошибок
и поля окружения ОС/FPU исходного Proc находятся в том же объекте потока.
`Prog.R` остаётся сохранённым состоянием приостановленного процесса.

Для потока интерпретатора используйте `dvm_native_process_create`, затем
`dvm_native_context_bind`. Общий конструктор контекста остаётся для host-only
состояния, но не создаёт Proc и не подходит типизированному регистровому адаптеру.
Этот выбранный хост реализует getup в native_registers.c; одновременно подключать
другую реализацию getup из ОС Inferno нельзя. Полная настройка окружения Proc/FPU,
групп дочерних процессов и их очистка ещё требуют интеграции хоста. Размер указателей
и ABI байткода/кадров Dis в этой серии не меняются.

[Координатор native world](../include/disvm/native_world.h) работает так:

1. Связанный с потоком владелец регистрирует корни контекста. Установленный hook
   не позволяет выполнить unbind до явного detach.
2. Enter отмечает активного исполнителя; сами инструкции идут без мьютекса world.
3. Poll между завершёнными инструкциями останавливает поток при запросе сборки.
   В генерируемом xec экспериментального режима эта проверка стоит перед decode,
   C-translated step и leaf-JIT dispatch обычного цикла инструкций.
4. Перед блокирующим I/O/каналом или переходом в неактивное состояние владелец
   вызывает leave, публикуя стабильные корни. Повторный enter ждёт завершения
   сборки. Память корней должна оставаться живой и неизменной. Эти вызовы ещё
   нужно подключить к настоящим блокирующим операциям рантайма.
5. Отдельный связанный контекст сборщика вызывает stop_begin, обходит корни всех
   участников и вызывает stop_end. Вложенный/конкурирующий сборщик отвергается.
   Предыдущее поколение остановленных потоков полностью возобновляется перед
   следующим stop. Принудительной остановки потока ОС нет.

Callback обхода держит мьютекс world: нельзя повторно входить в world API,
блокироваться, бросать исключения/longjmp, уничтожать контексты или память корней.
Настоящему сборщику нужны подготовка потенциально ошибочных операций вне callback
и гарантированная пара stop/resume при ошибках. Инструкция или native callback
без безопасной точки может задержать сборку неограниченно; таймаут и принудительное
убийство потока не заявлены. Старые целиком скомпилированные модули пока не имеют
внутренних poll-точек.

Реализованы координация и публикация корней, а не настоящий mark/sweep GC.
Общие кучи, таблицы модулей, нативные модули, исключения, spawn/планирование и
публикация JIT ещё требуют интеграции с владением и синхронизацией. Один этот тест
не разрешает произвольное параллельное исполнение с общей кучей.

Новая проверка исполняет настоящую addw в двух потоках с расширенным up и делает
100 stop/scan/resume. Каждый обход проверяет оба настоящих REG и операнды.
Прежний тест 4000 инструкций теперь проверяет также независимость up.nerr/iprog.
Генератор отвергает изменившуюся границу dispatch, вместо скрытой вставки poll
в неподходящее место.
