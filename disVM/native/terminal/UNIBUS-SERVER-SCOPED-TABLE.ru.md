# styxunibusserverstartscopedtable

[English](UNIBUS-SERVER-SCOPED-TABLE.md) · [Заголовок](unibus_server.h) · [Реализация](unibus_loaded.c)

```c
StyxUnibusServer *styxunibusserverstartscopedtable(RemotePhy *channel,
    const StyxMountedScalar *entries, size_t count, DVM_Provider *reverse);
```

Подключите `unibus_server.h` и библиотеку `styx_unibus_server`. Сервер
публикует несколько загруженных Dis-модулей в одной прямой сессии Styx.
Каждый каталог под `mounted` получает свой `.interface` из экспортов модуля.

| Параметр | Контракт |
| --- | --- |
| `channel` | Прямой транспорт Styx. Функция принимает владение при любом исходе. |
| `entries` | Заимствованная таблица. В `module` укажите имя каталога, в `name` — имя экспорта. Профиль вызова определяется загруженной реализацией Dis. |
| `count` | От 1 до 64 записей, до 8 на модуль. |
| `reverse` | Обязательный провайдер с корнем выше клиентского `.prog`. Удерживается до join. |

Функция возвращает сервер во владение вызывающего или NULL при неверном
входе, нехватке памяти или отказе запуска диспетчера. Диспетчер запускается
сразу. Первое обращение к профилю ждёт подтверждения загрузки. Приёмники
запросов, ответов и профилей индексируются в порядке `entries`.

Передайте диспетчеру владельца таб-разделённую строку, начинающуюся с
`loaded-table`. На запись приходятся пять полей: путь к исходной реализации
Dis, имя экспорта, пути приёмников запроса, ответа и профиля. Экспорты с
одним путём реализации используют общий экземпляр данных. У отдельно
загруженных реализаций свои данные модуля. Контекстные вызовы клиента
используют один `Prog` провайдера на всю таблицу. После отмены вызова этот
`Prog` завершается. Следующий вызов того же PID получает новый `Prog`.
Чтобы освободить сессию, закройте транспорт и дождитесь сервера через join.

[Пример из двух модулей](tests/scalar/pair.c) публикует таблицу.
[Клиент Limbo](../../examples/remote-scalar/styx-scoped-calls.b) проверяет
переиспользование исполнителя между модулями и его замену после отмены.

## Публикация точки запуска в той же сессии

`styxunibusserverstartscopedlaunchtable` добавляет `implementation.dis`,
корневой `.interface`, `.unibus` и `.exit` в ту же сессию.
Передайте `StyxUnibusLaunch` с ненулевым тегом S-записи запуска,
провайдером исходного образа и провайдером объявления запуска.
Сервер удерживает оба провайдера до join. Интерфейсы отдельных модулей
доступны под `mounted`.

Поле `persistent` в `StyxUnibusLaunch` включает ограниченную очередь
запросов с контекстом. Хост получает запись через
`styxunibusservernextlaunch` и отправляет итог через
`styxunibuslaunchcomplete`. Билет относится к одному запросу, даже если
следующий завершится раньше. Закрытие fid снимает запрос из очереди или
запрашивает остановку уже исполняемого потомка. Если fid закрыт между
извлечением запроса и первой инструкцией, отмена доставляется при
регистрации потомка. Старый fid только на запись получает один результат
через `.exit`.

При выключенном `persistent` используются одноразовый приёмник и
`styxunibusserverlaunchstatus`. [Тест протокола](tests/scalar/route_launch.inc)
проверяет разные fid, обратный порядок завершения и старый формат результата.
