# styxunibusserverstartfunction

[English](SCALAR-FUNCTION.md) · [Заголовок](unibus_server.h) · [Пример на C](tests/scalar/route.c) · [Пример на Limbo](../../examples/remote-scalar/styx-mounted.b)

```c
StyxUnibusServer *styxunibusserverstartfunction(
    RemotePhy *channel, const char *module, const char *name,
    const struct StyxScalarFunction *function);
```

Подключите библиотеку `styx_unibus_server` и заголовки `unibus_server.h`
и `scalar_function.h`. Функция принимает канал Styx во владение при любом
исходе и возвращает сервер или NULL. После закрытия другой стороны передайте
сервер в `styxunibusserverjoin`.

Имя модуля и имя экспорта задаются по одному элементу пути. Сервер публикует
`mounted/<модуль>/<функция>` с правами 0777 и разрешает вызов через ORDWR.
Сервер копирует описание функции. Состояние обработчика должно жить до
завершения сервера. Оба тега — ненулевые 32-битные беззнаковые значения.
Обработчик выполняется в потоке диспетчера Styx. Для этой точки входа
подходят синхронные нативные методы с коротким временем выполнения. У каждого
открытия отдельный ответ. Один сервер выполняет обработчики последовательно.

Запишите одну полную [скалярную S-запись](SCALAR-WRITE.ru.md) со смещения
ноль. Читайте ответ со смещения ноль, сдвигаясь на подтверждённое число
байтов. Результат или ошибка метода возвращается одной записью. Styx
возвращает ошибку при неверном запросе, чтении до запроса или второй
попытке вызова на том же fid. Закрытие fid освобождает ответ. Здесь
используется существующий скалярный формат.

При теге запроса `STYX_FUNCTION_REQUEST_TAG` (72) и теге ответа
`STYX_FUNCTION_REPLY_TAG` (73) сервер также публикует доступный только для
чтения профиль `.interface`. Он описывает один именованный экспорт
с компилированной сигнатурой `fn(int): int`. DisVM сверяет этот профиль,
когда типизированный `load` выбирает каталог в VFS с поддержкой отмены.
Загрузчик закрепляет файл экспорта через выбранный каталог. Для каждого
вызова он открывает новый fid на чтение и запись. Путь к каталогу,
полученный через `bind`, работает так же. Другие пары тегов по-прежнему
доступны клиентам на C, которые задают теги явно.

Соберите и запустите `terminal-scalar-route` из нативного SDK. Пример дважды
открывает `mounted/compute.dis/compute`, отправляет два вызова и читает
ответы в обратном порядке. Он также проверяет, что усечённая запись и
повторная отправка не вызывают обработчик.

В SDK с настроенными DisVM и компилятором Limbo запустите
`ctest -R '^terminal-scalar-guest$' -V`. Пример проверяет отказ при
несовместимом импорте, результат и исключение по прямому пути и через
`bind`. Пример перекрывает исходный монт пустым каталогом и проверяет, что
оба загруженных экземпляра сохраняют доступ к закреплённому экспорту.
Ожидаемая строка `PASS typed Styx mounted function` появляется
для обоих режимов VM. Существующий типизированный
маршрут описан в [примере с двумя DisVM](../../examples/remote-scalar/STYX.ru.md).

Для исходной реализации Dis см. [styxunibusserverstartdis](SCALAR-FUNCTION-DIS.ru.md).

## PID клиента при типизированном вызове

Экспорт на C может задать `caller_method` с тегом запроса 74 и тегом ответа
73. Запись такого экспорта в `.interface` имеет тег 75. Запрос состоит из
одной S-записи с двумя 32-битными словами старшим байтом вперёд. Первое
слово содержит ненулевой PID клиента, второе — знаковый аргумент. Формат
ответа обычный скалярный. Экспорты с тегом запроса 72 сохраняют свой формат.

DisVM берёт PID активного процесса при каждом вызове. PID относится к
сеансу клиента.

Для вызова на C с контекстом укажите `program_method` вместо
`caller_method` и передайте в `program_root` выданный каталог модуля на
встречном Styx-маунте. Удерживайте этот корень до завершения сервера.
Перед вызовом диспетчер захватывает `.prog/<pid>` и передаёт обработчику
этот каталог как его собственный корень `.self`. Из него доступны
опубликованные `.pid`, `.fd`, `.vfs` и `.var` с выданными правами.
Ссылка заимствуется на время обработчика. Ошибка поиска и узел другого
типа возвращают отказ Styx до вызова обработчика. Каждый вызов захватывает
свой каталог. Автоматическая публикация живого дерева клиента при
`load` пока открыта.

Пример встречного Styx в `terminal-scalar-route` выбирает по PID два
каталога и отклоняет третий, отсутствующий PID. Ожидается
`PASS mounted scalar .self over reverse Styx`.

Пример `styx-caller.b` запускается в тесте `terminal-scalar-guest`.
Родитель и потомок после `spawn` используют один экземпляр модуля.
Обработчик на C сверяет PID, переданный автоматически, с PID, который
каждый процесс прочитал у себя. В обоих режимах VM ожидается
`PASS typed Styx caller PID`.

## Сборка встречного дерева клиента

Нативный код, встраивающий DisVM, может собрать корень модуля через
`dvm_program_view`. Для каждого процесса передаётся одна запись
`DVM_ProgramView`. Она создаёт файл `.pid` только на чтение с десятичным
номером и переводом строки, а также подключает выданные каталоги
`.fd`, `.vfs` и `.var`. Доступ к их содержимому сохраняет исходные права
провайдеров. Повтор PID или неверный каталог отменяет всю сборку.
Встраивающий код владеет результатом и может опубликовать его как корень
встречной сессии. Захваченный каталог PID переживает освобождение корня.

Команда `ctest -R '^terminal-scalar-guest$' -V` проверяет сборку, время
жизни захваченного каталога и видимость выданных путей. Ожидается
`PASS captured caller program tree`. Записи процессов и выданные им
каталоги пока передаёт встраивающий код.

Для постоянной встречной публикации `dvm_program_publication` возвращает
пустой корень модуля и управление обновлениями. Корень можно удерживать
смонтированным и передавать текущий список в
`dvm_program_publication_replace`. После успешной замены новый поиск
от корня видит актуальные каталоги. Нулевое число записей очищает дерево.
При ошибке сохраняется прежний список. Уже захваченные каталоги
сохраняют своё содержимое. Обновления пока подаёт встраивающий код.

## Публикация текущего клиента на время вызова

Встраивающий код может установить доверенную связь
`DVM_CallerBinding` через `dvm_provider_bind_caller` на свежем нативном
провайдере до публикации маунта. Захваченные узлы функций наследуют эту
связь. При обычном типизированном вызове DisVM собирает дерево текущего
процесса и вызывает `begin` до отправки запроса. Дерево содержит
`.prog/<pid>/.pid`. Точный узел функции и дерево заимствуются на время
вызова callback. Публикация действует до завершения обмена, после чего
`end` её снимает. Отказ `begin` отменяет отправку. Маунты без такой
связи продолжают использовать существующую запись с PID.

Гостевой стенд использует две сессии Styx на одном мультиплексированном
соединении. По прямой сессии идёт запрос функции. Провайдер через
встречную сессию проходит к `.prog/<pid>/.pid` и читает виртуальный файл,
созданный DisVM. Родитель и потомок после `spawn` вызывают один
загруженный экземпляр. С JIT и без него ожидается
`PASS typed Styx caller PID`.

Встречный путь к PID обслуживает стенд. Подключение штатного маунта и
сбор полномочий для дескрипторов, пространства имён и переменных
ещё предстоят.
