# styxunibusserverstartfunction

[English](SCALAR-FUNCTION.md) · [Заголовок](unibus_server.h) · [Пример на C](tests/scalar/route.c) · [Пример на Limbo](../../examples/remote-scalar/styx-mounted.b)

```c
StyxUnibusServer *styxunibusserverstartfunction(
    RemotePhy *channel, const char *module, const char *name,
    const struct StyxScalarFunction *function);
```

Подключите библиотеку `styx_unibus_server` и заголовки `unibus_server.h`
и `scalar_function.h`. Функция принимает канал Styx во владение при любом
исходе и возвращает сервер или NULL. После закрытия другой стороны передайте
сервер в `styxunibusserverjoin`.

Имя модуля и имя экспорта задаются по одному элементу пути. Сервер публикует
`mounted/<модуль>/<функция>` с правами 0777 и разрешает вызов через ORDWR.
Сервер копирует описание функции. Состояние обработчика должно жить до
завершения сервера. Оба тега — ненулевые 32-битные беззнаковые значения.
Обработчик выполняется в потоке диспетчера Styx. Для этой точки входа
подходят синхронные нативные методы с коротким временем выполнения. У каждого
открытия отдельный ответ. Один сервер выполняет обработчики последовательно.

Запишите одну полную [скалярную S-запись](SCALAR-WRITE.ru.md) со смещения
ноль. Читайте ответ со смещения ноль, сдвигаясь на подтверждённое число
байтов. Результат или ошибка метода возвращается одной записью. Styx
возвращает ошибку при неверном запросе, чтении до запроса или второй
попытке вызова на том же fid. Закрытие fid освобождает ответ. Здесь
используется существующий скалярный формат.

При теге запроса `STYX_FUNCTION_REQUEST_TAG` (72) и теге ответа
`STYX_FUNCTION_REPLY_TAG` (73) сервер также публикует доступный только для
чтения профиль `.interface`. Он описывает один именованный экспорт
с компилированной сигнатурой `fn(int): int`. DisVM сверяет этот профиль,
когда типизированный `load` выбирает каталог в VFS с поддержкой отмены.
Загрузчик закрепляет файл экспорта через выбранный каталог. Для каждого
вызова он открывает новый fid на чтение и запись. Путь к каталогу,
полученный через `bind`, работает так же. Другие пары тегов по-прежнему
доступны клиентам на C, которые задают теги явно.

Соберите и запустите `terminal-scalar-route` из нативного SDK. Пример дважды
открывает `mounted/compute.dis/compute`, отправляет два вызова и читает
ответы в обратном порядке. Он также проверяет, что усечённая запись и
повторная отправка не вызывают обработчик.

В SDK с настроенными DisVM и компилятором Limbo запустите
`ctest -R '^terminal-scalar-guest$' -V`. Пример проверяет отказ при
несовместимом импорте, результат и исключение по прямому пути и через
`bind`. Пример перекрывает исходный монт пустым каталогом и проверяет, что
оба загруженных экземпляра сохраняют доступ к закреплённому экспорту.
Ожидаемая строка `PASS typed Styx mounted function` появляется
для обоих режимов VM. Существующий типизированный
маршрут описан в [примере с двумя DisVM](../../examples/remote-scalar/STYX.ru.md).

Для исходной реализации Dis см. [styxunibusserverstartdis](SCALAR-FUNCTION-DIS.ru.md).

## PID клиента при типизированном вызове

Экспорт на C может задать `caller_method` с тегом запроса 74 и тегом ответа
73. Запись такого экспорта в `.interface` имеет тег 75. Запрос состоит из
одной S-записи с двумя 32-битными словами старшим байтом вперёд. Первое
слово содержит ненулевой PID клиента, второе — знаковый аргумент. Формат
ответа обычный скалярный. Экспорты с тегом запроса 72 сохраняют свой формат.

DisVM берёт PID активного процесса при каждом вызове. PID относится к
сеансу клиента.

Для вызова на C с контекстом укажите `program_method` вместо
`caller_method` и передайте в `program_root` выданный каталог модуля на
встречном Styx-маунте. Удерживайте этот корень до завершения сервера.
Перед вызовом диспетчер захватывает `.prog/<pid>` и передаёт обработчику
этот каталог как его собственный корень `.self`. Из него доступны
опубликованные `.pid`, `.fd`, `.vfs` и `.var` с выданными правами.
Ссылка заимствуется на время обработчика. Ошибка поиска и узел другого
типа возвращают отказ Styx до вызова обработчика. Каждый вызов захватывает
свой каталог. Автоматическая публикация живого дерева клиента при
`load` пока открыта.

Пример встречного Styx в `terminal-scalar-route` выбирает по PID два
каталога и отклоняет третий, отсутствующий PID. Ожидается
`PASS mounted scalar .self over reverse Styx`.

Пример `styx-caller.b` запускается в тесте `terminal-scalar-guest`.
Родитель и потомок после `spawn` используют один экземпляр модуля.
Обработчик на C сверяет PID, переданный автоматически, с PID, который
каждый процесс прочитал у себя. В обоих режимах VM ожидается
`PASS typed Styx caller PID`.

## Сборка встречного дерева клиента

Нативный код, встраивающий DisVM, может собрать корень модуля через
`dvm_program_view`. Для каждого процесса передаётся одна запись
`DVM_ProgramView`. Она создаёт файл `.pid` только на чтение с десятичным
номером и переводом строки, а также подключает выданные каталоги
`.fd`, `.vfs` и `.var`. Доступ к их содержимому сохраняет исходные права
провайдеров. Повтор PID или неверный каталог отменяет всю сборку.
Встраивающий код владеет результатом и может опубликовать его как корень
встречной сессии. Захваченный каталог PID переживает освобождение корня.

Команда `ctest -R '^terminal-scalar-guest$' -V` проверяет сборку, время
жизни захваченного каталога и видимость выданных путей. Ожидается
`PASS captured caller program tree`. Записи процессов и выданные им
каталоги пока передаёт встраивающий код.

Для постоянной встречной публикации `dvm_program_publication` возвращает
пустой корень модуля и управление обновлениями. Корень можно удерживать
смонтированным и передавать текущий список в
`dvm_program_publication_replace`. После успешной замены новый поиск
от корня видит актуальные каталоги. Нулевое число записей очищает дерево.
При ошибке сохраняется прежний список. Уже захваченные каталоги
сохраняют своё содержимое. Обновления пока подаёт встраивающий код.

## Публикация текущего клиента на время вызова

Встраивающий код может установить доверенную связь
`DVM_CallerBinding` через `dvm_provider_bind_caller` на свежем нативном
провайдере до публикации маунта. Захваченные узлы функций наследуют эту
связь. При обычном типизированном вызове DisVM собирает дерево текущего
процесса и вызывает `begin` до отправки запроса. Дерево содержит
`.prog/<pid>/.pid`. Точный узел функции и дерево заимствуются на время
вызова callback. Публикация действует до завершения обмена, после чего
`end` её снимает. Отказ `begin` отменяет отправку. Маунты без такой
связи продолжают использовать существующую запись с PID.

Гостевой стенд использует две сессии Styx на одном мультиплексированном
соединении. По прямой сессии идёт запрос функции. Провайдер через
встречную сессию проходит к `.prog/<pid>/.pid` и читает виртуальный файл,
созданный DisVM. Родитель и потомок после `spawn` вызывают один
загруженный экземпляр. С JIT и без него ожидается
`PASS typed Styx caller PID`.

Перед публикацией DisVM захватывает явно смонтированные каталоги
`/.fd`, `/.vfs` и `/.var` из пространства имён вызывающего процесса.
Отсутствующие маунты пропускаются. Union или маунт без захвата с
поддержкой отмены блокирует отправку вызова. Стенд проверяет через встречный Styx файлы `.vfs/env/CLIENT` и
`.var/counter` для обоих процессов.

В SDK есть общий встречный сервер. Запустите `styxcallerserver` на
встречном канале, затем передайте управление и подключённый прямой
клиент в `styxcallermount`. Маунт получит готовую встречную связь. На стороне провайдера смонтируйте встречный канал и
передайте корень обработчику `program_method`. При закрытии транспорта
вызовите `styxcallerjoin`. Маунт и захваченные узлы могут пережить
управление. Они удерживают остановленное состояние и отклоняют новые
вызовы. Стенд использует эти
же функции и читает файлы из выбранного провайдером `.self`.

Встречная сессия допускает до 16 одновременных публикаций с разными
PID и одну активную публикацию на PID. Чтение `.prog` отдаёт снимок
активных PID. У каждого вызова своё поколение Qid и до 511 дополнительных
узлов обхода. После завершения вызова его fid теряют доступ к данным.
Провайдер может выполнять скалярные функции последовательно при
одновременно активных клиентах. Хост поднимает оба канала транспорта. Автоматическая
выдача обычных управляемых FD и общих переменных ещё предстоит.

Если у вызывающего процесса нет явного маунта `/.fd`, DisVM публикует
номерные дескрипторы, импортированные при запуске процесса. Псевдоним
удерживает открытый слот, сохраняет режим чтения и записи и делит позицию
с локальными псевдонимами. Стенд импортирует FD 3 при запуске.
Провайдер последовательно читает два блока через встречный Styx при
вызовах из родителя и потомка. Родитель читает третий блок локально
через `Sys->fildes(3)` и подтверждает результат ещё одним типизированным
вызовом. Действует диапазон номеров запуска 0–31.
На POSIX-хостах с дублированием close-on-exec номера 0–2 также
публикуются, если они открыты как обычные файлы, не скрыты и не заменены
импортированным слотом. Дубликат сохраняет позицию и режим доступа
исходного открытого файла. Подключённые потоковые сокеты публикуются на хостах, где отдельную
операцию можно выполнить без ожидания и подавить SIGPIPE. Пустой сокет
сообщает о временной недоступности. Флаги исходного FD сохраняются.
Pipe, терминалы и обычные управляемые открытия пока вне этой публикации. Встречный маунт
всё ещё настраивает встраивающий код.

## Знаковые скаляры big

Нативный экспорт может объявить сигнатуру Limbo `fn(big): big`.
Для обычного `method` используется `STYX_FUNCTION_BIG_TAG` (76),
для обработчика с контекстом — `STYX_FUNCTION_BIG_CALLER_TAG` (77).
Тег ответа в обоих случаях 73. Запрос с контекстом содержит ненулевой
32-битный PID и знаковый 64-битный аргумент старшим байтом вперёд.
Обычный запрос использует существующий формат знакового скаляра.

Загрузчик связывает экспорты `int` и `big` в одном модуле. Перед
созданием экземпляра он сверяет скомпилированную сигнатуру каждого
импорта. Путь `int` проверяет 32-битный диапазон на обеих сторонах.
Служба вызова исходного Dis также поддерживает одиночный экспорт `big`.

[Смешанный интерфейс](../../examples/remote-scalar/mixed.m) и тест
`terminal-caller-mount-cli` проверяют оба профиля big, границы
64-битного диапазона и отказ для несовместимого импорта.

## Кортеж в аргументе и результате

Нативная смонтированная функция поддерживает сигнатуру Limbo
`fn((int,big)): (int,big)`. Задайте `tuple_method` с тегами запроса
78 и ответа 79. При заданном `program_root` используется тег запроса
80. Обработчик заимствует выбранный каталог `.self` на время вызова.

Внутри записи идут знаковые поля `int` (тег 1) и `big` (тег 2).
В запросе с контекстом перед ними идёт запись PID (тег 3).
Диспетчер сверяет типы, порядок и полную длину до вызова функции.
Результат использует тот же порядок. Для ошибки применяется
существующая скалярная запись.

[Смешанный интерфейс](../../examples/remote-scalar/mixed.m) проверяет
знаковые границы, отказ при перестановке типов и вызов после удалённого
исключения. Кортеж также поддерживается исходным Dis в режиме без контекста клиента.

## Возврат полей ADT по ссылке

Смонтированный экспорт может принять `ref Cell`, где `Cell` содержит поля
`int` и `big` в таком порядке, и вернуть `(int,big)`. Загрузчик сверяет
сигнатуру из скомпилированного модуля при связывании. Аргумент `nil`
отклоняется на клиенте.

| Тег S-записи | Содержимое |
| --- | --- |
| 81 | Два типизированных поля аргумента |
| 82 | PID клиента и те же два поля |
| 83 | Кортеж результата и обновлённые поля |
| 73 | Скалярная ошибка |

При успехе ответ содержит две полные вложенные записи кортежей. Клиент
проверяет обе, затем вместе публикует результат и обновляет исходный объект
в куче. Другие ссылки на этот объект видят новые поля. Если значение хотя бы
одного поля отличается от снимка до вызова, публикация завершается ошибкой
`remote ref changed during call`. При исключении, неверном ответе или отмене
обратная запись не выполняется. Уже выполненные действия владельца могут сохраниться.

Провайдер на C регистрирует `ref_method` и задаёт `program_root`, если
использует PID клиента. Исходный экспорт Dis работает через
[сервис владельца](../../runtime/SCALAR-OWNER-SERVICE.ru.md#один-экспорт-с-adt-по-ссылке)
без PID. См. [пример с двумя VM](../../examples/remote-scalar/STYX.ru.md#возврат-полей-из-исходного-dis).
Профиль поддерживает одну ссылку на два скалярных поля. Ссылки внутри
объекта и совместный доступ к нему во время вызова выходят за рамки профиля.

## Список аргументов и вложенный результат

Кодек записывает аргументы по порядку в одну внешнюю S-запись. Вложенный
кортеж Limbo занимает одну позицию и кодируется своей S-записью с тегом 4.
Теги 1 и 2 обозначают знаковые `int` и `big`. Порядок и типы задаёт
проверенная сигнатура функции. Кодек принимает пустой список, один
элемент или несколько. Пределы составляют 64 байта на запись, восемь
скалярных ячеек и четыре уровня вложенности.

Загрузчик смонтированных модулей поддерживает профиль
`fn(int,(int,big),big): (int,(int,big))`. В запросе с тегом 84 три
позиции, в ответе с тегом 85 одно вложенное значение. Ошибка владельца
сохраняет тег 73. Обе стороны проверяют полную структуру перед выдачей
значений. Клиент пишет запрос и читает ответ через один открытый fid
функции. Аргументы и результат не получают путей в VFS окружения модуля.
Прежние профили кортежа и `ref` используют тот же кодек для полей
и сохраняют свои теги на проводе.

См. [запускаемый пример](../../examples/remote-scalar/STYX.ru.md#вызов-с-тремя-аргументами).
Этот профиль поддерживает указанную сигнатуру и использует запрос без PID.

## Две ссылки в одном вызове

Профиль `fn(ref Cell,ref Cell): (int,big)` использует тот же `Cell` из двух
полей. Обе позиции обязательны. Ссылка `nil` отклоняется до отправки.
Запрос содержит номера объектов в порядке первого появления и по одному
снимку на каждый отдельный объект. Номера `(0,0)` означают, что провайдер
создаёт один объект и передаёт его в обе позиции. При `(0,1)` он создаёт
два объекта, даже если все их поля совпадают.

| Внешний тег S-записи | Порядок вложенных полей |
| --- | --- |
| 86 | Номера аргументов, снимки в порядке номеров |
| 87 | Кортеж результата, номера аргументов, итоговые снимки |
| 73 | Скалярная ошибка |

Вложенный тег 1 содержит два однобайтовых номера. Тег 2 содержит результат
в 12 байтах: знаковый 32-битный `int` и знаковый 64-битный `big` в сетевом
порядке. Каждая запись с тегом 3 содержит однобайтовый номер объекта и
те же 12 байтов. Таблица номеров в ответе должна совпадать с запросом.

DisVM проверяет весь ответ и захватывает оба отдельных объекта и место
для результата перед записью. Если значение хотя бы одного поля отличается
от снимка, возникает `remote ref changed during call`, а все поля клиента и
место для результата остаются прежними. Отмена, неверный ответ и исключение
провайдера тоже отменяют обратную запись. Номера действуют в пределах одного
вызова на fid функции. Профиль использует запрос без PID и поддерживает
два аргумента с этим скалярным ADT.
См. [запускаемый пример с двумя VM](../../examples/remote-scalar/STYX.ru.md#передача-одного-объекта-в-два-аргумента-ref).

## Вызов по скомпилированным скалярным типам

Экспорт вне фиксированных профилей может использовать общий диспетчер,
если в обоих скомпилированных образах записаны типы. Во время `load`
DisVM сверяет имя, сигнатуру и полные схемы аргументов и результата,
затем связывает удалённый слот. Владелец сверяет по той же схеме каждый
вызов.

Аргументы образуют один упорядоченный список. Кортеж представлен вложенным
списком. Результат описывает один скаляр или кортеж. У функции без
результата список пустой. Каждый список может содержать до четырёх скалярных
листовых полей. Значения `int`, `big` и `real` передаются в сетевом порядке байтов.
Кодек поддерживает до четырёх уровней с учётом внешнего списка и запись
размером до 64 байт. Общий диспетчер принимает аргументы по значению.
У существующих профилей с `ref` сохраняется обратная запись.

| Тег внешней S-записи | Содержимое |
| --- | --- |
| 89 | Типизированный список аргументов |
| 90 | Типизированный список результата |
| 73 | Ошибка скалярного вызова |

Теги вложенных S-записей 1, 2, 4 и 5 обозначают `int`, `big`, кортеж
и `real`. Каждое скалярное поле содержит байт вида 2 и восемь байтов данных.
Значение `int` должно помещаться в 32 бита. Для `real` это биты IEEE 754
binary64 с сохранением знака нуля и полезной нагрузки NaN. Для связывания
экспорта с `real` обе стороны должны поддерживать токен `f`.

Теги применяются к упакованным запросам без контекста PID через файл
функции в Styx. Владелец связывает и вызывает исходный экспорт Dis в своей
VM. См. [пример с двумя VM](../../examples/remote-scalar/STYX.ru.md#вызов-по-скомпилированной-схеме).

## Вызов по скомпилированным типам ref

Владелец может выбрать существующий протокол передачи ссылок по
скомпилированной схеме. В списке аргументов допустимы одна или две ссылки
на ADT с полями `int` и `big` в этом порядке. Две ссылки можно передать
одним кортежем. Функция может возвращать `int`, `(int,big)` или
завершаться без результата. Для этих дополнительных сигнатур метаданные
типов нужны с обеих сторон. Перед публикацией экспорта владелец проверяет
карту указателей исходного кадра Dis.

Протоколы для одной и двух ссылок сохраняют существующие теги и снимки.
При пустом результате оба поля результата в ответе равны нулю. Для
результата `int` обнуляется второе поле. Клиент проверяет заполнение до
захвата объектов и области результата. Он записывает только объявленные
ячейки результата и применяет изменения объектов вместе с ними. При
пустом результате захватываются только объекты. Если две позиции
указывают на один объект, он передаётся и обновляется один раз. При
отмене, исключении владельца, неверном ответе или конфликте с локальной
правкой обратной записи нет. При двусторонней публикации эти профили
могут получать [контекст клиента](#контекст-клиента-для-вызовов-по-схеме).

См. [пример с двумя VM](../../examples/remote-scalar/STYX.ru.md#вызов-по-скомпилированным-типам-ref).

## Контекст клиента для вызовов по схеме

Провайдер, запущенный через [styxunibusserverstartscopedset](UNIBUS-SERVER-SCOPED-SET.ru.md),
использует Styx в обоих направлениях. Клиент по-прежнему вызывает обычный
Limbo `load` и передаёт объявленные аргументы функции. DisVM берёт PID
текущего процесса и его выдачи у клиентского маунта. Встречная выдача
удерживается от записи запроса до завершения чтения ответа.

| Тег S-записи | Содержимое |
| --- | --- |
| 91 | Полезная нагрузка профиля 88 с требованием встречного маунта |
| 92 | Четыре байта PID в сетевом порядке, затем полный запрос выбранного профиля |
| 90 | Ответ для профиля значений. У вызовов с `ref` свой тег ответа. |
| 73 | Обычный ответ об ошибке владельца |

Перед вызовом диспетчер проверяет аргументы и захватывает `.prog/<pid>`
из встречного корня этой сессии. Захваченный нативный провайдер хранится
вместе с локальным запросом. VM владельца открывает его в `/.prog/.self`
в частном пространстве имён исходного экспорта Dis. Файлы и поддеревья
приходят из выдачи клиента. Внутренний запрос использует тег 89 для
списка значений, 81 для одной ссылки или 86 для карты объектов. Правила
снимков и атомарной обратной записи `ref` применяются и здесь. VM
создаёт алиас в VFS и привязывает частную очередь Sysevents.
См. [события удалённого вызова](../../runtime/SYSTEM-EVENTS.md#пространство-имён-удалённого-вызова).
Режим доступен дополнительным сигнатурам, выбранным по схеме.
См. [пример с двумя VM](../../examples/remote-scalar/STYX.ru.md#вызов-через-встречный-маунт-styx).

### Явный конец запроса

Нативный клиент может записать тег 94 с целым обычным запросом функции
внутри, затем записать пустой тег 95 по следующему байтовому смещению
того же fid. Первая запись сохраняет байты. Вторая проверяет запрос
и передаёт его на выполнение. Чтение с нулевого смещения до выполнения возвращает ноль байтов.
Закрытие fid до тега 95 освобождает запрос. Прежние клиенты с одной
записью продолжают работать.

Экспорт с контекстом может объявить в профиле тег 96 с тем же содержимым,
что у 91. Обычный Limbo `load` выбирает для тега 96 две записи с явным
концом запроса. Встречная выдача PID действует на протяжении обеих записей
и чтения результата. Тег 91 по-прежнему выбирает одну запись. Для
импорта каталога с тегом 96 прежним загрузчикам требуется обновление.

Профиль 98 добавляет перед аргументами S-запись 97 с относительным
путём контекста. Обычный `load` посылает `.prog/.self`. Явный
`.prog/<pid>` должен совпасть с PID запроса. Теги 91 и 96 сохраняют
прежние форматы. Аргументы и конец по-прежнему идут на том же fid.

Нативный тест проверяет два отложенных запроса на одном соединении. Один fid закрывается до тега конца, выполняется только запрос с оставшегося fid.

Для профиля 98 запись тега конца подтверждает приём задачи нативным
воркером. Пока ответ готовится, чтение с нулевого смещения возвращает
ноль байтов. Рантайм опрашивает тот же fid и удерживает контекст до
конца обмена. Вызовы разных экспортов могут продвигаться по одному
соединению. Вызовы одного экспорта используют его приёмник по очереди.
Clunk снимает задачу, которая ещё ждёт передачи владельцу. Если
передача уже началась, clunk закрывает fid и подаёт сигнал обработчику.

У активного вызова с контекстом есть собственный токен отмены. Clunk
подаёт сигнал в этот токен. Долгая функция на стороне владельца может
проверить `Vfsnative->callcancelled()` в безопасной точке и выйти из
вызова. Сигнал относится к одному вызову. Код без проверки может
продолжить выполнение до возврата.
