# Контекст клиента на маршруте Styx

[English](LAUNCH-PROGRAM-ROUTE.md) · [Пример запуска](test_unibus_files.c) · [Номерные FD](LAUNCH-PROGRAM-FDS.ru.md)

Лаунчер связывает маршрут запуска с выданным каталогом конкретной загрузки
модуля на стороне клиента. Он передаёт этот провайдер в
`DVM_LaunchSpec.program_root`. Запрос выбирает процесс внутри этого каталога.
Две загрузки одного модуля могут использовать один и тот же номер PID
для разных контекстов. PID имеет смысл внутри выданного каталога загрузки.

## Запись запуска

`styxterminallaunchprogramaddress` удерживает файл запроса и копирует
`DVM_LaunchProgram`. При отправке существующая S-запись получает
13-байтный префикс перед аргументами гостя.

| Байты | Поле |
| --- | --- |
| 0 | Версия 1 |
| 1–4 | Ненулевой PID клиента |
| 5–8 | PID базы наследования, 0 при её отсутствии |
| 9–12 | Маска скрытых номеров FD |
| 13 и далее | Исходные байты аргументов запуска |

Числовые поля после версии записываются старшим байтом вперёд. В одной
записи, включая префикс, допускается до 65 536 байт данных. На маршруте с
`program_root` приёмник отклоняет неверную версию, неполный префикс,
нулевой PID и совпадение PID с базой. Подготовка запуска захватывает
`.prog/<pid>` и, при наличии, каталог базы до состояния READY.
Отсутствующий каталог приводит к отказу. `Launchcontext.arguments()`
возвращает исходные аргументы, включая встроенные нулевые байты.
Маршруты без `program_root` принимают прежний формат аргументов.

## Пространство процесса

Реализован импорт `<загрузка>/.prog/<pid>/.fd`. В тесте внешний Styx-сервер
публикует `loaded.dis/.prog/41` и `loaded.dis/.prog/42`. Запустите
`ctest -R '^terminal-ordered-files-guest$' -V`. Ожидается
`PASS actual portable Dis guest record files scoped` в обоих режимах VM.

При подготовке запуска DisVM захватывает `.vfs` выбранного процесса.
Только подтверждённое отсутствие разрешает унаследовать весь каталог
`.vfs` базового процесса. Если путь ведёт к файлу или поиск завершился
ошибкой, запуск отклоняется. До `init` каталог подключается в новом процессе
как `/.vfs`. Если по этому пути или внутри него уже есть явные привязки,
принятие запуска отклоняется. Локальный `spawn` наследует пространство имён,
а доступ определяется обычными правами файлов. Окружение клиента доступно
через обычные файлы, например `/.vfs/env/CLIENT`. Принятый корень провайдера
и контекст запуска остаются доступны рядом с этим поддеревом.

Стенд проверяет собственное пространство клиента и наследование базового
пространства. В каждом случае запущенный процесс и его потомок читают
соответствующее значение окружения через `/.vfs`.

Для двустороннего доступа к переменным Limbo/DisVM и FlashVM предусмотрена
`.var`. Составное значение представляется каталогом. `.type` и `.len`
дают тип и длину. Для индексированного доступа клиент открывает `.idx`,
пишет индекс, выполняет чтение или запись через `.val` и закрывает `.idx`.
Диспетчер должен связывать выбор индекса с открытой операцией, чтобы два
параллельных обращения к одной переменной сохраняли свои индексы.
`.ins`, `.add`, `.push` и `.pop` задуманы как операции обновления коллекции.

При принятии запуска DisVM публикует в его частном пространстве
`/.prog/.self/.pid` и `/.prog/.self/.vfs`. Первый путь читает
доступный только для чтения файл `.pid` выбранного клиентского процесса.
Публикатор записывает туда десятичный PID с переводом строки. Второй путь
ведёт к тому же эффективному дереву, что и `/.vfs`, включая унаследованный
вариант. Окружение остаётся файлами в `.vfs/env`. Привязка живёт в
пространстве запуска и наследуется локальным `spawn`. Номерные FD
доступны через `Sys.fildes`. Если выбранный процесс публикует каталог `.var`, он доступен через
`/.prog/.self/.var` с правами исходного Styx-экспорта. Файлы читаются и
записываются напрямую. Отсутствующая `.var` базой не подменяется.
Стенд проверяет изменение `counter` запущенным кодом и его потомком.
Автоматическая публикация переменных VM и операции с составными значениями
остаются отдельной работой.

Стенд использует [целочисленный прокси с обработчиками владельца](../native/terminal/VARIABLE-FILE.ru.md).

## PID из активного вызывающего процесса

Для маршрута, принимающего контекст процесса, объявите адрес через
`styxterminallaunchcalleraddress`. Обычные `Vfsnative.run` и
`Vfsnative.runargs` снимают PID текущего процесса до перехода в нативное
ожидание. Адрес кодирует его в заголовке записи Styx. Принимающая сторона
по-прежнему выбирает процесс только внутри выданного корня загрузки.
Аргументы гостя передаются как отдельный хвост записи. Если запустить
отправку без активного PID, такой адрес откажет до записи в Styx.

Сквозная проверка отправляет запросы с одного маршрута из двух Limbo-процессов
и сравнивает оба PID с `Processctl.pid()`. Настройка маршрута и выдача корня
загрузки пока выполняются лаунчером. Этот путь относится к запуску процесса.
