
## Локальный встречный процесс
`disvm --styx-local-pair PROGRAM [PEER OPTIONS] -- [MOUNT OPTIONS] -- [VM OPTIONS] BOOTSTRAP.dis`
выполняет обычный двусторонний маунт `--styx-mount-fd` по частной паре Unix-сокетов.
`PROGRAM` — явный путь к программе. Она получает `--fd FD`, затем `PEER OPTIONS`.
DisVM владеет процессом и дожидается его завершения. Команда возвращает код
DisVM или код встречного процесса, если DisVM завершилась успешно.

Необязательный `--assets АБСОЛЮТНЫЙ_КАТАЛОГ` после `--at` создаёт маунт
`/ide-assets` только для чтения и задаёт базу начальных относительных импортов.
Рабочая область остаётся в текущем каталоге. Опция `--document PATH` или
`--new PATH` передаёт гостевой путь приложению через привязку Unibus.
`--new` запрашивает пустой буфер без чтения файла на старте.

[Пример установленной IDE](../../ide/DESKTOP-PAIRED.ru.md)

[Типизированный обмен UniBus](STYX-CHANNEL.ru.md) работает в двунаправленной сессии, которую уже подключил CLI.

## Подключение по TCP

Сборка Linux64 с нативным SDK открывает транспорт сама. Вместо
`--styx-mount-fd FD` можно использовать `--styx-mount-tcp HOST PORT`,
вместо `--styx-serve-fd FD` — `--styx-serve-tcp HOST PORT`, вместо
`--styx-library-serve-fd FD` — `--styx-library-serve-tcp HOST PORT`.
Остальные аргументы каждой команды те же. Программа в Dis получает ту же
живую VFS и контекст StyxRPC.

```sh
disvm --styx-serve-tcp 127.0.0.1 7474 --persistent --execute-as job.dis job.dis -- --native-spawn owner.dis
disvm --styx-mount-tcp 127.0.0.1 7474 --at /peer -- --native-spawn caller.dis
```

Сначала запустите слушатель. `HOST` у слушателя задаёт местный адрес, а у
подключающейся стороны — адрес собеседника. Порт десятичный. При `0`
слушатель печатает выбранный порт первой строкой `styx listening PORT`.
Обслуживается одно транспортное соединение. `--persistent` допускает
несколько запусков программ на нём. Параметр `--raw` предназначен для
сервера обычного Styx без двустороннего транспорта. Прямой TCP работает
открытым текстом без проверки собеседника. Используйте loopback, доверенную
сеть либо отдельно защищённый поток, переданный через команду с FD.

[Команды FlashVM](../../flashVM/doc/STYX_RPC_PLAYER.ru.md#запуск-через-tcp) ·
[Справка транспорта](../../lib/styx/docs/reference/phytcpdial.ru.md)

## Двусторонний маунт для локальной программы

В сборке DisVM с нативным SDK можно передать подключённый поток и
запустить локальную программу, которая загружает библиотеки у провайдера.

```sh
disvm --styx-mount-fd 3 -- --no-jit caller.dis
```

По умолчанию точка монтирования — `/peer`. Укажите `--at /transport`
перед `--fd3` или `--`, чтобы выбрать канонический абсолютный путь в VFS.
Каталог для точки монтирования на хосте не требуется. Канал 0 мультиплексированного транспорта
несёт прямой маунт Styx, канал 1 обслуживает виртуальный контекст клиента.
Провайдер монтирует канал 1 и передаёт корень обработчику с контекстом.
Обычный типизированный `load` и вызов функции автоматически публикуют
контекст активного процесса. Провайдер определяется выданным соединением.

[Пример Limbo](../examples/remote-scalar/styx-cli.b) и тест
`terminal-caller-mount-cli` проверяют команду в двух процессах ОС с JIT и
без него. Укажите в настройке тестовой сборки SDK
`INFERNO_DISVM_TERMINAL_CLI` со ссылкой на исполняемый DisVM с этим SDK.

Если провайдер не публикует штатное объявление, можно явно указать
путь программы, файл запросов на запись и тег S-записи.

```sh
disvm --styx-mount-fd 3 --launch app.dis submit 17 -- caller.dis
```

Оба пути относятся к корню подключения. Маунт удерживает точные узлы.
Программа вызывает `Vfsnative.run` или `Vfsnative.runargs` для
`/peer/app.dis` либо его bind-имени. Провайдер обслуживает файл запросов
и принимает выбранный тег. Положительный результат подтверждает
доставку запроса провайдеру. В этом профиле передаются исходные
стартовые байты.

[Пример отправки запуска](../examples/remote-scalar/styx-run.b)
проверяет двоичные аргументы через bind и отказ для соседнего файла
без маршрута. Пример входит в тест `terminal-caller-mount-cli`.

### Запуск с обеих сторон

Передайте владельцу и клиенту разные концы одного подключённого
потока. На стороне владельца укажите локальный образ Dis.

```sh
disvm --styx-serve-fd 3 -- owner.dis
```

Служба публикует `implementation.dis` и принимает одну S-запись с
тегом 17 в `.unibus`. Запустите клиента с его концом соединения.

```sh
disvm --styx-mount-fd 3 -- caller.dis
```

Маунт читает объявление владельца из `.interface` и автоматически
закрепляет программу и файл запросов. Явные параметры `--launch` и
`--launch-context` имеют приоритет.

Владелец запускает указанный образ и выдаёт принятые байты через
`Launchcontext.arguments()`. Полная запись должна уместиться в
64-байтовый приёмник. В этом профиле запуска передаются стартовые байты.
Контекст процесса клиента пока не подключён. [Пример владельца](../examples/remote-scalar/styx-owner.b)
проверяет нулевой байт. Приёмочный тест запускает эти команды в двух
отдельных процессах DisVM.

### Запуск с живым контекстом клиента

Выберите профиль с контекстом на обоих концах выданного соединения.

```sh
disvm --styx-serve-fd 3 --context -- owner.dis
disvm --styx-mount-fd 3 -- caller.dis
```

Программа Limbo вызывает тот же `Vfsnative.runargs`. Перед отправкой
запроса DisVM публикует виртуальное дерево `.prog/<pid>`. Владелец
монтирует встречный канал, захватывает каталог PID и подключает
доступный контекст до `init`. Экспорт удерживается до результата,
обрыва соединения или отмены ожидания.

Пример в двух процессах читает PID клиента и перенаправленный stdin
через `Sys->fildes(0)`, затем пишет в перенаправленный stdout клиента.
В предел приёмника 64 байта входят заголовки S-записи и контекста.

## Маунт библиотеки Styx у владельца

Команда `disvm --styx-serve-fd FD --context --library-fd LIBFD -- OWNER.dis`
передаёт запускаемому Dis второе уже подключённое соединение Styx.
`LIBFD` обозначает отдельный подключённый FD от 3 с обычной сессией
Styx. Владелец монтирует его в `/libraries` до приёма запроса. При
ошибке маунта сервер прекращает запуск. Модуль загружает библиотеку
обычным Dis `load` в пространстве имён владельца.
См. [пример с тремя участниками](../examples/remote-scalar/STYX.ru.md#запуск-через-три-disvm).

Если библиотечный провайдер запущен через `--styx-library-serve-fd`,
передайте его сокет через `--library-bidir-fd LIBFD`. DisVM монтирует
прямое дерево Styx и запускает встречный сервер. Вызовы получают
`.prog/.self` клиента, включая выданные файлы `.vfs` и унаследованные FD.
Оба варианта принимают `--library-at PATH`. Хост передаёт уже подключённый
транспорт. Концы соединения могут находиться на разных машинах.

Двусторонний маунт обнаруживает и исполняемые файлы. Служба
`--styx-library-serve-fd` с параметром `--execute` публикует
`implementation.dis` и может добавить именованные образы в `programs/`.
Для маунта в `/remote-libs` вызовите
`Vfsnative->run("/remote-libs/implementation.dis")` либо сначала
привяжите опубликованный файл к локальному пути через `bind`.
Запущенная через Styx программа тем же способом может выполнить зависимость
на следующей машине. В следующий запуск переходят текущие представления
дескрипторов и выданная VFS процесса. Явный маунт `/.var` выбирает
дерево переменных для следующего звена. При его отсутствии передаётся
дерево входящего запуска с прежними правами доступа. Провайдер видит его
в `/.prog/.self/.var`. У каждого запуска свой fid до завершения или отмены. См. [пример с тремя участниками](../examples/remote-scalar/STYX.ru.md#запуск-через-три-disvm).

### Многоразовый запуск на самостоятельном сервере

```sh
disvm --styx-serve-fd 3 --persistent -- owner.dis
disvm --styx-mount-fd 3 -- caller.dis
```

Параметр `--persistent` включает профиль с контекстом клиента. Владелец
читает настроенный образ Dis при старте, публикует тот же неизменяемый
образ и обслуживает подключение. Каждый `run` или `runargs` по bind-пути
создаёт отдельного потомка с контекстом клиента и возвращает его результат.
Разные потоки могут запускать программу одновременно. Приёмник встроен в
DisVM. Зависимости можно примонтировать у владельца через `--library-fd` или
`--library-bidir-fd` до приёма запросов. Без `--persistent` самостоятельный сервер завершает
работу после одного запуска.

[Пример клиента](../examples/remote-scalar/styx-persistent-cli.b) проверяет
два последовательных и два одновременных запуска с разными итогами.
Тест с тремя участниками также проверяет этот режим с унаследованными FD
и отдельно смонтированными библиотеками.

В многоразовом режиме отмена ожидания клиента закрывает fid запуска.
Владелец снимает запрос из очереди или останавливает своего потомка на
точке завершения VM. После закрытия fid итог процесса уже недоступен
клиенту. Другие запуски сохраняют свои fid и продолжают пользоваться
той же сессией.

### Результат запуска и дополнительный дескриптор

При запуске с контекстом `Vfsnative.run` и `runargs` пишут в открытый на
чтение и запись `.unibus` и читают ответ через тот же fid. Вызов возвращает
`1` при успехе, `-2` при подтверждённой ошибке запуска и `-1`, если итог
неизвестен. Fid получает результат после принятия собственного запроса.
Прежний файл `.exit` остаётся доступен для чтения. Одноразовый владелец
ждёт отсоединения клиента до пяти секунд после публикации результата.

При запуске клиента команда `--styx-mount-fd FD --fd3 EXTRA -- APP.dis`
публикует отдельно переданный открытый обычный файл под номером 3
вместе со стандартными потоками. Права и позиция общие с переданным
FD. Из гостевого кода для запуска по-прежнему достаточно пути VFS.

После `--library-fd LIBFD` можно задать `--library-at /remote-libs`,
чтобы выбрать точку маунта в VFS владельца. По умолчанию используется
`/libraries`. Укажите канонический абсолютный путь вне деревьев
`/.prog`, `/.fd`, `/.vfs` и `/.var`. Пример с тремя участниками
монтирует C в `/remote-libs` и добавляет его каталог `mounted`
в union библиотек приложения.

Пару `--library-fd FD --library-at PATH` можно повторить до восьми раз.
Номера FD и пути маунтов должны различаться. Вложенные точки маунта
отклоняются до открытия соединений. Владелец принимает запуск только
после успешной установки всех маунтов.

Разные номера FD, указывающие на один сокет, отклоняются до начала обмена Styx.

### Публикация дополнительных исполняемых файлов на одном маунте

Повторяйте `--execute-as NAME.dis IMAGE.dis` после `--persistent` и перед
настройками транспорта библиотек. Каждое публичное имя уникально и содержит
не более 31 символа ASCII. Начните его с буквы или цифры, используйте буквы,
цифры, точки, подчёркивания или дефисы и завершите на `.dis`. Служба
принимает до 16 дополнительных образов и хранит снимок каждого до конца сессии.

```sh
disvm --styx-serve-fd 3 --persistent --execute-as second.dis other.dis -- owner.dis
```

Автоматический маунт обнаруживает дополнительные пути через `.programs`.
На обычной точке монтирования основной путь — `/peer/implementation.dis`,
дополнительный — `/peer/programs/second.dis`. Передайте нужный путь в
`Vfsnative->run` или предварительно сделайте bind на локальное имя.
Запрос именованного запуска использует `programs/.second.dis` на том же
транспорте. Открытый fid выбирает образ и ведёт результат своего запуска,
включая ошибку и отмену. Формат контекста клиента и аргументов остаётся общим.

Совмещённый библиотечный сервер также принимает `--execute-as` после
`--execute PROGRAM.dis` и перед первым `--export`. Библиотечные экспорты
доступны под `mounted/`.
[Пример клиента](../examples/remote-scalar/styx-launch-client.b) проверяет
прямой и забинженный пути со
[вторым исполняемым файлом](../examples/remote-scalar/styx-named-launch-owner.b).


## Публикация нескольких библиотек через одну сессию Styx

Передайте провайдеру подключённый потоковый дескриптор от хоста. Повторите
`--export PUBLIC.dis OWNER.dis NAME` для каждого публикуемого экспорта.

```sh
disvm --styx-library-serve-fd 3 \
  --export first.dis first-owner.dis update \
  --export second.dis second-owner.dis update \
  -- scalarowner.dis
```

`PUBLIC.dis` — имя в `/peer/mounted` у клиента. `OWNER.dis` — путь к
реализации у провайдера, `NAME` — имя экспорта в ней. Собирайте реализации
и клиента с `limbo -D R`, чтобы сохранить метаданные типов для контекстных
вызовов. Диспетчер `scalarowner.dis` собирается из [scalarowner.b](../limbo/scalarowner.b).
После `--` идут обычные опции VM и путь к диспетчеру.

На другом конце потока клиент запускает
`disvm --styx-mount-fd 3 --at /transport -- caller.dis`. Создайте локальный
каталог `libraries` в рабочем каталоге клиента. [Пример клиента](../examples/remote-scalar/styx-library-cli.b)
добавляет `/transport/mounted` в конец объединения `/libraries` через
`Sys->bind` с `MAFTER`, затем загружает обе библиотеки обычным Limbo `load`. [Интеграционный тест](../native/terminal/tests/scalar/mount_cli.py)
собирает образы, соединяет два процесса, проверяет обратную запись `ref`
и сравнивает PID исполнителей. После отмены тот же PID клиента получает нового
исполнителя в другой библиотеке. Если экспорт отсутствует, провайдер завершает
запуск с ошибкой и указывает реализацию и имя экспорта. При отсоединении клиента провайдер завершает
обслуживание экспортов и освобождает ожидающие исполнители.


### Дополнительные номерные FD

Перед `--` можно повторить `--fd N HOSTFD` для гостевых номеров от 3 до 31.
Хост передаёт открытый FD обычного файла. `--fd3 HOSTFD` остаётся короткой
формой для номера 3. Режим чтения и записи берётся из открытого FD.
Два гостевых номера могут указывать на один хостовый FD и делят его
позицию чтения и записи. Номера 0, 1 и 2 берутся из стандартных потоков.
[Сквозной пример](../examples/remote-scalar/styx-chain-owner.b) проверяет
чтение через два номера и запись через один из них.

Файлы, ранее открытые через `Sys->open` или `Sys->create`, публикуются
из файловой группы клиента без дополнительных параметров запуска.
Номерные файлы сохраняют исходный режим и позицию. Явно переданные
через `--fd` номера резервируются у клиента. Гостевой маунт `/fd`
не участвует в публикации.

При контекстном запуске принятые номера также видны как файлы в
`/.prog/.self/.fd`. Открытие такого файла использует тот же слот, что
`Sys->fildes(N)`, с тем же курсором и режимом. Если `/env` уже входит в
переданное дерево VFS клиента, провайдер видит его как обычный каталог
`/.vfs/env`.

### Публикация программы и библиотек вместе

Владелец библиотек монтирует собственные зависимости параметром
`--library-bidir-fd FD [--library-at PATH]` перед заключительным `--`.
Зависимости доступны обычной инструкции `load` из библиотеки. Вложенный
вызов наследует входящие каталоги клиента `.fd`, `.vfs` и `.var`, если их
не заменяют явные локальные маунты. См.
[пример с тремя VM](../examples/remote-scalar/STYX.ru.md#проверка-на-отдельных-машинах).

Укажите `--execute PROGRAM.dis` перед таблицей экспортов:

```sh
disvm --styx-library-serve-fd 3 --execute launch.dis \
  --export first.dis first-owner.dis update \
  --export second.dis second-owner.dis update -- scalarowner.dis
```

Один Styx-маунт публикует программу как `implementation.dis`, а библиотеки
под `mounted`. Клиент может привязать программу к другому пути в VFS
через `bind` и запустить её через `Vfsnative.run`. Каждый вызов запускает
настроенный образ в отдельном дочернем процессе Dis с контекстом клиента
и получает свой результат через открытый fid. Разные потоки могут
запускать программу одновременно, а один поток может запустить её снова
после завершения. Очередь вмещает до 64 ожидающих запросов. Полная запись
запроса вместе с селектором и заголовком S-записи умещается в 64 байта.
На той же сессии доступны библиотеки. Самостоятельный сервер включает
ту же очередь параметром `--persistent`.

[Тест штатного CLI](../native/terminal/tests/scalar/mount_cli.py) запускает
[пример программы](../examples/remote-scalar/styx-shared-launch-owner.b),
проверяет результат и вызывает библиотеки через тот же маунт.
