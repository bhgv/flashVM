# Локальное владение, публикация и области сильных ссылок

Решение от 2026-11-03: компилятор выбирает локальные или общие операции там,
где это доказано анализом. Не добавлять проверку «общий ли объект» к каждому
локальному чтению. Не использовать значение refcount как доказательство
локальности. Реализация минихипа может быть структурой учёта поверх существующих
аллокаций; отдельные mmap, системный allocator и C++ для этого не обязательны.

## Что можно выполнять без объектной блокировки

Локальный слот вызова принадлежит вызову, но объект по ссылке из слота может быть
общим. Скаляры и доказанно не выходящие к другим исполнителям объекты допускают
локальные операции. Данные экземпляра модуля требуют доказанного единственного
исполнителя. Наличие spawn — достаточный повод для консервативного общего пути,
его отсутствие само по себе не доказывает локальность.

Обычный load создаёт отдельный Modlink и MP, хотя Module/код могут разделяться.
spawn использует экземпляр родителя; переданная ссылка на экземпляр и $self
также могут сохранять общий MP. Native Sys — отдельный случай с ресурсами ОС.
Этот анализ должен идти по экземплярам и алиасам, а не только по имени модуля.

Границы публикации: аргументы spawn, передача ссылок по каналам, запись в общую
структуру, результат интерфейсной функции, передача экземпляра модуля, неизвестный
native вызов. Интерфейсный результат консервативен: сам выход из функции не всегда
создаёт второго исполнителя, но отсутствие доказательства требует общего пути.
Нужно учитывать доступный изменяемый граф, включая циклы, поля и массивы; нельзя
публиковать только контейнер, сохранив доступные детям ложные локальные гарантии.

Если объект становится общим, старые локальные алиасы тоже должны перестать
использовать локальные операции ДО допуска другого исполнителя. Нельзя лишь
поставить флаг на объекте и оставить ранее скомпилированный прямой store.
Начальный безопасный вариант: консервативный общий путь для потенциально
выходящих объектов с самого начала. Более поздний — проверенный переход на
границе с переключением специализации/deoptimization и публикацией корней.
Доказательство владения и его инвалидирование должны покрывать C и каждый JIT.
Неизвестный импорт/динамический вызов не считается доказанно локальным.

## Владельцы и время жизни

Восемь потоков могут иметь восемь владельцев, а могут иметь шестнадцать — если
каждый удерживает две независимые сильные ссылки. Указатель, заимствованный под
защитой другого владельца, отдельного счётчика не добавляет. До снятия защиты
исходного слота нужно либо получить свою сильную ссылку, либо закончить доступ.
Это нельзя откладывать до момента, когда исходный владелец уже исчез.

Копирование удерживает DISTINCT владельца перед публикацией. Перенос передаёт
уже существующего владельца и очищает источник, не увеличивая счётчик. Последнее
освобождение получает исключительную ответственность за retirement. Ссылки
ожидающих блокировку сохраняют объект живым. Корни GC, счётчики ссылок и доступ
к mutable payload — три разных обязанности. Циклы не исчезают от одного RC.

## Реализованный шаг v0.1758: native owner scopes

[owner_scope.h](https://github.com/bhgv/flashVM/blob/master/disVM/include/disvm/owner_scope.h) и
[owner_scope.c](https://github.com/bhgv/flashVM/blob/master/disVM/host/owner_scope.c) реализуют явный native реестр сильных
ссылок, привязанный к текущему NativeContext. Это не новая реализация аллокатора.
Записи предоставляются вызывающим кодом, не копируются и остаются по стабильным
адресам до удаления/закрытия. Вставка вызывает retain ровно один раз. Явное
обнуление удаляет запись и вызывает drop. Закрытие области очищает записи в
обратном порядке. Запись очищается ДО drop, который может освободить объект.
Синхронный повторный вход в изменяемый реестр из callback запрещён.

Экспорт переносит владельца в native envelope. Приём переносит его в область
получателя. Envelope требует внешней синхронизации публикации и единственного
получателя; API не делает raw указатели безопасными и не сериализует их между
VM. Неудачный запуск потока откатывается cancel только непереданного envelope.
Дублировать/копировать заполненный envelope нельзя. Своя область не пересылается
другому потоку; пересылается только её отдельный владелец.

Открытые области запрещают TLS unbind; они не запрещают обычные safepoint и не
являются managed GC roots. Изменение/закрытие области с удерживаемым object guard
отказывается до callback, чтобы drop не инициировал освобождение под блокировкой.
Scope не делает доступ к payload потокобезопасным и не доказывает локальность.
Callbacks должны завершаться нормально, без VM вызовов/смены контекста/longjmp.

Это ЯВНАЯ очистка, а не готовое автоматическое разворачивание Dis-стека. Native
пример вызывает close в эпилоге каждого рабочего потока. Подключение к обычным
и исключительным выходам Dis-процессов, mapped roots, каналам и родному C/JIT
ещё не выполнено. Принудительная OS cancellation не поддержана. До этой
интеграции нельзя объявлять новый scope владельцем произвольных managed ссылок.

## Проверки и граница готовности

Native fixture использует восемь OS-потоков и барьер: пока все ссылки удержаны,
счётчик равен 17; после эпилогов — 1. Есть реальные malloc/free lifetime передачи,
в которых отправитель закрыл область ДО старта получателя. Проверяются rollback,
повторный приём/cancel, foreign доступ, busy reentry, overflow/zero без публикации,
порядок cleanup и отказ drop под guard. Негативные controls требуют semantic
exit 10; сигнал, timeout и ошибка компилятора не считаются обнаружением.

Это native ownership evidence. Managed Heap/Type/Jit, формат Dis64 и исключительный
NativeWorld не меняются. Анализ выходящих ссылок и генерация специализированных
операций выше — согласованный план, ещё не реализованный проход компилятора.
