# Ожидание событий редактора и неизменная сцена

[English](EDITOR-IDLE.md) · [Runtime](README.md)

## Назначение

У графического редактора два native-владельца: FlashVM/SDL в main и Dis в
собственном потоке ОС. При пустой очереди ввода оба должны ждать. Неизменная
сцена не требует ни нового задания растеризации, ни новой презентации SDL.
Правило общее для одиночного редактора и desktop-приложения, а не политика IDE.

## Источники пробуждения

[Launcher](editor_thread.c) будит UI main после публикации Dis скопированного
кадра, native RPC, завершения или запроса остановки. Мьютекс сессии и поколение
condition исключают потерю пробуждения между проверкой и ожиданием. При живой
сессии отправляется также частное SDL-событие без указателей в кучи VM.

[Ожидание UI](editor/view/idle_wait.inc) использует SDL_WaitEventTimeout на
современных оконных backend. Полученное обычное событие сохраняется в прежнем
postponed FIFO-слоте, поэтому ожидание не поглощает ввод. Если ввод пока
заблокирован презентацией или подтверждением Dis, это не вызывает нулевой
таймаут и непрерывный повтор проверки.

Срок ожидания сокращается для настоящего таймера/Async callback FlashVM,
незавершённой растеризации, группировки ввода или активной интерполяции.
[fvm_timers_next_delay](../../flashVM/include/flashvm/timers.h) учитывает и
[Async.post](../../flashVM/include/flashvm/async.h). Само пробуждение и запрос
дедлайна не инвалидируют сцену. Необходимость рисования определяет существующий
конвейер dirty/pending кадров.

Предел 1000 мс восстанавливает работу при отказе native wake, а не задаёт частоту
кадров. Raster и настоящая анимация проверяются через 8 мс. Для dummy/offscreen
и версий SDL до 2.0.18 используется condition с пределом 16 мс: собственное
fallback-ожидание SDL может внутри опрашивать события каждую миллисекунду.
Проверка платформенного ввода сохраняется; сообщения Dis будят condition сразу.
Это компромисс задержки старого ввода и числа пробуждений. SDL также может
опрашивать устройства внутри ожидания в зависимости от сборки и системы.

## Проверка

После сборки обычного runtime с SDL выполнить из корня репозитория:

```sh
ctest --test-dir build/runtime-clean-on -R 'disvm_(sdl_idle_window|editor_idle_cpu|desktop_workflow_)' --output-on-failure
```

Замените путь сборки своим. SDL-тест требует Linux, Python, совместимый C
компилятор/линкер и editor с SDL. Тестовые обёртки перелинковываются с настоящими
объектами runtime; renderer, интерпретатор и реализация очередей не заменяются.

[Регрессия](test_sdl_idle.py) независимо отправляет события и измеряет по две
тихие секунды видимого и свёрнутого dummy-окна. В каждом интервале требуется
ноль заданий растеризации и ноль SDL_RenderPresent. Проверяются CPU, количество
итераций UI и настоящий callback через 75 мс. Затем окно восстанавливается,
меняет размер, получает текст, сохраняет его и закрывается. Проверяются файл и
изображение. Предел итераций выявляет прежний цикл 1 мс независимо от скорости CPU.

Для проверки callback обёртки устанавливают scalar standard builtins в
single-view контексте, которому они обычно не требуются.

Дополнительная проверка ветки native wait с тем же dummy SDK:

```sh
DVM_TEST_NATIVE_WAIT=1 python3 disVM/runtime/test_sdl_idle.py build/runtime-clean-on/disvm-editor build/runtime-clean-on/desktop-ide.dis build/runtime-clean-on/fonts/NotoSansMono-Regular.ttf
```

Флаг понимают только тестовые обёртки. SDL сохраняет dummy-очередь; CPU её
внутреннего опроса не измеряет эффективность настоящего X11/Wayland wait.
Dummy-тест не подтверждает стоимость физического экрана, ввода или GPU.
Сборка replay без SDL компилируется и проверяется отдельно.
