# dvm_launch_handoff_program

[English](LAUNCH-PROGRAM-FDS.md) · [Заголовок](vfs/launch/ticket.h) · [Пример](test_unibus_files.c)

```c
int dvm_launch_handoff_program(DVM_LaunchHandoff *handoff, DVM_Provider *source,
    uint32_t pid, uint32_t parent_pid, uint32_t hidden_fds);
```

Вызовите функцию из нативного лаунчера до принятия эксклюзивного handoff.
Передайте уже разрешённый корень экспорта в `source`. PID — ненулевое
десятичное имя в этом экспорте. При нулевом `parent_pid` наследования
нет. Иначе параметр выбирает отдельный базовый контекст в том же экспорте.
Бит N в `hidden_fds` скрывает дескриптор N. Поддерживаются номера от 0 до
31. Функция может ждать провайдера. При успехе она возвращает 1 и удерживает
оба каталога, при отказе возвращает 0 и сохраняет исходный handoff.
Для освобождения используйте `dvm_launch_handoff_free`. PID указывает
имя внутри уже выданного корня.

При принятии запуска DisVM читает `.fd` в удерживаемых каталогах.
Запись выбранного контекста имеет приоритет над одноимённой записью базы.
Явное исключение скрывает обе записи. Каждый итоговый файл открывается
один раз до входа в код гостя. Режим берётся из прав на чтение и запись.
Отсутствующий стандартный дескриптор в этом режиме остаётся закрытым.
Локальный `spawn` наследует открытые файлы с общей позицией. Нативный
публикатор может сохранить семантику снимка, если удерживает открытые
объекты и сохраняет их привязки после захвата каталога.

В настроенном SDK запустите `ctest -R '^terminal-ordered-files-guest$' -V`.
Стенд выбирает `.prog/42` поверх `.prog/41`, заменяет FD 1, скрывает FD 2
и наследует FD 0 и 3. Гость читает FD 3 до и после чтения потомком и
проверяет общую позицию. Тест сверяет содержимое файлов базового FD 1
и скрытого FD 2. API принимает контекст, выбранный доверенным лаунчером.
Публикация процессов, выбор PID по протоколу запуска и группы окружения
остаются за границами этой точки входа.

Выбор контекста в записи запуска описан в разделе [Контекст клиента на маршруте Styx](LAUNCH-PROGRAM-ROUTE.ru.md).
