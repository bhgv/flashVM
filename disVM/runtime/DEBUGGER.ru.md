# Отладка с сохранением исходного состояния

В DisVM встроены отдельный системный поток управления и ограниченный протокол
отладки. Для работы VM не нужны установленные GDB, Python, библиотеки отладчика
или внешний сервис. Python-клиенты в `tools/` и примерах необязательны. Профиль
исполнения остаётся прежним: отдельные нативные потоки, exclusive=0.

```
disvm --debug /private/new-endpoint --jit application.dis
disvm --debug-fds 3 4 --jit application.dis
disvm --gdb --jit application.dis
```

`--debug` создаёт новый Unix socket с правами0600, отказывает существующему пути
и удаляет только собственный inode. `--debug-fds` дублирует разные унаследованные
FD>=3 для команд и ответов; ввод/вывод приложения не затрагивается. Защитите
родительский каталог и передачу FD. Pipe-вариант работает и при запрете sockets.

`--gdb` указывается первым. Только этот явный флаг запускает установленный `gdb`
через PATH, передавая остальные аргументы VM и открывая его приглашение. До загрузки
VM запрашивается non-stop; фактическая поддержка зависит от GDB target, её нужно
проверять. Можно дополнительно передать `--debug`. Символы зависят от параметров
сборки. Отсутствие GDB означает ошибку только явно запрошенного запуска под GDB.

## Протокол

Начальная команда `hello 0` возвращает `session` из32 случайных hex-символов
и PID системного процесса. Каждая следующая строка начинается с `@SESSION `.
Старая сессия не может управлять другой VM после повторного использования пути
или PID. Команда занимает до255 байт, ответ до4095. Принятие pause/terminate
асинхронно: подтверждённую остановку проверяют через status.

| Команда | Назначение |
| --- | --- |
| `list AFTERPID` | Следующий живой resident с большим PID |
| `status PID` | Скопированные location/opcode/error и подтверждение остановки |
| `registers PID` | VM REG; для работающего потока это последняя публикация |
| `operation PID` | Исходная Dis-инструкция и её закодированные операнды |
| `pause PID` | Запрос остановки на границе инструкции/нативного возврата |
| `continue PID` | Освободить исходное продолжение, выполнить обычный handler |
| `terminate PID` | Завершение самим владельцем и штатная отмена native wait |
| `step PID` | Одна Dis-инструкция только после остановки перед инструкцией |
| `backtrace PID INDEX` | Один кадр сохранённого Dis-стека, index<128 |
| `read PID stack\|mp FRAME OFFSET COUNT` | До64 байт внутри типизированного кадра/MP |
| `object PID stack\|mp FRAME SLOT OFFSET COUNT` | Данные объекта из сильного Type.map-слота |
| `census PID` | Обход опубликованных GC-корней этого потока по запросу |

Чтение памяти требует `retained:true`, использует штатные shared guards и не
принимает произвольные системные адреса. Указатели в REG — диагностические числа,
а не разрешения на чтение. Getter/guest callbacks не вызываются. Инспектор имеет
свой GC admission и никогда не исполняет чужой Prog.

Зацикленный Dis-поток останавливается на следующей проверенной границе инструкции.
Владелец, заблокированный на канале, сам публикует TLS-корни. При проверенном
native wait корни публикуются до выхода из managed admission, а debug gate
задерживает возврат в managed-код. Это не произвольная приостановка системного
вызова посреди его внешних эффектов. Возобновляется исходное C/TLS-продолжение;
снимки REG не используются для восстановления или переноса исполнения.

Managed-исключение в debug-режиме останавливается до `handler()` и разрушения
кадров, включая исключения, для которых существует Limbo handler. Исходные стек,
корни и исключение сохраняются до явного continue/terminate. Остальные потоки
и GC продолжают работу. Continue передаёт исключение обычному handler; непойманное
исключение завершает только исходный поток и даёт ненулевой итоговый статус
приложения. Terminate — явное действие отладчика. Невозможность безопасно выйти
из managed admission отмечается `fault_stop_refused`, без ложного обещания freeze.
Step не принимает fault/native/idle stops и не повторяет сомнительную операцию.

Отключение клиента не освобождает остановленные потоки. К socket можно подключиться
повторно; pipe EOF сохраняет состояние. Неполный ответ/timeout означает неизвестный
результат команды. Перед новым действием требуется status через рабочее соединение.
При завершении runtime сначала освобождаются gates и завершается инспектор,
затем GC; карточки удаляются после join исходных потоков. Потерянная pipe-сессия
может потребовать системного завершения процесса, если другого владельца FD нет.

## Статистика памяти

Census обходит опубликованные stack extents, модули, exval и сильные mapped edges
с временными нативными структурами только на время запроса. Постоянного каталога
объектов нет. Алиасы/циклы учитываются один раз; входящие guards удерживаются до
конца запроса. Размеры означают ёмкость аллокатора с заголовком/slack, а не payload
или RSS. Общие графы нельзя суммировать между потоками. Чужие корни, native queues,
внешние аллокации и системные ресурсы не входят в граф одного источника.

Пределы:256 объектов,384 поля,4096 байт карт,128 кадров,64 extents. Биты результата:
complete1,limit2,busy4,invalid8,opaque16. Limit даёт частичный префикс; busy/invalid
обнуляют счётчики. Непрозрачные edges не позволяют объявить полноту. Запрос ничего
не помечает, не удерживает и не изменяет в состоянии GC.

## Inferno и native crashes

В исходном Inferno `emu/port/devprog.c` реализует `/prog`, `dbgxec` и `progstack`;
`pctab` связывает нативный PC с Dis PC. В Linux `emu/Linux/os.c` передаёт
SIGILL/SIGBUS/SIGSEGV/SIGFPE в `disfault`. Это описание исходной организации,
а не основание возвращать её однопоточную модель в наш runtime.

[Карантин JIT-функций](JIT-QUARANTINE.ru.md) описан отдельно. Встроенное сохранение
охватывает managed throws, проверенные native waits и допущенные synchronous
integer/basic REAL scalar RX faults. [Контракт захвата](JIT-SIGNALS.ru.md) описывает actual-PC
checks, CPU context и admission/cleanup gates. `native-registers PID` возвращает
copied именованные integer CPU-регистры; `registers PID` остаётся VM REG.
Произвольные host/helper faults, повреждённая native memory, extended vector state и
произвольное native-frame retention не входят в эту гарантию. Явно выбранный
GDB может исследовать такие аварии независимо.

Базовые FP/SIMD-снимки и REAL fault policy: [контракт](JIT-FP.ru.md).
