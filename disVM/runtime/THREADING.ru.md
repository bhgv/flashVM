# Системные потоки UI и Dis

Runtime0.40.0 / IDE0.7.16 / серия v0.1732.
[English](THREADING.md) · [Запускаемый пример](https://github.com/bhgv/flashVM/blob/master/disVM/examples/threaded-owner/README.md).

`disvm-editor` теперь по умолчанию исполняет весь Dis runtime в отдельном
OS-потоке: загрузчик, interpreter/JIT, процессы Limbo, документы, каналы и GC.
Главный поток владеет SDL, FlashVM, вводом, сценой и нативной кистью. Растеризация
остаётся в существующих фоновых потоках. Опция `--threaded-ui` явно выбирает этот
режим; `--sequential-ui` оставляет последовательный маршрут для сравнения.
Повторное задание режима отклоняется до запуска.

## Границы владельцев

| Состояние | Владелец |
| --- | --- |
| extended up, REG, ошибки, очередь процессов, загрузчик, куча и GC Dis | Dis OS-worker |
| SDL, FlashVM-контекст, MovieClip, сцена, живые/замороженные штрихи | Главный UI-поток |
| Копии команд растеризации | Растеризационные workers |
| Сообщения между VM | Копии ограниченных значений |

`editor_thread.c` управляет запуском/завершением и одним RPC-слотом.
`editor_host.c` разделяет Dis-pump и UI-pump. `editor_bulk.c` отправляет геометрию
в ту же ограниченную очередь UI. Главный поток не обращается к Channel/Prog/
стеку/куче Dis; Dis-поток не вызывает напрямую сцену и контекст FlashVM.

В каждом направлении помещается32 записи. При переполнении bulk-очереди ждёт
отправитель Dis; главный UI-поток продолжает работу. Частичные снимки защищены
прежним барьером End. Принятие сообщения очередью не означает выполнения команды
документа. Локальные графические жесты и отрисовка по-прежнему независимы от кадров.

Запросы строк/настроек/пути и чтения/подтверждения/отмены штриха идут через RPC.
Сначала копируется сгенерированный нативный фрейм. Входные байты копируются в
нативную память с лимитом2MiB; ответ — скаляр или отдельно выделенная строка.
Возвращаются только замороженные штрихи. Ссылок на управляемую кучу в сообщениях
нет. Dis может ждать ответа, UI этот RPC не ожидает. Возвращённая C-строка
освобождается и при ошибке выделения строки Dis. Исходный размеченный фрейм
остаётся корнем аргументов и результата во время ожидания.

## Запуск и остановка

Главный поток разбирает параметры до запуска worker. Dis-worker создаёт свой
extended up/REG в существующем TLS и инициализирует настоящий runtime.
Инициализация UI выполняется главным потоком по запросу. Ошибки старта/очередей
приводят к контролируемому отказу. Закрытие очереди сверяется с синхронизированным
признаком остановки, чтобы нормальный EOF не становился ложной ошибкой.

Владелец Dis снимает заимствованные корни каналов, останавливает pumps, возвращается
из приложения и освобождает привязку TLS. Главный поток делает join до освобождения
очередей, RPC, UI и аргументов запуска. При ошибке UI закрываются очереди, чтобы
разбудить заблокированного отправителя. Принудительного обрыва потока нет;
некооперативный нативный вызов ещё может задержать остановку. Жёсткие аварии
аллокатора и process-exit сохраняют прежнюю семантику завершения процесса.

`DVM_EDITOR_THREAD_STATS=1` включает проверяемые сведения:

```
NATIVEOWNERS ui=main dis=worker ui_polls=... main_dis_tls=0 worker_bound=1 worker_released=1 result=0
```

Это наблюдаемые привязки/завершение, а не обещанная частота кадров. Главный поток
обрабатывает локальные жесты, пока Dis считает. Команды, которым нужен владелец
документа, всё ещё ожидают его ответ.

## Что проверено и что дальше

Подготовка up/REG/TLS используется непосредственно. Восемь отдельных процессов
запускают настоящие управляемые приложения, interpreter/JIT, каналы и GC с
нормальным возвратом; отдельно проверены два отказа и повторный флаг режима.
Сценарии SVG/pixel, clipboard и инструментов выполняются с новым разделением
потоков. Последовательный replay остаётся контрольным. Узкие проверки native
registers/world/Fast-Cycles сохраняют своё отдельное значение.

Сейчас у кучи и планировщика Dis один mutator-владелец. Limbo spawn по-прежнему
кооперативен внутри него. Следующие этапы — параллельные исполнители общей кучи,
подключение настоящего GC к world/safepoints, выход/вход вокруг блокирующих Sys,
синхронизация очередей, модулей/JIT и метаданных кучи. Эта серия не разрешает
несинхронизированные параллельные mutators и не завершает AS asinc lowering.

В этой сессии исполнение проверено на native Linux x64; использование общих OS-портов
не заменяет отдельные испытания ARM64/RV64, Android и физического дисплея.

## Runtime0.41.0: настоящий GC в системном потоке

Серия v0.1733 добавляет `--gc-worker` в консольный и графический host.
`--gc-inline` остаётся режимом сравнения по умолчанию. Отдельный поток сборщика
имеет собственные extended-up/REG, TLS и буфер ошибок. Он вызывает настоящий
`rungc`, сохраняя его адаптивный объём работы. Быстрый RC пока остаётся у Dis.

Модуль runtime_gc.c подключает native_world к настоящей куче и списку процессов.
После завершённой инструкции Dis останавливается; перед сканированием активные
регистры сохраняются в Prog.R. Между вызовами xec используются уже сохранённые
регистры, а активный процесс в TLS сбрасывается. Простой графического планировщика
тоже содержит точку остановки. Пока сборщик работает с кучей, Dis её не меняет.

При обычном выходе или управляемой ошибке host выходит из активного интервала,
дожидается принятой работы, присоединяет поток сборщика и снимает poll-hook до
освобождения TLS исполнителя. Итоговые счётчики печатаются после join. Исключение
самого сборщика завершает процесс, пока Dis остановлен: частично обработанную
кучу нельзя возвращать исполнителю. Жёсткое завершение процесса сохраняет
старую семантику. Блокирующий нативный Sys пока может задержать rendezvous до своего
возврата: полноценный release/reentry ещё предстоит подключить.

Пример examples/gc-worker создаёт 12 000 недостижимых циклов и проверяет сохранность
живого циклического объекта. Для каждого host тестируются шесть успешных запусков
и две управляемые ошибки лимита инструкций, JIT/интерпретатор и три кванта. Проверки
требуют настоящего освобождения циклического мусора, публикации корней, эпох GC и
согласованного учёта после join. Выполнено на Linux x64. Параллельный spawn в общей
куче, deferred RC и синхронизация публикации модулей/JIT остаются следующими этапами.
