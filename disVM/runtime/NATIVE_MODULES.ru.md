# Нативные C-модули Dis/DisVM: ABI и владение

[English](NATIVE_MODULES.md) · [Работающий пример](../examples/native-module/README.ru.md) ·
[Наш генератор .m → C](../../compiler/limbo/frontend/NATIVE_C.ru.md) ·
[Владение при смешанном UI](../../ide/RENDER_OWNERS.ru.md)

Нативный модуль реализует типизированный интерфейс Limbo `.m` функциями C.
Вызов остаётся обычным разрешённым модульным вызовом: loader сверяет сигнатуры,
VM предоставляет кадр с картой, callback публикует результат или поднимает ошибку.
Это не разрешение менять чужую кучу и не обход канального пути DisVM → Flash-контент.

## Порядок работы

1. Начните с `.m`: типы, владение, ошибки и допустимая блокировка. В интерфейс
   не должны попадать адреса C и раскладки OS-структур.
2. Выберите цель генерации кадров/сигнатур/карт. Наш
   `limbo_bindings --format native-c-nc64` поддерживает описанный скалярный профиль;
   `native-c-classic32` — другая явная цель. Для сложных старых интерфейсов пока
   нужен согласованный bootstrap, пока наш backend не разрешает их типы.
3. Реализуйте `Module_export(void *frame)` по полученным объявлениям. Не
   угадывайте смещения и не копируйте старые кадры от другой VM.
4. Соберите C в хост и зарегистрируйте таблицу через `builtinmod` после
   allocator. Не игнорируйте ошибку регистрации.
5. Соберите caller по тому же `.m`/ABI. Проверьте границы, ошибки, GC и оба
   режима исполнения, прежде чем подключать модуль к IDE.

Учебный `$Nativedemo` выполняет все эти шаги. Опция
`DVM_RUNTIME_NATIVE_DEMO=ON` требует явного `DVM_LIMBO_BINDINGS` и по умолчанию
выключена. Один `.m` не устанавливает модуль; пример не является загрузчиком
`.so`/DLL. Нативный кадр — внутренняя граница хоста, не сетевой формат.

## Целевой ABI

Исполняемый DisVM сейчас использует **NC64**: восьмибайтовые WORD, слоты
указателей/карт и аргументы, magic 819264. Классический Dis — четыре байта,
magic 819248. Неявного преобразования между ними нет. NC64 не означает, что во
всём стандартном Inferno автоматически поменялся размер int. Структурный хеш
не заменяет совпадение разметки, разрешение модуля и время жизни. Генератор
проверяет размеры WORD/указателя/big/real, NREG и смещения при компиляции C.
Экспериментальный `e.h` другой цели нельзя использовать как наш ABI.

`big` — точное знаковое 64-битное значение. Для wrap используйте unsigned и
публикуйте биты; знаковое переполнение C не реализует семантику Limbo. Типы
слотов — сгенерированные WORD/LONG/REAL. `memmove` снимает требования к
выравниванию упакованного доступа, но не проверяет произвольный поддельный
указатель. Доверенный кадр примера предоставляет сама VM.

## GC и возврат

Кадр и аргументы заимствуются только на время синхронного вызова. Управляемые
аргументы остаются корнями по карте. Ячейка результата принадлежит caller;
указатель на неё не является входным объектом GC. `String *` — не буфер UTF-8.
Адрес `malloc` или стека C не имеет Heap-префикса и не должен передаваться в
`D2H`, `destroy` или retain.

Используйте существующие проверенные helpers публикации. В примере `retstr`
создаёт строку Dis из литерала C, публикует её и освобождает прежнего владельца
ячейки. При выделениях с сохранением других VM-объектов нужны настоящие корни
и защищённая очистка частичного результата. Локальный C-указатель сам по себе
не дополнительный корень. Для массивов нужны правильный дескриптор/карта
элемента и проверка полной длины/данных, а не приведение указателя.

Приватное состояние C требует непрозрачного управляемого владельца, точного
дескриптора/finalizer, проверки каждого доступа и определённого завершения.
Число с адресом в ADT само по себе не становится capability. Более сложный
пример — hosted Bigtable; его lease/waiter-код не является общим публичным
API асинхронных модулей.

## Ошибки, блокировка, worker’ы

`error()` вызывается владельцем исполнения и разматывает состояние Dis.
C-ресурсы нужно защищать от обхода очистки при ошибке. Произвольный worker
не может вызывать VM error, allocator, каналы и GC. Учебный void-export
поднимает ошибку без захваченных ресурсов; Limbo-клиент её перехватывает.

Сейчас процессы Limbo планируются над одним native owner. Долгий нативный
диск/сеть может заблокировать этого владельца. Короткие операции оставляйте
в C, координацию — в Limbo. Для дорогого чистого вычисления копируйте
неизменяемый вход в задания с отдельными выходами, завершайте работу через
владельца, проверяйте ревизию/поколение и только затем публикуйте VM-результат.
Асинхронному export дополнительно нужны корни ожидающего вызова, отмена,
таймаут и очистка при исключении. `spawn` и pthread вокруг callback этого
не реализуют.

## UI и переносимость

Dis сохраняет прямое управление Flash-контентом через типизированные каналы.
Сложное представление можно собирать в AS. Колоризатор или рендер-helper на C
является расширением/сервисом, не вторым движком политики IDE. У каждого
AS-контекста/кучи есть владелец. Независимые снимки/области рендерятся параллельно
без конкурентного запуска одного изменяемого AVM1-контекста. Реализованные
границы и следующие шаги описаны в связанном контракте рендера.

Файлы, окна и потоки выносите в выбранные OS-порты; вычислительное ядро,
сообщения и владение буферами держите независимыми. C-модуль пересобирается для
каждого host ABI. Переносимость байткода Limbo/AS не делает машинную библиотеку
переносимой между ОС и архитектурами.
