# Общий Dis-хип: переход от одного владельца к объектным блокировкам

Статус: план реализации, а не включённый параллельный мутатор. В runtime0.59.0
два исполнителя ещё не могут одновременно исполнять произвольный код над хипом.
Пользователь предложил mutex для allocator и spinlock в GC-заголовке объекта.
Это подходящее направление; глобальное исключительное владение не является
обязательным свойством Dis или Limbo.

## Что означает нынешнее владение

NativeWorld выдаёт одному исполнителю право читать/изменять общий управляемый
хип на участок исполнения. Mutex защищает саму выдачу и публикацию состояния,
а не берётся заново на каждую инструкцию. Другие исполнители ждут допуска.
При проверенном native I/O владелец публикует корни, выходит из этого участка,
и другой исполнитель получает доступ к хипу. Поэтому native I/O, закрытие файлов
и Dis-код могут перекрываться, а произвольный Dis compute пока сериализован.
Отдельные Fast/Cycles потоки также пока получают остановленный мир для доступа
к управляемым объектам. Отдельный native closer к хипу не обращается вообще.

## Предлагаемая первая параллельная модель

- Allocator и списки/метаданные GC получают собственную синхронизацию.
- Heap-объект/контейнер получает атомарное слово блокировки; RC становится
  атомарным по всем путям изменения, включая Type и сгенерированный код.
- Все конфликтующие чтения и записи защищаются. Блокировки только для записи
  недостаточно, если другой поток читает те же неатомарные поля.
- Чисто локальные frame-регистры остаются у владельца Prog. Доступ отладчика
  идёт через опубликованное состояние/остановку; у каждой такой ячейки нет
  самостоятельного Heap-заголовка. Для interior/slice указателя используется
  владеющий объект, а не вычитание заголовка от произвольного адреса элемента.
- Сборка циклов в первой версии остаётся stop-the-world. Одновременно выполняется
  обычный код разных мутаторных потоков; GC ждёт их безопасных точек. Для самого
  полного обхода циклов мир остановлен. Если сохраняются инкрементальные порции
  с возобновлением между ними, Setmark/color/nprop и остальные маркирующие
  барьеры всё равно требуют согласования между мутаторными потоками. Назвать
  отдельную порцию STW недостаточно. Полностью конкурентный обход — следующий этап.

Блокировка в заголовке экономит отдельный объект mutex, но не делает время жизни
безопасным сама по себе. Нельзя сначала прочитать голый указатель, затем пытаться
захватить spinlock в объекте: объект могли уже освободить.

## Получение и изменение ссылки

Для получения ссылки из разделяемого контейнера:

1. Иметь собственную сильную ссылку на контейнер и захватить его блокировку.
2. Прочитать ячейку и увеличить RC целевого объекта, пока ссылка контейнера ещё
   защищена. Проверить переполнение/недопустимое состояние счётчика.
3. Отпустить контейнер. Теперь локальная сильная ссылка удерживает объект живым.
4. При необходимости захватить блокировку целевого объекта и работать с ним.
5. Отпустить блокировку, затем освободить локальную сильную ссылку.

Для обычного копирования ссылки новая цель уже удерживается локальной сильной
ссылкой. Перед публикацией приобретается ОТДЕЛЬНАЯ сильная ссылка для контейнера;
отказ по переполнению не меняет ячейку. Под блокировкой контейнера публикуется
эта новая ссылка с нужным порядком памяти; старую ссылку отпускаем после выхода
из блокировки. Локальная ссылка остаётся у вызывающего и освобождается отдельно
после последнего использования. Move — отдельная явно потребляющая операция:
она передаёт уже удерживаемую ссылку без второго retain и обнуляет локального
владельца; молча смешивать эти две семантики нельзя. Нельзя запускать каскадный
деструктор, произвольный callback или native ожидание внутри объектной блокировки.
Последнюю ссылку передаём очереди освобождения по отдельному протоколу;
объект не должен становиться доступным GC как свободный до завершения передачи.
Атомарный RC сам по себе не решает ни циклы, ни заимствование сырого указателя.

## Ожидание и безопасные точки

Короткий spin допустим для коротких критических участков. После ограниченного
числа попыток ожидающий поток паркуется. Возможна общая таблица native ожиданий
по адресу lock-word, чтобы не хранить тяжёлый OS mutex/condition в каждом объекте.
Проверка предиката и переход ко сну должны исключать потерю пробуждения.
Сильная ссылка удерживает объект/lock-word на всё время ожидания.

При двух одновременно нужных объектах нужны единый порядок блокировок либо
снимок с проверкой версии/повтором. Native I/O и safepoint не должны удерживать
объектные блокировки. Иначе GC может ждать поток, который ждёт блокировку у уже
остановленного потока. Все пути выхода по ошибке тоже освобождают свои блокировки.

## Что нужно изменить до снятия общего допуска

Интерпретатор, все JIT-архитектуры, прямые native/complete входы, каналы/alt,
перемещение ссылок, bulk-копирование, глобальные поля модулей, allocator/Type/RC,
корни и доступ отладчика должны использовать одинаковый протокол. Достаточно
одного старого прямого store, чтобы нарушить его. C-модулям потребуется API
удержания владельца и доступа; произвольный указатель не даёт разрешение на запись.
Неаудированные C-модули могут сначала сохранять исключительный fallback с
остановкой остальных мутаторных потоков, пока все их обращения не переведены
на новый протокол.

В текущем Heap есть color/ref/Type*/hprof; H2D/D2H используют sizeof(Heap).
Добавление lock-word меняет native layout и требует перестройки адаптеров/JIT
и проверки их смещений. Это не повод менять файловые Dis/Dis64 IDs. Фактический
Heap в этой серии не изменён; обновление owning upstream и интеграция должны
быть проверены отдельно, без ручной правки vendored snapshot.

## Уже сделанный шаг runtime0.59.0

Очередь отложенного RC теперь принимает последнюю ссылку от любого ACTIVE
исполнителя своего NativeWorld, а не только от исходного контроллера. Проверка
состояния идёт до чтения payload. IDLE/NATIVE/неподтверждённый reentry/другой мир/
collector не допускаются. Учёт helper_enqueued показывает реальные передачи.
Fast освобождает такие ссылки в своей остановке мира; рекурсивное освобождение
из collector обратно в очередь не попадает. При лимитах512 владельцев/4MiB
прямых блоков сохраняется inline fallback. Это не обещает ограниченного времени
для произвольно большого графа и не включает параллельные записи в хип.


## Шаг runtime0.60.0: типизированные атомарные примитивы

Добавлен disvm/refcount.h для unsigned-long и signed-int счётчиков с проверкой
нуля, переполнения и последнего освобождения. Подключены выбранные ручные host
retain/release; остальные C/JIT обращения ещё не переведены. Сам Heap-заголовок
не менялся, объектных блокировок и общего параллельного мутаторного режима пока
нет. [Точная граница конверсии](REFCOUNT-CONVERSION.md).


## Шаг runtime0.61.0: native object guards и границы контекста

Проверен отдельный native guard: ограниченный spin/CAS, парковка через общие
stripe mutex/condition, точный владелец TLS и отдельные результаты доступности
и захвата. Контекст с удерживаемым guard не может уйти в safepoint/native-переход,
освободить scheduler turn или отвязать TLS. Нативный пример реально изменяет
общий mutable C-объект из OS-потоков. Это не изменение Heap-заголовка: перенос
в managed-хип ещё требует всех ранее перечисленных правил, включая стабильный
адрес/GC-пины, полный C/JIT/marking и безопасное разворачивание по ошибке.
[Точный протокол и проверки](OBJECT-GUARDS.md).
