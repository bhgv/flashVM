# Гарантированная инициализация через ветви — компилятор 0.42

[English](JOIN_INITIALIZATION.md) · [Комментированный пример](../examples/tables/join-initialization.b) ·
[Операторы функции](FUNCTION_FLOW.ru.md) · [Удерживаемые ячейки](RETAINED_LOOPS.ru.md)

Профиль Limbo big/table с парсером Coco/R теперь принимает ранее объявленную
переменную, инициализированную на каждом продолжающемся пути условия. После
объединения читается её общая типизированная ячейка. Частичное присваивание
допустимо без последующего чтения, но не доказывает инициализацию.

```limbo
answer: big;
text: string;
selected: table of big;
count: int;
if (enabled) {
    answer = big 40;
    text = "ready";
    selected = table of big {extra=2};
    count = int 1;
} else {
    answer = big 21;
    text = "fallback";
    selected = table of big {extra=21};
    count = int 2;
}
return answer + selected.extra;
```

Здесь `enabled` — уже инициализированный bool. Поддерживаются четыре явных типа
объявления из примера. Новых ключевых слов объявления bool, последовательностей
и отдельных ключей нет; их прежние выведенные инициализированные переменные
сохраняются. Присваивание требует точного типа. Объявление затеняющей переменной
внутри ветви инициализирует только её, а не внешнее имя.

## Факты исходного языка и границы циклов

Перед условием компилятор резервирует типизированное хранение объявленных
переменных, не делая их готовыми к чтению. Для двух продолжающихся путей
инициализация — пересечение фактов обоих выходов. Возвращающая ветвь не участвует
в продолжающемся пути; единственный оставшийся путь сохраняет собственные факты.
Вложенные условия работают так же. Чтение исходной переменной отклоняется,
даже если её физический скалярный слот содержит ноль, а ссылочный — nil.

Первая инициализация внешней переменной в потенциально пустом цикле по-прежнему
отклоняется. Локальные переменные тела можно инициализировать внутренними
ветвями и читать в той же итерации. При выходе восстанавливаются входные факты
неинициализированности и идентификаторы ячеек: ячейка, созданная только в теле,
не становится внешним доминирующим определением. Это действует для while,
трёхчастного for и обхода снимка. Позднее обычное присваивание вне цикла допустимо
и не записывает значение в ячейку, созданную лишь внутри тела.

```limbo
for (index := int 0; index < int 2; index++) {
    local: string;
    if (index == int 0) {
        local = "first";
    } else {
        local = "second";
    }
    # Каждый нормальный путь записал строку до этого чтения.
    length := len local;
}
```

CLI и последовательный библиотечный API C99 используют одни факты. Объявления
и присваивания сохраняют идентичность имени и исходные отладочные позиции.
Прежние проверки полного возврата, областей и недостижимого кода сохранены.

## FIR ref.nil и независимое доказательство

В конец перечисления операций FIR добавлен один producer. Он резервирует
приватную ссылочную ячейку без выделения фиктивной пустой таблицы или строки:

```fir
%cell: string.cell = ref.nil
%text: string = const.string "42"
ref.store %cell, %text
%value: string = ref.load %cell
```

`ref.nil` принимает `string.cell`, `table.cell`, `keys.cell`, `key.cell`. При
повторном исполнении прежний владелец корректно освобождается; для ключа снимка
обнуляется и скалярная позиция. Неиспользуемую ячейку заполнять не обязательно.
До каждого чтения должна быть запись на всех нормальных путях. Nil-хранение
не считается инициализированным значением исходного языка. Скалярные big/bool
сохраняют прежний контракт начального нуля FIR; исходные факты проверяются
отдельно от физического значения слота.

Верификатор FIR доказывает инициализацию независимо от метаданных frontend:

1. Нумерует nil-ячейки SSA; приватные ячейки нельзя копировать и выводить наружу.
2. Начинает вход функции с пустых фактов, остальные блоки — с верхнего состояния.
3. Пересекает факты предшественников; `ref.nil` сбрасывает факт, `ref.store` задаёт.
4. Доходит до убывающей неподвижной точки, затем проверяет чтения в порядке
   инструкций каждого блока.

Учитываются обратные рёбра, возвращающие предшественники, повторные конструкторы
и сходящиеся записи. До обычной проверки/оптимизации не предполагается выбор
ветви только по виду константного условия. Ограниченные временные векторы C
освобождаются на всех выходах. Модули без `ref.nil` пропускают этот проход.
Ранее проверяются типы, число операндов, достижимость и доминирование.

Ручной FIR с чтением до записи, после записи только в одной ветви либо после
потенциально пустого записывающего цикла отклоняется с сообщением `reference
cell read before initialization`. Оптимизатор не публикует такой модуль и
сохраняет прежний выход вызывающей стороны. Инициализированный `ref.local`
сохраняет прежний контракт конструктора и не требует отдельного nil-факта.

## Владение NC64 и эталон

Backend Dis резервирует одно помеченное слово канонического nil в данных модуля,
только когда оно требуется. Загрузчик инициализирует его согласно карте указателей.
Существующий удерживающий MOVP копирует nil в помеченную ячейку кадра и корректно
освобождает прежнего владельца. Второе слово ключа остаётся скаляром без отметки.
Новых инструкций Dis, импортов нативных модулей, фиктивных объектов кучи и формата
SWF нет. Старые программы без нового конструктора сохраняют прежнюю раскладку.

Независимый эталон очищает приватную запись значения; доказательство FIR не даёт
прочитать её до записи. После корректного присваивания реестр одного запуска
удерживает обычные таблицы, ключи и текст. Нативная VM использует реальные корни
и счётчики ссылок. Тесты требуют нулевых счётчиков таблиц/ключей при завершении
в обоих режимах исполнения.

Исходное расширение и операция FIR остаются в FlashVM. Приватные ячейки кадра
не передают адреса наружу, не добавляют сетевой RPC и не меняют контракты
брокера, внешних проекций и блокировок каналов.

## Сборка и запуск

Из корня репозитория после сборки:

```sh
mkdir -p build/tmp
export TMPDIR="$PWD/build/tmp"
build/fir/fir1_source limbo --input fir/v1/examples/tables/join-initialization.b join.fir -g join.json
build/fir/fir1 opt join.fir join.opt.fir
build/fir/fir1_table_run join.opt.fir
build/fir/fir1 dis join.opt.fir join.dis
build/runtime/disvm --jit --quantum 1 --stats --inspect-words 0 4 join.dis
build/runtime/disvm --no-jit --quantum 2048 --stats --inspect-words 0 4 join.dis
```

Эталон печатает 42. VM показывает `42, 0, 1, 0`: два места return и флаги их
исполнения. Оба устанавливаемых SDK компилируют пример заново связанными
клиентами C99, оптимизируют/перечитывают FIR и запускают оба режима VM.

Тесты `fir1_join_initialization` и `disvm_join_initialization_{jit,interpreter}`
покрывают оба состояния FIR, два кванта, явные типы объявления, вложенность,
частичную инициализацию, затенение, возвращающие ветви, локальные ячейки тела
и факты выхода цикла. Независимые FIR-фикстуры проверяют все четыре ссылочных
типа, повторный nil-конструктор, оба исхода, возвращающих предшественников,
неверные типы и отклонение чтений через объединения/обратные рёбра. Прежние
регрессии скалярного нуля, удерживаемых ячеек, терминального дерева и восстановления
запросов C99 сохраняются.
