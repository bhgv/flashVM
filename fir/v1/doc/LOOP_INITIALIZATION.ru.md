# Первое присваивание внутри циклов — компилятор 0.43

[English](LOOP_INITIALIZATION.md) · [Комментированный пример](../examples/tables/loop-initialization.b) ·
[Инициализация через ветви](JOIN_INITIALIZATION.ru.md) · [Удерживаемые ячейки](RETAINED_LOOPS.ru.md)

Ранее объявленные переменные `big`, `int`, `string` и `table of big` теперь могут
получать первое значение в теле цикла. Следующее чтение на том же продолжающемся
пути допустимо. Это работает в `while`, обычном `for` и обходе `for in`.
Точное совпадение типов и правила затенения внешних имён сохраняются.

```limbo
text: string;
part: table of big;
total := big 0;
for (index := int 0; index < int 3; index++) {
    text = "14";
    part = table of big {value=big text};
    total += part.value;
}
# Здесь гарантированной инициализации text и part ещё нет.
text = string total;
return big text;
```

Пример возвращает 42 без предварительного создания фиктивных строки и таблицы.
CLI и последовательный библиотечный C99-компилятор используют прежнюю грамматику
Coco/R. Нового синтаксиса объявлений и самописного парсера нет.

## Ячейки и доказательство инициализации

Перед проверкой условия компилятор резервирует доминирующие типизированные ячейки
для всех поддерживаемых активных объявлений. Уже доступные значения сохраняются
обычным способом. Для ещё недоступных ссылок используется `ref.nil`, для скаляров
— прежние нулевые приватные ячейки. Ни nil, ни физический ноль не разрешают чтение
переменной в исходной программе. Присваивания в теле используют общую ячейку,
в том числе после вложенного условия или цикла.

Первое присваивание устанавливает факт инициализации только на текущем пути.
Перед чтением после условия обе продолжающиеся ветви должны записать значение;
ветвь с возвратом не участвует в пересечении. `continue` и `break` не превращают
пропущенную запись в гарантированную. Чтение собственной ещё недоступной переменной
справа от присваивания, составное обновление и чтение до доказанной записи на
следующей итерации по-прежнему запрещены.

На выходе восстанавливаются факты для переменных, не инициализированных при входе.
Даже явно непустой цикл или бесконечный цикл с `break` не доказывает инициализацию
в продолжении. Это консервативное правило не зависит от реального числа проходов.
Вложенные циклы работают так же: запись только во внутреннем теле не разрешает
чтение после внутреннего цикла. Запись перед ним остаётся действительной.

Локальные для тела ячейки создаются заново при каждом входе в тело. Внешняя ячейка
на обратном ребре не обнуляется: старый объект может физически удерживаться корнем,
но исходная программа не получает права прочитать его без доказательства для
текущего пути. Вывода фактов между итерациями нет. Новое обычное присваивание после
цикла безопасно использует ту же доминирующую ячейку.

## Порядок шага обычного for

Парсер разбирает шаг в заголовке раньше тела, хотя исполняется шаг после тела или
`continue`. Поэтому первое присваивание внешней ещё недоступной переменной в шаге
отвергается с сообщением `for step assignment requires an initialized local at
loop entry`. Иначе разбор заголовка ошибочно разрешил бы чтение в первом теле.

Инициализируйте переменную перед циклом либо перенесите первую запись в тело.
Эта версия не доказывает, что все пути к отложенному шагу инициализируют его
операнды. Чтения в шаге также проверяются по фактам, доступным при разборе заголовка.
Обновления уже инициализированных счётчиков и ссылок сохраняют прежнее поведение.

## FIR, DisVM и владение

Новых операций FIR, инструкций Dis, ABI кадра и публичных функций не требуется.
Независимый анализ FIR проверяет каждое `ref.load` после понижения и оптимизации.
Запись в потенциально пустом теле не разрешает чтение на выходе. Такой ошибочный
модуль FIR отвергается независимо от исходного компилятора.

NC64 использует прежний отображённый корень канонического nil и удерживающий MOVP.
Повторная запись удерживает новый объект и освобождает прежнего владельца ячейки;
SSA-корни сохраняют прежнее время жизни кадра. Эталонный исполнитель использует
существующий реестр владельцев одного вызова. Изменение не создаёт сетевых
возможностей, экспортированных адресов кадров и новых блокировок. Внешние
канальные проекции остаются отдельным интерфейсом.

Это расширение компилятора FlashVM. В компилятор Limbo из Inferno оно не переносится.
Выбранный снимок интерпретатора/JIT Inferno остаётся прежним.

## Запуск и проверки

Из корня репозитория после сборки:

```sh
mkdir -p build/tmp
export TMPDIR="$PWD/build/tmp"
build/fir/fir1_source limbo --input fir/v1/examples/tables/loop-initialization.b loop.fir -g loop.json
build/fir/fir1 opt loop.fir loop.opt.fir
build/fir/fir1_table_run loop.opt.fir
build/fir/fir1 dis loop.opt.fir loop.dis
build/runtime/disvm --jit --quantum 1 --stats --inspect-words 0 2 loop.dis
build/runtime/disvm --no-jit --quantum 2048 --stats --inspect-words 0 2 loop.dis
```

Эталон печатает `42`, DisVM выдаёт `DATA 0 42` и `DATA 8 1`.
`fir1_join_initialization` и два runtime-варианта проверяют все четыре типа,
оба кванта, исходный и оптимизированный FIR, вложенные и пропущенные циклы,
записи через ветви, continue/break, повторную инициализацию после цикла и запреты
чтения. Отрицательные случаи сохраняют прежние FIR/debug-файлы вызывающего кода.
Библиотечный C99-тест чередует успешные запросы с запрещённой первой записью
в шаге, синтаксической ошибкой и неполной инициализацией через ветви.
Оба установленных SDK компилируют пример через заново скомпонованные клиенты
и исполняют полученный модуль в обоих режимах VM.
