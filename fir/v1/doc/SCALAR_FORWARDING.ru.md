# Устранение загрузок приватных скаляров — компилятор 0.45

[English](SCALAR_FORWARDING.md) · [Комментированный пример](../examples/tables/scalar-forwarding.b) ·
[Реализация peephole](../optimiser/peephole.c) · [Эффекты](FORMAT.md) ·
[Удерживаемые ссылочные ячейки](RETAINED_LOOPS.ru.md)

Peephole-оптимизатор FIR теперь устраняет повторные `big.load` и `bool.load`
в пределах одного базового блока. Загрузка может использовать значение последней
записи в ту же приватную ячейку либо результат предыдущей загрузки, если известной
записи ещё нет. Она становится типизированной копией; обычное распространение
копий перенаправляет использования и удаляет копию. Конструкторы и записи
сохраняются как операции с памятью.

```fir
%text: string = const.string "42"
%value: i64 = value.big %text
%cell: i64.slot = big.local
big.store %cell, %value
%first: i64 = big.load %cell
%second: i64 = big.load %cell
%sum: i64 = big.add %first, %second
trace %sum
```

После оптимизации `%sum` дважды использует `%value`. Динамическое преобразование
и запись остаются, две загрузки исчезают. Правило работает с неконстантными
значениями, включая полные знаковые 64 бита, без промежуточного floating point.
Ячейка bool сохраняет именно тип bool. Исходный `int` по-прежнему хранится через
расширенное big-значение и прежнее сужение; новых преобразований языка нет.

## Почему правило допустимо для приватных ячеек

Верификатор запрещает копирование и экспорт скалярных дескрипторов ячеек. Каждый
дескриптор обозначает отдельное хранилище кадра функции; другая ячейка не может
оказаться его алиасом. Внутри блока сохранённое SSA-значение скаляра остаётся тем
же до следующей записи в эту ячейку. Оптимизация не пересекает рёбра CFG и циклов.

Проход ведёт ограниченную карту «идентификатор ячейки → доступное SSA-значение»:

- На границе блока все факты забываются.
- Конструктор оставляет новую ячейку неизвестной. Нулевая инициализация сохраняется;
  новый факт инициализации исходного языка или литерал не выдумывается.
- Скалярная запись заменяет факт только своей ячейки. Записи в другие приватные
  скалярные ячейки друг другу не мешают.
- Первая неизвестная загрузка остаётся в FIR и запоминается. Следующая загрузка
  известной ячейки становится копией.
- Остальные операции с `FIR_WRITES_MEMORY` или `FIR_MAY_SUSPEND` очищают карту.
  Неизвестные эффекты получают прежнюю консервативную маску.

Trace, канальные операции, изменение таблиц и удержания присваивания служат
барьерами именно для нового локального правила. Операции только чтения не меняют
приватную скалярную ячейку. Прежнее отдельное правило единственной доминирующей
записи *литерала* сохраняется и может устранять загрузки через блоки/барьеры по
своему более узкому доказательству для всей функции. Локальная политика барьеров
не отключает существующее доказательство константной записи.

Подставляемое значение доминирует над исходной загрузкой и её использованиями.
Верификация выполняется до и после полного оптимизатора до неподвижной точки.
Следующие итерации могут свернуть открывшиеся арифметику и ветви по прежним
правилам достижимости и эффектов. Проход не выделяет объекты VM, не синхронизирует
потоки и не сохраняет состояние между запросами API.

## Границы и владение

Ссылочные ячейки, элементы таблиц, срезы и внешние канальные проекции не участвуют
в подстановке. `ref.load` продолжает создавать отдельный удерживаемый корень
значения; `ref.store` и удерживающая публикация MOVP не меняются. Проход не удаляет
операцию счётчика ссылок и не принимает общую таблицу за приватный скаляр.
Атомарности удалённому read-modify-write он не добавляет.

Факты не переносятся из предшественника в соединение, через заголовок цикла или
из тела в следующую итерацию. Исходная проверка инициализации и независимый анализ
nil-ячеек FIR по-прежнему обязательны до оптимизации. Новых операций FIR, синтаксиса,
инструкций Dis, публичных API и нативного ABI нет. Парсеры остаются на Coco/R.

FIRDBG1 описывает исходные неоптимизированные SSA-идентификаторы. Проход не обещает
переназначить удалённые позиции значений на окончательные нативные PC; оставшиеся
инструкции сохраняют прежние заметки строк входа. Канонический FIR можно снова
разобрать и оптимизировать без дальнейших семантических изменений.

## Пример и проверки

Из корня репозитория после сборки:

```sh
mkdir -p build/tmp
export TMPDIR="$PWD/build/tmp"
build/fir/fir1_source limbo --input fir/v1/examples/tables/scalar-forwarding.b scalar.fir
build/fir/fir1 opt scalar.fir scalar.opt.fir
build/fir/fir1_table_run scalar.opt.fir
build/fir/fir1 dis scalar.opt.fir scalar.dis
build/runtime/disvm --jit --quantum 1 --stats --inspect-words 0 2 scalar.dis
build/runtime/disvm --no-jit --quantum 2048 --stats --inspect-words 0 2 scalar.dis
```

Результат — 42; нативные захваты: `DATA 0 42`, `DATA 8 1`. Повторные чтения
аккумулятора исчезают в теле, а загрузки заголовка/выхода и записи сохраняют
семантику итераций. Оба установленных SDK компилируют пример через заново
скомпонованные C99-клиенты, оптимизируют FIR и запускают оба режима VM.

`fir1_scalar_forwarding` и `disvm_scalar_forwarding_{jit,interpreter}` сравнивают
исполнение исходного и оптимизированного кода, точное число оставшихся загрузок
и повторную оптимизацию. Случаи FIR охватывают нулевые big/bool, неконстантные
записи, перезапись, разные ячейки, true/false, переполнение INT64_MIN, соединения,
обратные рёбра, барьеры trace/изменения таблицы/удержания и ссылочные загрузки.
Нативные случаи используют кванты 1 и 2048 и требуют отсутствия живых владельцев
таблиц/ключей после исполнения. Пример исходного языка также требует строгого
уменьшения числа скалярных загрузок.

[Версия 0.46](SCALAR_STORES.ru.md) добавляет отдельный проход удаления перезаписанных скалярных записей. Сама подстановка загрузок записи не удаляет; весь оптимизатор теперь может удалять доказанно ненаблюдаемые промежуточные записи.
