# Типизированные циклы и обход неизменяемых значений — компилятор 0.39

[English](TYPED_LOOPS.md) · [Подробно комментированный пример](../examples/tables/typed-loops.b) ·
[Трёхчастный for](COUNTED_FOR.ru.md) · [Переходы в циклах](LOOP_CONTROL.ru.md)

Профиль Limbo big/table с парсером Coco/R теперь переносит инициализированные
локальные `int` и выведенные `bool` через обратные переходы циклов и объединения
ветвей loop-if. Консольный компилятор и библиотека C99 используют один код.
Тип переменной сохраняется: int присваивается только int, bool — только bool.
Арифметика int/big требует явного приведения.

```limbo
running := 1 == 1;
counter := int 0;
while (running) {
    counter++;
    if (counter == int 3) {
        running = 1 == 0;
    }
}
```

Постфиксные `int ++/--`, как и big-вариант, допустимы отдельным оператором.
Переполнение происходит по модулю 2^32: после INT_MAX получается INT_MIN.
Знакового переполнения C при компиляции нет. Обновление bool через ++/--
запрещено. Bool выводится из сравнения или логической операции; новых литералов
и ключевого слова объявления bool этот профиль не вводит. По существующему
контракту отражения Limbo `typeof` называет нормализованный bool типом `"int"`.

## Хранение и слияние ветвей

Перед условием цикла или структурированным loop-if активные инициализированные
скаляры переводятся в доминирующие приватные ячейки FIR. Для big используются
`big.local/load/store`, для bool — `bool.local/load/store`. Int хранится в
существующей big-ячейке: при записи знаково расширяется, при чтении сужается по
модулю 2^32. Это внутреннее представление: `typeof`, операции и отладочные
значения чтения продолжают видеть int. Новых публичных типов/операций FIR,
инструкций Dis и импортов нативных модулей нет. Ячейка не выходит из функции
и не является блокировкой внешнего прокси.

Вложенный цикл использует уже доминирующую ячейку. Перед компиляцией соседней
терминальной ветви восстанавливаются исходные идентификаторы ячеек. Локальный
скаляр тела может получить ячейку внутри итерации; его инициализатор по-прежнему
исполняется при каждом входе. Присваивание в потенциально пустом цикле не делает
внешнее неинициализированное объявление гарантированно инициализированным.
В [компиляторе 0.40](RETAINED_LOOPS.ru.md) добавлены удерживаемые ячейки
строк/таблиц/снимков/ключей для переназначений через слияния.

## Типы и время жизни for-in

Выражение-получатель и длина неизменяемой последовательности вычисляются один раз перед обходом. Два имени локальны для
тела, должны различаться и могут затенять внешние имена. Continue продвигает
курсор ровно один раз; break и return пропускают шаг.

| Получатель | Первое имя | Второе имя | Что читается |
| --- | --- | --- | --- |
| `table of big` | capability ключа снимка | big | Снимок ключей, живое проверяемое значение |
| `string` | int индекс руны | int Unicode-скаляр | Захваченная неизменяемая строка |
| `keysof table` или переменная снимка | big позиция | capability ключа | Захваченный неизменяемый снимок |

Индексы строки начинаются с нуля и считают Unicode-скаляры, а не UTF-8-байты.
Символ вне BMP занимает одну итерацию. Строку удерживают обычные корни VM.
Индекс и значение руны имеют тип int.

```limbo
for (index, rune in "A😀Я") {
    # index = 0, 1, 2; rune = U+0041, U+1F600, U+042F.
}
keys := keysof values;
for (position, key in keys) {
    delete values[key]; # Удаление записи не разрушает независимый снимок ключей.
}
```

Capability ключа сохраняет числовое или строковое пространство: `values[key]`
обращается к исходному ключу. `typeof key` сообщает динамический тип ключа.
Обход самого снимка не читает значения таблицы. Прямой обход таблицы читает
живое значение до входа в тело; удаление будущего ключа может вызвать ошибку
отсутствующего ключа. Пустая строка или снимок не исполняют тело.

## Запуск и проверки

Из корня репозитория после сборки:

```sh
mkdir -p build/tmp
export TMPDIR="$PWD/build/tmp"
build/fir/fir1_source limbo --input fir/v1/examples/tables/typed-loops.b typed.fir -g typed.json
build/fir/fir1 opt typed.fir typed.opt.fir
build/fir/fir1_table_run typed.opt.fir
build/fir/fir1 dis typed.opt.fir typed.dis
build/runtime/disvm --jit --quantum 1 --stats --inspect-words 0 4 typed.dis
build/runtime/disvm --no-jit --quantum 2048 --stats --inspect-words 0 4 typed.dis
```

Эталон возвращает 42. VM показывает `42, 0, 1, 0`: два места результата и флаги
их исполнения. Счётчики владельцев таблиц/ключей в конце равны нулю. Пример
объясняет все операции; оба устанавливаемых SDK компилируют его через заново
связанный клиент C99.

Тесты `fir1_typed_loops` и `disvm_typed_loops_{jit,interpreter}` проверяют FIR до
и после оптимизации, два кванта планировщика, переполнение int, выход по bool,
вложенность и области видимости, соседние терминальные ветви, Unicode и пустые
строки, вложенные обходы, удержание ключей, typeof, отладочные идентификаторы и
отказ при несовместимых/неинициализированных присваиваниях. Тест C99 API чередует
корректный типизированный обход с синтаксической и семантической ошибками в
отложенном шаге for, проверяя изоляцию запросов компилятора.

Расширение остаётся в FlashVM и не переносится в Inferno. Общие переназначения
ссылок, произвольные массивы/кортежи, полный frontend Limbo и окончательная
релокация SBL из исходника в Dis остаются отдельной работой.
