# Overwritten private scalar stores — compiler 0.46

[Русский](SCALAR_STORES.ru.md) · [Commented tutorial](../examples/tables/scalar-stores.b) ·
[Scalar load forwarding](SCALAR_FORWARDING.md) · [Effects](FORMAT.md) ·
[Retained owners](RETAINED_LOOPS.md)

FIR now removes a private `big.store` or `bool.store` when a later store to the
same cell replaces it in the same basic block before an observation boundary.
The last store is retained so successors, loop iterations and normal exits see
the correct cell state. Scalar constructors are retained as well.

```fir
%text: string = const.string "42"
%value: i64 = value.big %text
%old: i64 = const.i64 1
%cell: i64.slot = big.local
big.store %cell, %old
big.store %cell, %value
%answer: i64 = big.load %cell
trace %answer
```

The first store disappears; the final store and the independently effectful
conversion remain. The existing load-forwarding pass can replace the final load
with `%value`. Normal scalar copy propagation and pure DCE can then remove dead
payload calculations, but not dynamic effects.

## Proof and ordering

The module is verified before optimization. Private scalar cell handles cannot
alias, be copied or escape the frame. Each pass walks backward within one block,
tracking whether a later unobserved write exists for each exact cell:

- A store with an already tracked later write is removed. Otherwise it stays as
  the final write. Either case establishes the later-write fact for earlier code.
- A remaining scalar load ends the fact for its cell. A constructor likewise
  ends only its new cell's fact; writes to distinct scalar cells are independent.
- Any other memory write, possible suspension or possible exception clears all
  facts. Unknown effects keep the existing conservative mask.
- Every block boundary clears all facts. No write is removed by a guess about
  successor branches, loop trip counts or another iteration.

Load forwarding runs first. A captured scalar read may already be an SSA copy
of the earlier store's payload, so deleting that overwritten store does not
change the captured value. In the tutorial, `saved` keeps the first intermediate
accumulator value even after later assignments. This is value capture, not an
alias to the private cell.

A may-throw operation is deliberately a stronger barrier here than in local load
forwarding. A write before a divide, allocation or retained-reference operation
is not removed across that operation merely because another write follows on
the normal path. Tests retain the prior store and the actual zero-divide error,
even when the quotient is unused. If an existing pure constant fold later proves
an operation total, the next fixed-point iteration may use its narrower effects.

The map is bounded compiler-local storage with no VM allocation, blocking or
state retained between API calls. After all fixed-point passes, independent FIR
verification runs again. Reparse/reoptimization keeps the resulting instruction
sequence stable, apart from ordinary serialized input-line notes.

## Ownership and concurrency boundaries

`ref.store`, `ref.local`, `ref.nil` and `ref.load` retain their existing owner and
initialization contracts. No retaining MOVP, frame root or reference count update
is removed by this rule. Reference operations are barriers, not candidates.
Table stores, assignment leases and channel/trace operations also stop the proof.

Shared tables, network proxies and externally projected variables are not
private scalar cells. This optimization neither removes their writes nor makes
a remote compound update atomic. Source definite-initialization checks and the
independent nil-cell analysis remain in force before optimization. FIRDBG1 still
describes unoptimized SSA origins; no native-PC remapping is added here.

The source parser remains generated by Coco/R. There is no new FIR opcode,
Limbo/AS syntax, Dis instruction, public C99 API or native ABI. This optimizer
extension remains FlashVM-only, separate from synchronized Inferno stack fixes.

## Run and validation

From the repository root after building:

```sh
mkdir -p build/tmp
export TMPDIR="$PWD/build/tmp"
build/fir/fir1_source limbo --input fir/v1/examples/tables/scalar-stores.b stores.fir
build/fir/fir1 opt stores.fir stores.opt.fir
build/fir/fir1_table_run stores.opt.fir
build/fir/fir1 dis stores.opt.fir stores.dis
build/runtime/disvm --jit --quantum 1 --stats --inspect-words 0 2 stores.dis
build/runtime/disvm --no-jit --quantum 2048 --stats --inspect-words 0 2 stores.dis
```

The reference prints `42`; native captures are `DATA 0 42`, `DATA 8 1`.
This tutorial reduces scalar stores from 7 to 4 and scalar loads from 8 to 4.
The source regression requires strictly fewer scalar stores, with the same result
before and after optimization. Both installed SDKs compile through freshly
linked C99 clients and execute the generated module in both VM modes.

`fir1_scalar_stores` and `disvm_scalar_stores_{jit,interpreter}` check exact
remaining big/bool/reference stores, repeated overwrite chains, captured reads,
distinct cells, zero initialization, branch boundaries, trace/table/lease and
may-throw barriers, retained owners and a discarded payload's dynamic conversion.
A separate original/optimized failure case must retain both stores around an
unused division by zero and preserve its `zero divide` identity. Successful
native cases use quanta 1 and 2048 and require zero live table/key owners.
Existing loop, all-path initialization and scalar-forwarding suites continue to
exercise backedges and reference lifetimes through the composed optimizer.
