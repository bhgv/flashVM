# Порядок Unicode-строк и проверяемые int-cast — компилятор 0.30

[English](TEXT_VALUES.md) · [Комментированный пример](../examples/tables/text-values.b) ·
[README примеров](../examples/tables/README.ru.md) · [Строки](TEXT_BITS.ru.md) ·
[Сравнения](COMPARISON_VALUES.ru.md) · [Int-арифметика](INT_ARITHMETIC.ru.md)

Coco/R big/table-профиль Limbo поддерживает все шесть сравнений однотипных строк
и явное преобразование строки либо отдельного ключа неизменяемого снимка в int:

```limbo
ordered := "file10" < "file2";
line := int digits;
key_number := int keys[0];
valid := ordered && (line == key_number);
```

## Контракт порядка

`<`, `>`, `<=`, `>=`, `==`, `!=` возвращают bool. Операнды вычисляются один раз,
слева направо, в том числе для отношений, реализованных перестановкой операндов
или отрицанием нормализованного результата. Более короткий равный префикс идёт
раньше. Пустые строки сравниваются обычным образом. Смешение строки с числом,
таблицей или bool остаётся статической ошибкой.

Сравниваются Unicode-скаляры, как в stringcmp/BLTC Inferno. Локали, нормализации,
изменения регистра, UTF-16-порядка и естественной числовой сортировки нет:
`"file10" < "file2"`, `"A" < "a"`, `"é" != "é"`. U+E000 идёт раньше U+1F600,
хотя порядок кодовых единиц UTF-16 обратный. Поддержаны конкатенации, алиасы,
отражённые имена типов и полуоткрытые срезы. Отдельные однородный int-профиль
и числовые AS-профили не расширяются.

## Контракт преобразования в int

Для строки или текстового ключа `int` составляет прежнее проверяемое
преобразование `big` и сужение до signed32 по модулю 2^32. Разбирается полная
непустая последовательность десятичных ASCII-цифр с необязательным знаком +/-
и ведущими нулями. Сначала число должно помещаться в signed64. Пробелы, суффиксы,
не-ASCII цифры, дроби, пустая строка, один знак и переполнение big вызывают
`invalid big conversion`.

| Текст | Результат int |
| --- | --- |
| `"+00042"` | 42 |
| `"2147483648"` | -2147483648 |
| `"4294967295"` | -1 |
| `"4294967296"` | 0 |
| `"9223372036854775808"` | ошибка до сужения |

Числовой ключ снимка предоставляет сохранённый точный big, текстовый — свою
копию текста. Cast не меняет вид ключа и не читает заново изменяемую таблицу:
снимок остаётся пригодным после удаления исходного ключа. Прежние преобразования
int/big/bool сохранены. Таблицу или всю коллекцию ключей нельзя преобразовать
целиком — сначала нужно выбрать отдельный ключ.

Это строгий проверяемый контракт нашего ограниченного профиля, а не замена
нативной семантики CVTCW/strtol Inferno и не обещание полной совместимости всех
лексических cast Limbo. Операции VM и ABI не меняются. Ошибочный разбор вызывает
исключение даже при неиспользуемом результате и после оптимизации. Действительно
невыбранная ленивая или терминальная ветка не выполняет своё преобразование.

## FIR, оптимизатор и владение

В конец enum дописана операция `string.lt`: string/string → bool, эффект
READS_MEMORY. Равенство использует прежнюю string.eq. Остальные отношения
понижаются перестановкой/отрицанием без повторного вычисления выражений.
Константный порядок сворачивается через порядок unsigned-байтов корректного
UTF-8, совпадающий с порядком скаляров. Динамическое сравнение использует BLTC
и корни кадра; готовые ядра AMD64/ARM64 и C fallback остаются основой исполнения.
Новых opcode, ABI помощников или представлений контейнеров нет.

Эталонный исполнитель сравнивает общий участок memcmp, затем длины. Завершающий
NUL у среза не предполагается. Cast строки/ключа в int порождает value.big и
value.int. Сигнатура value.int в FIR остаётся int/big/bool → int: подделанный
прямой строковый операнд отвергается текстовым и C99-верификатором. Консервативные
эффекты разбора сохраняют ошибку после удаления неиспользуемого сужения. Обе
операции cast имеют точную позицию исходного токена int в отладочном JSON,
в том числе после Unicode-префикса.

Живые новые выражения требуют эталонного исполнителя или hosted Dis; SWF
отвергает неподдержанное до замены выходного файла. Это подготовка исходных
сервисов IDE; панели Build/Run/Debug и подключение отладчика остаются отдельными
работами. Расширение остаётся только в FlashVM.

## Запуск и ожидаемый результат

Из корня репозитория после сборки FIR и runtime:

```sh
mkdir -p build/tmp
export TMPDIR="$PWD/build/tmp"
build/fir/fir1_source limbo --input fir/v1/examples/tables/text-values.b build/values.fir -g build/values.json
build/fir/fir1 check build/values.fir
build/fir/fir1 opt build/values.fir build/values-opt.fir
build/fir/fir1 dis build/values-opt.fir build/values.dis
build/runtime/disvm --jit --quantum 1 --inspect-words 0 4 build/values.dis
build/runtime/disvm --no-jit --quantum 1 --inspect-words 0 4 build/values.dis
```

Значения trace: 42, 0; флаги исполнения: 1, 0. Приёмка установленного SDK заново
линкует C99-клиенты source/FIR и проверяет исходный/оптимизированный пример
в обоих режимах VM. Ядра ARM64 проверяются эмуляцией инструкций; приёмка на
физическом ARM64 остаётся отдельной работой.
