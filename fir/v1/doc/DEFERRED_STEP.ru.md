# Инициализация в отложенном шаге for — компилятор 0.44

[English](DEFERRED_STEP.md) · [Комментированный пример](../examples/tables/deferred-step.b) ·
[Записи в теле цикла](LOOP_INITIALIZATION.ru.md) · [Инициализация через ветви](JOIN_INITIALIZATION.ru.md)

Заголовок обычного for разбирается раньше тела, но шаг исполняется после тела
или `continue`. Компилятор профиля Limbo big/table с парсером Coco/R теперь
проверяет инициализацию в порядке исполнения. В шаге можно читать переменную,
впервые записанную на каждом пути тела, который действительно доходит до шага.

```limbo
part: table of big;
text: string;
total := big 0;
for (index := int 0; index < int 3; total += part.value + big text) {
    index++;
    if (index == int 2) {
        part = table of big {value=7};
        text = "7";
        continue;
    }
    part = table of big {value=7};
    text = "7";
}
return total;
```

Результат — 42. Оба операнда шага записаны как перед `continue`, так и перед
обычным выходом из тела. Путь с `continue`, пропускающий хотя бы одну запись,
отвергается: значение с будущей итерации не считается доказательством.
Правило охватывает `big`, `int`, `string`, `table of big`, составные обновления
и типизированные получатели операций в шаге. Ранее инициализированные bool,
ключи и последовательности ключей сохраняют обычное поведение; новых явных
типов объявления исходного языка нет.

## Доказательство в порядке исполнения

1. Вход в цикл резервирует прежние типизированные ячейки активных объявлений.
2. Перед разбором шага сохраняется входное окружение. Чтение объявленной, но ещё
   недоступной ячейки записывает обязательство и исходную позицию; типизированная
   загрузка попадает в приватный отложенный поток FIR.
3. Перед телом восстанавливается сохранённое окружение. Запись в шаге не может
   заранее инициализировать первое тело или условие.
4. Каждый continue именно этого обычного for пересекает свои факты с фактами
   входа в шаг. Continue вложенного while/for-in или другого обычного for
   относится только к своей цели.
5. Если обычный выход тела открыт, его факты тоже участвуют в пересечении.
   Каждое отложенное чтение требует факта в этом пересечении. Пути break и return
   не доходят до шага и в доказательстве не участвуют.
6. Шаг и его debug-записи публикуются лишь после успешного доказательства.
   Если ни один путь к шагу не ведёт, они удаляются без требования инициализации.

Каждый вложенный обычный цикл имеет отдельный ограниченный контекст. Повторное
использование освобождённого контекста очищает обязательства и входные факты.
Ошибка освобождает потоки и debug-состояние; следующий C99-запрос начинает работу
с чистыми контекстами. Это учёт компилятора, без выделения объектов VM, блокировки
или сетевого ожидания.

Первое присваивание в самом шаге теперь допустимо, если правая часть корректна,
но оно не устанавливает факты для тела и продолжения после цикла. Чтения тела
доказываются его входными фактами и предшествующими операторами. Неизвестные имена,
несовпадение типов и объявления в шаге остаются ошибками даже для недостижимого
шага. Чтение объявленной, но недоступной переменной в недостижимом шаге не требует
доказательства: его загрузка и debug-запись в результат не попадут.

## Отказы и исходные позиции

Следующий код ошибочен:

```limbo
text: string;
for (index := int 0; index < int 2; text = text+"x") {
    index++;
    if (index == int 1) {
        continue; # Значение для первого шага не записано.
    }
    text = "ready";
}
return big 42;
```

Диагностика: `for step read requires initialization on every incoming path`.
Она указывает на чтение `text` в заголовке, а не на закрывающую скобку тела.
Последовательный C99 API возвращает исходное байтовое смещение UTF-8 и длину
токена. Ошибка сохраняет прежние FIR и FIRDBG1 вызывающего кода. При нескольких
недоказанных операндах сообщается одно обязательство; порядок переменных не
обязан совпадать с текстовым порядком всех чтений.

Число итераций статически не доказывается. Даже буквально ложное условие не
удаляет структурно достижимый шаг до исходной проверки. Запись только во
вложенном теле также не инициализирует переменную после внутреннего цикла.
Факты продолжения остаются консервативными, как описано в руководстве 0.43.

## FIR и DisVM

Отложенные загрузки обращаются к доминирующим приватным ячейкам, а не к SSA-значению,
существующему лишь в теле. Прежний независимый анализ `ref.nil` в FIR проверяет
ссылочные чтения в полученных соединениях и обратных рёбрах до исполнения и
оптимизации. Скалярные ячейки сохраняют контракт нулевого хранения, но исходная
проверка не принимает этот ноль за доказанное значение переменной. Новых операций
FIR, инструкций Dis, сигнатур нативных модулей и публичных C99 API нет.

NC64 использует удерживающий MOVP и отображённые корни строк/таблиц. Эталонный
исполнитель сохраняет прежний реестр владельцев одного вызова. Тесты сравнивают
исходный и оптимизированный FIR и требуют отсутствия живых владельцев таблиц/ключей
после JIT и интерпретатора. Внешние канальные проекции не раскрывают эти ячейки.
Расширение языка остаётся только во FlashVM, отдельно от импорта исправлений
интерпретатора/JIT Inferno.

## Сборка, запуск и проверки

Из корня репозитория после сборки:

```sh
mkdir -p build/tmp
export TMPDIR="$PWD/build/tmp"
build/fir/fir1_source limbo --input fir/v1/examples/tables/deferred-step.b step.fir -g step.json
build/fir/fir1 opt step.fir step.opt.fir
build/fir/fir1_table_run step.opt.fir
build/fir/fir1 dis step.opt.fir step.dis
build/runtime/disvm --jit --quantum 1 --stats --inspect-words 0 2 step.dis
build/runtime/disvm --no-jit --quantum 2048 --stats --inspect-words 0 2 step.dis
```

Эталон печатает `42`; нативные захваты — `DATA 0 42`, `DATA 8 1`.
Регрессии проверяют четыре явных типа, пересечения ветвей и continue, вложенные
контексты, получателей изменений таблиц, недостижимые шаги, первые записи только
в шаге и запреты чтений в теле/после цикла. Правильные случаи исполняются до и
после оптимизации с квантами 1 и 2048 в обоих режимах VM. C99-тест чередует успехи
с отказом отложенного доказательства и проверяет точный токен диагностики и
сохранность прежних файлов. Оба установленных SDK заново собирают клиентов и
исполняют пример независимо от дерева исходников.
