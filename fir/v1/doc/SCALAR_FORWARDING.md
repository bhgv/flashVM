# Private scalar load forwarding — compiler 0.45

[Русский](SCALAR_FORWARDING.ru.md) · [Commented tutorial](../examples/tables/scalar-forwarding.b) ·
[Peephole implementation](../optimiser/peephole.c) · [Effects](FORMAT.md) ·
[Retained reference cells](RETAINED_LOOPS.md)

The FIR peephole optimizer now forwards `big.load` and `bool.load` inside a
single basic block. A load can reuse the payload of the latest store to that
same private cell, or the result of an earlier load when no known payload is
available. It becomes an ordinary typed copy; existing copy propagation then
redirects uses and removes the copy. Constructors and stores remain observable
memory operations and are retained.

```fir
%text: string = const.string "42"
%value: i64 = value.big %text
%cell: i64.slot = big.local
big.store %cell, %value
%first: i64 = big.load %cell
%second: i64 = big.load %cell
%sum: i64 = big.add %first, %second
trace %sum
```

After optimization, `%sum` uses `%value` twice. The dynamic conversion and store
remain; the two loads disappear. This works for nonconstant payloads, including
full signed 64-bit values, without converting through floating point. Bool cells
retain their exact bool payload type. Source `int` cells still use the existing
widened-big storage and narrowing operations; no new source conversion is added.

## Why this is safe for private cells

The verifier forbids copying or exporting scalar cell handles. Each handle names
its own function-frame storage; another cell cannot alias it. Within one block,
a previously stored scalar SSA payload retains the same value until the next
write to that cell. No backedge or other CFG edge is crossed by this rule.

The pass maintains a bounded map from cell IDs to available payload SSA IDs:

- At each block boundary, forget every fact.
- A scalar constructor leaves its new cell unknown. Zero initialization is
  preserved; the pass does not invent a source initialization fact or literal.
- A scalar store replaces only its exact cell's fact. Stores to distinct private
  scalar cells do not invalidate each other's facts.
- A first unknown load stays in FIR and establishes a reusable result. A later
  load of the known cell becomes a copy.
- Other operations marked `FIR_WRITES_MEMORY` or `FIR_MAY_SUSPEND` clear the map.
  Unknown effects receive the conservative existing effect mask.

Trace/channel operations, table mutation and assignment leases therefore form
barriers for this new local rule. Read-only operations do not alter a private
scalar cell. The existing separate rule for a unique dominating *literal* store
remains valid and may fold loads across blocks/barriers under its narrower
whole-function contract. Do not interpret the local barrier policy as disabling
that pre-existing constant-store proof.

Each replacement value dominates its original load, and therefore its uses.
Verification runs before and after the complete fixed-point optimizer. A later
iteration can fold arithmetic or branches exposed by forwarding, but it still
uses the ordinary CFG reachability and effect rules. The pass allocates no VM
objects, performs no synchronization and keeps no state between API calls.

## Boundaries and ownership

Reference cells, table elements, slices and external broker/channel projections
are not forwarded. In particular, `ref.load` continues to create its independent
retained payload root; `ref.store` and retaining MOVP publication are unchanged.
This pass neither drops a reference count operation nor treats a shared table as
private scalar storage. It does not make a remote read-modify-write atomic.

Facts do not flow from a predecessor into a join, through a loop header, or from
a body back to a later iteration. The existing source definite-initialization
checks and independent FIR nil-cell analysis remain required before optimization.
This release adds no FIR operation, parser syntax, Dis opcode, public API or
native ABI. Source parsers remain generated by Coco/R.

FIRDBG1 describes unoptimized SSA identities. This optimization does not claim
to remap removed value sites into final native PCs; retained instructions keep
their existing input-line notes. Published canonical FIR can be reparsed and
optimized again without further semantic changes.

## Tutorial and verification

From the repository root after building:

```sh
mkdir -p build/tmp
export TMPDIR="$PWD/build/tmp"
build/fir/fir1_source limbo --input fir/v1/examples/tables/scalar-forwarding.b scalar.fir
build/fir/fir1 opt scalar.fir scalar.opt.fir
build/fir/fir1_table_run scalar.opt.fir
build/fir/fir1 dis scalar.opt.fir scalar.dis
build/runtime/disvm --jit --quantum 1 --stats --inspect-words 0 2 scalar.dis
build/runtime/disvm --no-jit --quantum 2048 --stats --inspect-words 0 2 scalar.dis
```

The tutorial returns 42; native captures are `DATA 0 42`, `DATA 8 1`. Its repeated
accumulator reads disappear inside the body, while loop header/exit loads and
stores preserve iteration semantics. Both installed SDK paths compile it with
newly linked C99 clients, optimize FIR and run the resulting module in both modes.

`fir1_scalar_forwarding` and `disvm_scalar_forwarding_{jit,interpreter}` compare
original and optimized execution, exact remaining load counts and a second
optimization. Raw cases cover zero-initialized big/bool, nonconstant stores,
overwrite ordering, distinct cells, true/false bool, INT64_MIN wrap, CFG joins,
loop backedges, trace/table-write/lease barriers and retained-reference loads.
Native cases use quanta 1 and 2048 and require table/key owners to return to zero.
The source tutorial also requires a strict reduction in scalar load count.
