# Точные сравнения big и терминальные решения исходного Limbo — FIR 0.18

[English](BIG_DECISIONS.md) · [Комментированный Limbo](../examples/dis/big-decisions.b) ·
[Основа CFG](BIG_CFG.ru.md) · [Цель Dis](DIS_BACKEND.ru.md)

Наш Coco/R-профиль Limbo с результатом big принимает терминальное дерево решений
после обычного пролога объявлений/присваиваний. Каждая ветвь — `return expr;` либо
вложенный `if (left relation right) { result } else { result }`. Все шесть
отношений `<`, `==`, `>`, `!=`, `<=`, `>=` требуют два точных big-операнда.
Нет преобразования через binary64 и сужения до i32. Bool пока внутренний тип
условий: объявления bool, неявная истинность, сравнения смешанных типов и
bool-элементы таблиц здесь не добавляются.

Операции FIR `big.lt.signed` и `big.eq` добавлены в конец enum, старые ID сохранены.
Обе принимают i64/i64 и возвращают bool. Остальные отношения исходника используют
перестановку операндов и/или инверсию рёбер, не вычисляя выражения повторно.
Операнды вычисляются слева направо в исходном порядке. Событие сравнения указывает
на точные байты написанного оператора, включая корректные смещения после UTF-8
комментариев; событие ветвления — на `if`.

## Прямой код и оптимизация

Скалярный backend материализует bool существующими BLTL (130), BEQL (134), MOVW
и JMP, с переходами по PC инструкций. Runtime helper для сравнения не вызывается.
Тождественный `big` cast в скалярном backend использует MOVL; оптимизатор удаляет
такие копии, точно сворачивает константные сравнения и убирает мёртвые ветви.
Преобразования текста/ключей сохраняют возможные ошибки и выделения памяти.
Сравнения чистые и полные: неиспользуемое можно удалить, одинаковые — переиспользовать.
Деление и остаток сохраняют MAY_THROW даже при неиспользуемом результате.
Невыбранная ветвь с нулевым делителем не исполняется и может исчезнуть после opt.

Одноблочный hosted-backend таблиц и независимый C reference runner также понимают
обе операции, скалярные bool copy/trace. Загруженные из таблицы big сравниваются
во всех 64 битах; bool-ячейки не получают GC-бит указателя. Материализация
использует те же нативные long branch инструкции. Многоблочный CFG таблиц здесь
не добавлен: решения с живыми владельцами или импортируемыми преобразованиями
могут компилироваться в FIR, но direct Dis требует поддерживаемое подмножество.
При отказе preflight байты образа не публикуются.

## Границы поддержки

Каждая ветвь завершается. Объявления/присваивания внутри ветвей, продолжение
после дерева, phi/join, изменяемые исходные циклы, сдвиги, прозрачный any/прокси,
общие функции и полный Dis SBL остаются отдельной работой. Пределы сохраняются:
общая глубина 64, 1000 значений исходника, 127 решений/255 блоков, 64 КиБ исходника.
Отказы синтаксиса/типов/лимитов сохраняют прежние файлы FIR и debug-sidecar.
Сравнение не изменяет удалённого владельца. Метаданные профиля остаются
`limbo_tables` для совместимости; чистому big-коду импорт таблиц не нужен.

## Запуск

После независимой сборки нашего FIR и runtime, из корня репозитория:

```sh
mkdir -p build/tmp
export TMPDIR="$PWD/build/tmp"
build/fir/fir1_source limbo --input fir/v1/examples/dis/big-decisions.b build/decision.fir -g build/decision.json
build/fir/fir1 dis build/decision.fir build/decision.dis
build/runtime/disvm --jit --inspect-words 0 6 build/decision.dis
build/runtime/disvm --no-jit --inspect-words 0 6 build/decision.dis
```

Исходные ячейки: `MIN, 0, 0, 1, 0, 0`, MIN = -9223372036854775808.
Последние три — флаги исполнения. Явный `fir1 opt INPUT OUTPUT` удаляет оба
константных решения: перед inspection надо пересчитать live trace, остаются
одно значение и один флаг. Поставляемый пример C99-компилятора в процессе
принимает тот же исходник; переносимые SDK проверяют его в обоих режимах.

Проверяются шесть отношений с обоими исходами, знаковые границы, равенство,
значения выше 2^53, вложенные решения, неверные типы, незавершённые ветви,
запрещённые bindings, переполнение глубины, source spans и код до/после opt.
Oracle — точные Python integer-сравнения и табличный C reference runner.
Эмуляция инструкций ARM64 не означает испытания на физическом ARM64.
