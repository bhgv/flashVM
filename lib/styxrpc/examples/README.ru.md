# Вызов независимого устройства на C

[English](README.md) · [libstyxrpc](../README.ru.md)

Соберите примеры с `-DSTYXRPC_EXAMPLES=ON` и установленной серверной библиотекой
Styx. Из каталога исходников `styxrpc`, если каталог сборки называется `build`:

```sh
python3 examples/socketpair.py build/styxrpc-device build/styxrpc-client
```

Сценарий запускает два C-процесса на разных концах сокета. Устройство
публикует `sample` в `/mounted/device.dis`, удерживает состояние на fid и
вызывает колбэк инкремента один раз после полного запроса. Клиент использует
новые fid для скалярных вызовов, обычного обновления ref и вложенного графа
через [`styxrpc_graph_invoke`](../reference/graph_invoke.ru.md). Через позиционный
API VFS он читает и записывает регистр. При успехе клиент
печатает `PASS native C calls standalone C device`. Клиент дочитывает ответ
до clunk. Неподтверждённая передача завершает проверку с ошибкой, сценарий
завершает оба процесса.

Для проверки из DisVM укажите пути к собранной VM, bootstrap-компилятору
Limbo и каталогу интерфейсов Limbo:

```sh
python3 examples/disvm/run.py --runtime /path/to/disvm \
    --limbo /path/to/limbo-bootstrap --module /path/to/upstream/module \
    --device build/styxrpc-device
```

Ожидаемый вывод — `PASS Dis load of standalone C device`. Для JIT добавьте
`--jit`. Клиент также читает байт `value`, пишет новый и снова читает его.
Сценарий передаёт подключённый дескриптор через
`--styx-mount-fd FD --raw --at /device`. Режим `--raw` здесь монтирует
однонаправленный Styx. Сценарий ограничивает время и дожидается завершения
обоих процессов. Клиент Limbo компилируется до запуска устройства.

## Запуск DisVM из C

```sh
python3 examples/disvm/launch.py --runtime /path/to/disvm \
    --limbo /path/to/limbo-bootstrap --module /path/to/disVM/module \
    --driver build/styxrpc-launch
```

C-клиент выбирает существующее обрамление двустороннего транспорта и монтирует
прямой поток Styx. Он сверяет профиль запуска raw, передаёт байты по `.unibus`
и опрашивает `.exit` по тому же соединению. Сценарий проверяет успешный и
неуспешный запуск в обоих режимах VM. Статус 2 означает подтверждённый успех,
статус 3 — подтверждённую ошибку программы.

## Именованные запуски и встречный контекст

```sh
python3 examples/disvm/named.py --runtime /path/to/disvm \
    --limbo /path/to/limbo-bootstrap --module /path/to/upstream/module \
    --native-module /path/to/disVM/module --driver build/styxrpc-named
```

Сценарий запускает постоянного провайдера DisVM и C-клиента на двух концах
сокета. C-клиент публикует `.prog/42` во встречном потоке, вызывает две программы
по публичным именам, закрывает fid запущенной задачи с бесконечным циклом и
проверяет следующий вызов на том же соединении. Первый образ читает `.pid` и
файл из `.vfs`, обновляет `.var/count`, читает FD 0 и пишет в FD 1 и 7.
В обоих режимах ожидается `PASS one socket, two named Dis modules, reverse .var/.fd/.vfs`.

## Сгенерированный интерфейс и вложенный ref

Бинарник `styxrpc-interface` печатает `device.m` из того же описателя,
который использует устройство. Сценарий `examples/disvm/run.py` запускает
генератор из каталога `--device` или по явно переданному `--interface`, затем
компилирует Limbo с `-D RG`. После вызова `bump` проверяется, что свойство
вложенного объекта обновилось, а ссылка по-прежнему указывает на тот же
объект. В обоих режимах ожидается `PASS Dis load of standalone C device`.

## Ветвление каналов через UniBus

```sh
ctest --test-dir build -R 'styxrpc-(unibus-socket|channel-scheduler)' --output-on-failure
```

Два C-конца используют `.prog/42/.unibus` по Styx. Тестовый планировщик
выбирает готовую ветку со строкой, пока соседний fid ещё ожидает приём.
После clunk проверяется один вызов обработчика отмены. Отдельный тест
переносимого планировщика C проверяет FIFO, смешанное `alt`, срок WAIT
и снятие ожидающей операции.

## Живые каналы Dis и C

```sh
python3 examples/disvm/run.py --channels --runtime /path/to/disvm \
    --limbo /path/to/limbo-bootstrap --module /path/to/disVM/upstream/module \
    --device build/styxrpc-channel-device
```

Ожидается `PASS Limbo/C live channels over Styx`. Добавьте `--jit` для JIT.
Limbo передаёт три канала C-экспорту. C проверяет пустую ветку, получает
строку через встречный UniBus и отправляет ответ. Затем Limbo передаёт
внутренний канал через `chan of chan of string`, проверяет его идентичность
при возврате и обменивается строками по нему. Два вызова `port()` выдают каналы с отдельными
буферами C. Limbo проверяет чтение и `alt`. Файл `.unibus` модуля
проверяет токен, который отзывается при закрытии fid функции. Устройство
сообщает ошибку fid при отклонении операции. Скрипт закрывает сокет и
дожидается завершения обоих процессов.

Именованный [пример](disvm/named.py) дополнительно проверяет коллекции Int32
при обращении Dis к C. Для позиционного вектора он выполняет вставку,
добавление в конец, извлечение и обновление. Для числовых ключей — добавление
и выбор через `.idx`/ `.val`. Закрытие селектора отзывает доступ старого fid.

## Гибридная таблица на встречной стороне

Запустите [именованный пример](disvm/named.py) по команде из раздела об именованных запусках.
`device-program.b` открывает `.prog/.self/.var/hybrid`, сравнивает позицию
`1`, строку `"1"` и разреженный числовой ключ `5`. Ключ `-1` выбирает
последнюю позицию плотной части. Программа вставляет и добавляет элементы,
извлекает последний элемент, затем проверяет `.len` и `.count`. Повторное
чтение открытого `.pop` возвращает тот же снимок. Повторное добавление
ключа и чтение `.val` после закрытия выбранного `.idx` должны завершиться
ошибкой. Состояние примера принадлежит C-процессу.

## Рекурсивная выдача между C и DisVM

Соберите примеры с `STYXRPC_EXAMPLES=ON` и запустите из каталога libstyxrpc.
Параметр `--disvm-source` указывает на исходники DisVM с компиляторными
интерфейсами и Limbo-примером рекурсивных каналов.

```sh
python3 examples/disvm/routed.py --runtime /path/to/disvm \
    --limbo /path/to/limbo-bootstrap --disvm-source /path/to/disVM \
    --driver build/styxrpc-routed-client
```

C-клиент публикует два встречных `.prog/<pid>/.unibus` и открывает функцию
DisVM на том же соединении. Функция возвращает два канала модуля. C отправляет
в первый из них полномочие на свою встречную шину. DisVM дважды передаёт через
неё один и тот же токен модуля. Клиент сверяет адрес и возвращает исходный
кадр. Затем C открывает вложенный канал по токену и передаёт ему свой второй
встречный PID. DisVM отправляет по нему 43, получает в ответ 81 и передаёт 81
на второй канал модуля.

Клиент проверяет отказ для неправильного токена и для обоих выданных токенов
после закрытия fid функции. При ошибке пример сообщает номер этапа. При успехе
оба режима исполнения выводят `PASS delegated PID and module channels between
C and DisVM`. Сценарий закрывает сокет и дожидается завершения провайдера.

## Сквозная приёмка DisVM

Соберите [нативную DisVM с SDK терминального запуска](https://github.com/bhgv/flashVM/blob/master/disVM/runtime/TERMINAL-LAUNCH-CLI.md).
Укажите исходный каталог DisVM и каталог этой сборки с файлами `disvm`
и `bootstrap/limbo-bootstrap`. Из каталога `lib/styxrpc` запустите:

```sh
cmake -S . -B build -DCMAKE_PREFIX_PATH=/path/to/prefix \
    -DSTYXRPC_EXAMPLES=ON -DSTYXRPC_DISVM_SOURCE=/path/to/disVM \
    -DSTYXRPC_DISVM_BUILD=/path/to/disvm-terminal
cmake --build build
ctest --test-dir build -R '^styxrpc-disvm-' --output-on-failure
```

Проверки запускают интерпретатор и JIT. Они охватывают загрузку C-модуля,
типизированные вызовы и вложенный ref, именованный и одноразовый запуск,
встречные ресурсы, живые каналы и отзыв делегированных маршрутов.

Для FlashVM соберите [исполняемый тест адаптера](https://github.com/bhgv/flashVM/blob/master/flashVM/doc/STYX_RPC.ru.md#сборка) и передайте
`-DSTYXRPC_FLASHVM_TEST_HOST=/path/to/flashvm_tests_styxrpc_host`. Запустите
`ctest --test-dir build -R 'styxrpc-((managed-|ref-|graph-|hybrid-|channel-|channel-args-|channel-incoming-|channel-delegated-)?(flash-to-dis|dis-to-flash)|flashvm-)' --output-on-failure`.
Двадцать четыре проверки охватывают скалярные и управляемые вызовы, обычные ref, позиционные графы, гибридные таблицы и живые каналы результата в двух направлениях и обоих режимах DisVM. Графовые вызовы проверяют вложенные и возвращаемые ссылки, массивы ref, изменение кортежа и откат. [Гибридные таблицы](../reference/hybrid_tables.ru.md) добавляют упорядоченные патчи ключей, смешанные правки таблиц и ADT, 64-битные значения и профиль с таблицей только в результате. [Живые каналы](../reference/channel_leases.ru.md) проверяют контекстный результат, точные алиасы, отсутствие готовой ветки, начальное значение FIFO, rendezvous и отзыв при clunk. Две дополнительные проверки передают каналы FlashVM как аргументы DisVM в интерпретаторе и JIT и проверяют alt, состояние очередей и отзыв области. Ещё две проверки передают каналы DisVM [обработчикам FlashVM](../reference/channel_handler_modules.ru.md). Они проверяют двусторонний обмен через встречную шину, rendezvous, исключения, тайм-ауты, отзыв сохранённых объектов независимые каналы результата и повторную доставку вложенных каналов. В обоих направлениях проверяются вложенные каналы результата после закрытия внешнего канала. Провайдер FlashVM сохраняет признак rendezvous, когда Limbo отправляет вложенный канал обратно. Три теста проверяют именованный запуск из ActionScript, встречные ресурсы, отмену и позиционное I/O на независимом устройстве C.

Рекурсивная проверка FlashVM передаёт два встречных PID и принимает отдельный токен модуля через ту же аренду. Запустите её в обоих режимах DisVM через `ctest --test-dir build -R channel-delegated`.
