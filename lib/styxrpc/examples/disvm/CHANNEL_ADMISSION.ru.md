# Отмена допуска делегированных каналов

[English](CHANNEL_ADMISSION.md) · [Примеры SDK](../README.ru.md) · [Аренда каналов](../../reference/channel_leases.ru.md)

Нативный результат может передавать канал того же модуля DisVM или
временный PID на встречном соединении. Получатель подтверждает маршрут
перед использованием. SDK C готовит все записи одного кадра во временной
таблице и допускает их вместе. При отмене проверки индексы прежних
маршрутов доступны. FlashVM, DisVM и SDK используют одинаковые записи
UniBus и запросы 9P.

| Адрес в полученном кадре | Где SDK его подтверждает | Что сохраняет успешный импорт |
| --- | --- | --- |
| Токен и ключ модуля | `.unibus` на модуле, удерживаемом выдавшим результатом | Токен, ключ, схему элемента и признак рандеву в аренде |
| Встречный PID и ключ | `.prog/<pid>/.pid` и `.unibus` исходного владельца на встречном подключении | Корень в таблице PID вызывающего с ключом, схемой и признаком рандеву |

## Срок ожидания в C

Используйте монотонные часы и передайте один абсолютный срок на импорт.
Колбэк проверяет его в вызывающем потоке, в том числе при ожидании
ответа на мультиплексированном подключении. В приведённой функции
`deadline` указывает на заполненный `timespec` для тех же часов.
При сбое часов колбэк запрашивает остановку. Сроки запросов клиента
Styx также действуют.

```c
#define _POSIX_C_SOURCE 200809L  /* Доступ к clock_gettime под Linux. */
#include <time.h>
#include <styxrpc/channel_client.h>

static int deadline_reached(void *state)
{
    const struct timespec *deadline = state;  /* Заимствованный срок. */
    struct timespec now;                     /* Текущее монотонное время. */
    if (clock_gettime(CLOCK_MONOTONIC, &now) != 0)
    {
        return 1;  /* Остановить запрос, если сравнение невозможно. */
    }
    return now.tv_sec > deadline->tv_sec ||
        (now.tv_sec == deadline->tv_sec && now.tv_nsec >= deadline->tv_nsec);
}
```

Владелец результата вызывает [импорт модуля](../../reference/channel_lease_import_message_until.ru.md)
с удерживаемой арендой или [импорт PID](../../reference/channel_pid_import_until.ru.md)
со своей таблицей и встречным подключением. Передайте `deadline_reached`
и адрес срока. Если приложение хранит байты кадра и решило повторить
импорт, задайте новый срок. Если очередь FlashVM уже извлекла кадр, он
считается полученным и при последующей отмене проверки. Следующее
чтение очереди возьмёт новый кадр.

## Запуск полного обмена

Соберите нативный DisVM с терминальным запуском под Linux64 и
`limbo-bootstrap`. Настройте хостовый SDK с `STYXRPC_EXAMPLES=ON`.
См. [сборку SDK](../../README.ru.md) и
[терминальный запуск DisVM](https://github.com/bhgv/flashVM/blob/master/disVM/runtime/STYX-CHANNEL.md).
Запустите из корня репозитория с обоими проектами, подставив свои пути.

```sh
python3 lib/styxrpc/tests/flashvm/channel_admission.py \
    --source disVM --runtime build/disvm/disvm \
    --limbo build/disvm/bootstrap/limbo-bootstrap \
    --driver build/rpc/styxrpc-routed-client
```

| Аргумент | Назначение |
| --- | --- |
| `--source` | Каталог исходников DisVM с примером Limbo и интерфейсами модулей |
| `--runtime` | Нативный DisVM с терминальным запуском |
| `--limbo` | Компилятор начальной загрузки Limbo для провайдера и диспетчера |
| `--driver` | Исполняемый пример C, связанный с отдельно собранным SDK |
| `--jit` | Включить JIT DisVM. По умолчанию работает интерпретатор. |
| `--tcp` | Использовать петлевые TCP-подключения для обоих плеч ретранслятора. По умолчанию используются пары сокетов Unix. |

При успехе сценарий выводит `PASS atomic route import against native DisVM`.
Скрипт дожидается обоих процессов, закрывает подключённые дескрипторы
и удаляет временный каталог. Неожиданное подтверждение, пропущенный
clunk или ошибка канальной операции дают ненулевой код выхода.
При настройке SDK задайте `STYXRPC_DISVM_SOURCE` и `STYXRPC_DISVM_BUILD`,
чтобы зарегистрировать все четыре сочетания режима и транспорта в CTest.
Команда запуска имеет вид
`ctest --test-dir build/rpc -R styxrpc-disvm-channel-admission --output-on-failure`.

## Ход запросов

1. [Клиент C](routed_client.c) публикует два встречных канала и вызывает
   [провайдера Limbo](https://github.com/bhgv/flashVM/blob/master/disVM/examples/remote-scalar/styx-channel-recursive-owner.b).
   Результат содержит два маршрута одной аренды. Через первый встречный
   канал DisVM передаёт клиенту новый канал модуля.
2. Клиент готовит кортеж с новым маршрутом и прежним алиасом.
   [Ретранслятор](../../tests/flashvm/channel_admission.py) пропускает
   первую проверку токена. Он удерживает второй исходный `Rwrite` от
   нативного DisVM и сигнализирует колбэку остановки. Тест проверяет
   `Tflush` с исходным тегом и подтверждённый clunk временного fid шины.
3. Клиент C получает `STYXRPC_CANCELLED` и проверяет, что прежний индекс
   по-прежнему выбирает исходный маршрут. Новый индекс отсутствует.
   Клиент импортирует тот же кадр с новым ожиданием, получает новый
   индекс и через канал посылает свой второй встречный PID. DisVM и C
   обмениваются `43` и `81`, а клиент читает `81` на исходном результате.
4. Clunk выдавшего результата закрывает аренду. Дальнейший допуск и
   обмен по обоим токенам завершаются отказом. Исполняемый сценарий
   проверяет обмен после clunk и отказ для заведомо неправильного токена.

[Проверка встречного PID по протоколу](../../tests/channel_stop_wire.c)
сверяет точный тег и fid при остановке обхода, открытия и чтения
идентификатора. Она также передаёт исходный `Rread` перед `Rflush`.
Импорт сообщает об отмене, если остановка обнаружена до публикации
таблицы. Соседний fid отвечает до и после flush.
[Пример FlashVM со встречным PID](../../tests/flashvm/channel_pid_result.b).
