# Самостоятельная библиотека Unibus

Copyright (c) 2026 bhgv. [Лицензия](LICENSE.bhgv).

Библиотека реализована на C и не требует C++ compiler/runtime. Другие языки допустимы для примеров, тестовых клиентов и инструментов; C++ consumer tests проверяют совместимость C API, не язык реализации.

[English](README.md) · [Справка API](docs/index.ru.md) · [Примеры](examples/README.ru.md)

Это отдельная исходная библиотека. Она не включает и не линкует Styx, DisVM,
FlashVM, GUI, lib9 или другую папку рабочего репозитория. Необязательный 9P-шлюз
передаёт непрозрачные байты внешнему серверу, линкуясь только с Unibus и системными
средствами. Вместо 9P можно передавать команды датчиков, роботов, БД и приложений.

## Состав

| Слой | CMake target | Зависимости и назначение |
| --- | --- | --- |
| Binary S-record и канонические целые | `Unibus::wire` | C89, буферы вызывающего, стандартные byte operations; без allocation/threads/OS |
| Фрагментированный ввод, directional type bindings, согласование лимитов | `Unibus::wire` | Тот же core без выделений; состоянием явно владеет вызывающий |
| Fixed slots, media fragments, измерения и решения адаптации | `Unibus::wire` | Только protocol/state machines; буферы и политику задаёт embedding |
| uint64 prefix, CRC5, именованные order-service сообщения | `Unibus::wire` | Существующий точный wire codec, без поколения в каждом пакете |
| Очереди тегов, восстановление порядка, checkpoints подтверждений | `Unibus::queues` | C99, allocator/pthread; потребитель ждёт только свой тег |

Host выбирает физический носитель и запускает его обслуживающий поток. Wire core
не порождает интерпретатор, не открывает файлы, не dial TCP и не навязывает политику
терминала/робота. SPI/I2C/USB/CAN/радио/serial — адаптеры приложения, не скрытая
обязательная зависимость от TCP или UDP.

FlashVM terminal grants, публикация runtime sysevents, admission запуска и реальное
создание дополнительных медиатранспортов находятся вне этой внешней библиотеки.
Их wire-записи и вспомогательные state machines доступны; OS/устройство выбирает
свои ownership, workers, лимиты и права. Шлюз-пример не объявляется полной заменой
нативного терминального брокера FlashVM или универсальным RPC-маршаллером.

## Минимальная сборка

```sh
cmake -S . -B build-small -DUNIBUS_QUEUES=OFF -DBUILD_TESTING=ON
cmake --build build-small
ctest --test-dir build-small --output-on-failure
```

Собираются C89 wire-библиотека и пример вложенных записей без allocator/OS.
Python, pthread и socket не нужны. При `BUILD_TESTING=OFF` остаются только archive
и headers для включения в toolchain устройства.

## Нативные очереди и примеры

```sh
cmake -S . -B build -DUNIBUS_QUEUES=ON -DBUILD_TESTING=ON
cmake --build build -j
ctest --test-dir build --output-on-failure
cmake --install build --prefix "$PWD/sdk"
```

Очередям нужен pthread. POSIX-шлюз добавляет sockets, его проверка — Python3;
Python в библиотеку не линкуется. Отдельный установленный потребитель:

```cmake
find_package(Unibus CONFIG REQUIRED)
add_executable(sensor main.c)
target_link_libraries(sensor PRIVATE Unibus::wire)
```

Укажите prefix в `CMAKE_PREFIX_PATH` либо используйте скопированный проект через
`add_subdirectory`. Для нативных ordered queues выбирается `Unibus::queues`.
Сохранённые C-имена `styxorder*` исторические и совместимы с исходным API;
они не означают зависимости от libstyx.

## Записи, служебная часть и изоляция

Обычная S-запись содержит кодированные checksum, length, tag и непрозрачный payload.
Целые имеют существующий канонический формат переменной длины; native C-структуры
не пересылаются. Фрагмент транспорта не является границей записи. До проверки
framing, размера и checksum запись клиенту не выдаётся.

Внешним tag0 владеет служебный поток. Там назначения тегов направлений,
согласование и управление передачей. Внешний ненулевой конверт клиента содержит
его собственные записи. Два клиента могут использовать внутренний tag1: внешний
маршрутизатор разделяет их. Приложения не получают внешний tag0. Внутренний tag0
клиента, если он предусмотрен схемой приложения, — другое пространство имён.

Старая version1 binding-таблица после назначения неизменна: точные повторы
идемпотентны, конфликт отклоняется. Динамическое переназначение нельзя делать
перезаписью этой таблицы. Именованное согласование order-service, renewal и
подтверждённые границы отдельного счётчика — другой API. Новый профиль/назначение
не выпускает данные до соответствующего согласия. Изменение одного клиента
само по себе не требует полного drain остальных клиентов.

## Порядок, частичный I/O и закрытие

Ordered packet имеет prefix byte с 3 битами ширины unsigned номера и CRC5,
затем 1..8 байтов номера и существующую checked S-запись. Номер uint64 принадлежит
выбранному тегу/направлению. Дополнительного поколения в каждом пакете нет.
Исчерпанный счётчик требует явного нового согласования; не оборачивается молча.

Закодированный пакет удерживается до приёма транспортом: повторяются те же байты,
не второе кодирование с новым номером. Частичная запись не разрешает повтор эффекта.
Checksum обнаруживает повреждения, но не является аутентификацией или шифрованием.
Существующий profile оставляет короткую checksum для коротких записей; экспорт
не меняет алгоритм и wire-формат.

Feed/dispatch-владелец ставит записи независимо от исполнения получателей.
Потребитель блокируется только на своей очереди. Отказ allocator — явная ошибка,
не разрешение терять сообщение или усыплять весь канал. Physical backpressure
может задержать вывод; это не ожидание клиентом своей записи. Close будит ожидающих
и оставляет готовые записи доступными для drain. Free допустим после завершения
всех feed/encode/consumer calls.

## Примеры

- [Вложенные записи](examples/nested.ru.md): настоящий tag0 binding, вход по одному
  байту, внешний клиент7 и внутренний tag1, без allocator и OS.
- [Независимые очереди](examples/queues.ru.md): клиент7 ждёт в своём нативном
  потоке, диспетчер обслуживает клиент8, затем выполняется join.
- [9P-шлюз](examples/bridge/README.ru.md): один RX/service-владелец, FIFO и workers двух
  клиентов, бинарный stdin/stdout; tag0 разбирается только брокером. У обоих клиентов
  внутренний tag1 и одинаковые 9P fid в независимых backend-соединениях.

Шлюз — один явно заданный baseline compact-record профиль приложения. В нём
предобъявлены клиент7/клиент8 и один незавершённый backend RPC на клиента.
Пример не реализует произвольные службы, согласование новых клиентов, автонаращивание
линий или конкурентный Tflush заблокированного RPC того же клиента. Это embedding/
coordinator policy, не следствие наличия codec. Socket timeout действует на отдельный
I/O, а не доказывает общий end-to-end deadline.

[Рецепты файловых серверов](examples/bridge/README.ru.md) показывают плоское,
фиксированное многоуровневое, живое key/value, ленивое HTTP и меняющееся window/control
пространство через тот же непрозрачный шлюз. Выбор backend не меняет core Unibus
и его зависимости.

## Справка и совместимость

```sh
python3 view_docs.py --port 8911 --no-browser
```

Просмотрщик скопированного пакета использует только стандартную библиотеку Python3,
обслуживает этот каталог read-only на loopback. Оба языка, словарные страницы
функций, примеры и адресуемые строки исходников доступны offline.

Имена API и wire-функции сохранены из основных реализаций; происхождение и
преобразования записаны в `SOURCES.jsonl`. Проверяются все ширины номеров, CRC5,
неверные/усечённые пакеты, независимость тегов, ACK/rollover и границы отказа памяти.
См. [протокол](docs/protocol.ru.md), [перенос](docs/porting.ru.md), [API](docs/index.ru.md).

## Идентификация исходного выпуска

Архив инструмента выпуска содержит `RELEASE.json` с точным commit исходников,
SHA-256 и режимом каждого файла. Отдельный `SHA256SUMS` описывает сжатые архивы.
Перед распаковкой проверьте хеш архива. Для сборки распакованных исходников Git
не нужен; настройки сборки остаются описанными выше.
