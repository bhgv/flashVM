## Назначение и состав

Каждый архив — самостоятельный исходный проект: C-реализация, заголовки, CMake,
лицензии, справочник и руководства EN/RU, примеры и локальный просмотрщик.
Styx и libunibus остаются разными архивами с отдельными настройками сборки;
им не нужны ни соседняя библиотека, ни VM. Это исходные дистрибутивы, а не готовые
бинарники и не обещание проверки на любом оборудовании.

Инструмент сопровождения [package.py](package.py) читает точные закоммиченные
Git-объекты. Рабочие правки, неотслеживаемые результаты сборки и локальные SDK
в выпуск не включаются. Режимы файлов нормализуются до 0644/0755, имена/ID
владельцев пустые или нулевые, время архива равно времени выбранного commit.
Gzip не содержит имени файла на машине сборки. При том же commit и инструменте
сжатия получаются одинаковые байты архива независимо от каталога назначения и
локальных настроек/фильтров Git archive. Сеть не используется.

В архив добавляется `RELEASE.json`: версия формата 1, имя пакета, полный commit
репозитория и отсортированный список исходников с путями, режимами и SHA-256.
Манифест описывает все исходники, кроме самого себя. Отдельный `SHA256SUMS`
содержит хеши двух сжатых архивов. Хеши выявляют повреждение, но не удостоверяют
издателя. Исходные лицензионные уведомления сохраняются.

## Создать оба архива

Из корня репозитория, с Git и Python 3.9 или новее:

```sh
python3 lib/package.py --revision HEAD --output build/library-distributions
cd build/library-distributions
sha256sum -c SHA256SUMS
```

`--revision` задаёт закоммиченный Git revision, по умолчанию `HEAD`; он разрешается
один раз для двух пакетов. Правки библиотек нужно сначала закоммитить, иначе
они не попадут в выпуск. Обязательный `--output` задаёт каталог назначения
относительно текущего рабочего каталога; допустим и абсолютный путь.
Существующие одноимённые архивы и `SHA256SUMS` заменяются. Остальные файлы
сохраняются; новый каталог позволяет не оставлять рядом посторонние старые выпуски.

Имена: `styx-<12-hex-commit>.tar.gz` и `libunibus-<12-hex-commit>.tar.gz`.
Внутри каждого только собственный корень `styx/` либо `libunibus/`.
Необычные Git-записи, ссылки и конфликт с отслеживаемым `RELEASE.json` приводят
к отказу. Архив заменяется только после успешного сжатия, но два архива и список
хешей не составляют единую атомарную файловую транзакцию. После ошибки нужно
устранить причину и повторить команду до распространения комплекта.

## Использовать в другом проекте

Перенесите выбранный архив и квитанцию хешей на целевую машину, проверьте хеш,
затем распакуйте. Для сборки распакованного проекта этот репозиторий и Git
не нужны. Например, минимальный Styx:

```sh
cmake -S styx -B styx-build -DSTYX_HOSTED=OFF -DBUILD_TESTING=ON
cmake --build styx-build
ctest --test-dir styx-build --output-on-failure
```

Минимальный libunibus:

```sh
cmake -S libunibus -B unibus-build -DUNIBUS_QUEUES=OFF -DBUILD_TESTING=ON
cmake --build unibus-build
ctest --test-dir unibus-build --output-on-failure
```

[README Styx](styx/README.ru.md) и [README libunibus](libunibus/README.ru.md)
описывают hosted client/server/очереди, установку и внешние CMake-приложения.
Запуск `python3 view_docs.py` внутри распакованного проекта открывает его
собственную документацию. Минимальным C-библиотекам Python не нужен;
конфигурации hosted Styx и некоторым примерам/тестам нужен.

## Приёмка именно распространяемых пакетов

```sh
python3 lib/tests/package_contract.py
python3 lib/tests/distribution.py /absolute/path/to/cmake --revision HEAD
```

Первая проверка создаёт временный Git fixture: правки и неотслеживаемые файлы
не влияют на выпуск; сохраняются бинарные байты и исполняемые режимы;
export-ignore и локальные archive-настройки не меняют исходники; ссылки и
зарезервированные пути отклоняются.

[Приёмка дистрибутивов](tests/distribution.py) дважды создаёт каждый архив,
требует одинаковые байты, проверяет манифест/хеш/режим каждого файла и извлекает
только проверенные обычные файлы. Все четыре hosted/minimal профиля собираются
вне репозитория при недоступном C++-компиляторе. Затем SDK устанавливаются и
переносятся; внешние C/C++98-приложения собираются и запускаются, проверяются
установленные документы/просмотрщики, пять моделей Styx-сервера работают через
независимо слинкованный Unibus gateway. C++ проверяет C-заголовки, а не меняет
язык реализации библиотек.

Временные каталоги извлечения/сборки удаляются при выходе. Диагностика остаётся
в `build/library-distribution-acceptance.log`; ошибки дают ненулевой код выхода.
Полная приёмка требует Linux amd64, компилятор/toolchain, Git, Python и `ctest`
рядом с указанным `cmake`. Это проверка host-сборки, а не физического SPI/CAN/
радиоканала или MCU. См. [границы сопровождения](MAINTENANCE.ru.md).
