# GC Inferno/Dis и FlashVM: отдельное сравнение

[English](GC-COMPARISON.md) · [Методика и воспроизведение](../tools/gc-compare/README.md) ·
[Потоки Fast/Cycles](../disVM/host/GC.ru.md)

## Вывод

**Преимущество Inferno GC в целом пока не доказано; заменять GC FlashVM и выносить
его как выбранный общий GC сейчас преждевременно.** У Inferno есть полезные
свойства RC и инкрементального обхода, у FlashVM — уже проверенная интеграция
с динамическими объектами, строками, корнями AS и финализаторами. Простая замена
функций сборщика не переносит эти гарантии между разными моделями объектов.

Это сравнение исходников, корректности и исходного профиля FlashVM. Оно не выдаёт
тайминги тестового пула Inferno за измерение настоящего аллокатора. Честного
численного рейтинга скорости/памяти двух готовых VM на одинаковом workload пока нет.

## Зафиксированные версии и условия

- FlashVM: GC/string-GC из дерева опубликованного v0.1535 (`930eaa97`), без изменений
  алгоритмов во время сравнения; нативная библиотека собрана Release.
- Inferno: `bhgv/Inferno-OS-bhgv`, experiment, `3e3536578b969cf1a460210d8ec667713869ccfc`.
  Проверка удалённой ветки на момент работы дала тот же commit.
- Среда измерения: Linux AMD64, GCC 13.3.0, glibc 2.39. Пять отдельных процессов
  на каждый случай, размеры 10 000 и 50 000. Ни Windows, ни Android, ни macOS
  этими числами не представлены.
- В тайминг FlashVM входит настоящий `fvm_gc_collect`, а не модель алгоритма.
  Выключено автоматическое планирование, коллекции вызываются явно.

## Сравнение механизмов

| Критерий | Inferno/Dis | FlashVM |
| --- | --- | --- |
| Основа | RC `destroy` плюс цветовой `rungc` | Точная трассировка mark/sweep объектов |
| Ациклический мусор | RC может освободить сразу при последнем release | Освобождается при очередной коллекции |
| Циклы | Собираются трассировкой от корней | Собираются трассировкой от корней |
| Планирование | `rungc` сканирует порциями с адаптивной квотой | `fvm_gc_step` при пороге вызывает полную `fvm_gc_collect` |
| Жёсткая граница паузы | Нет: обход корней/массива и каскадный RC могут быть длинными | Нет: полная трассировка/финализация/освобождение |
| Ссылки | Карты типов и кадров, специальные контейнеры | Поля объектов, AS-стек/регистры, captures, pins, native roots и ресурсы |
| Строки | Управляемые объекты в модели Dis | По умолчанию arena; есть явный traced-режим |
| Финализаторы | Деструкторы типов/нативных ресурсов | AS/native finalizers, resurrection и повторная маркировка |
| Ошибки выделения | Требуется проверять на полном хосте/аллокаторе | Есть отдельные проверенные OOM-регрессии |
| Параллельная общая куча | Старые глобальные GC/RC не являются автоматически потокобезопасными | Коллектор контекстный, API требует потока владельца |
| Компактизация | Аллокатор имеет callback-механизм poolcompact, по умолчанию move отсутствует | Автоматического moving/compacting GC нет |

Поэтому Inferno перспективнее как источник механизма раннего RC-освобождения и
порционного обхода, но эти свойства сами по себе не доказывают меньшее общее CPU
или меньший RSS после переноса на прежние FVM_Object и их контейнеры.

## Подтверждённые проверки корректности

На FlashVM прошли 16 настоящих GC-регрессий: циклы, глубокий граф, native roots,
вложенные scope, resurrection, release-resurrection, строки, перенос строк,
снимок финализации и три allocation-failure сценария. Это не полная приёмка всей VM.

На Inferno выполнены настоящие тела `destroy`/`rungc` на явно тестовом пуле:
каскадный RC, недостижимые циклы, сохранение глобальных/стековых корней и сборка
после их удаления. Целое поле, равное адресу, не удерживает объект без бита карты.
Этот тест подтверждает алгоритмическое поведение, но не качество аллокатора арен,
пиковый RSS или производительность работающей Dis VM.

## Исходные числа FlashVM

Медиана CPU-времени одной полной коллекции, 50 000 элементов, пять запусков:

| Случай | CPU коллекции | Осталось объектов/строк |
| --- | ---: | --- |
| Независимые недостижимые объекты | 5.863 мс | Все 50 000 освобождены |
| Недостижимое кольцо | 7.503 мс | Все 50 000 освобождены |
| Кольцо с pin | 5.381 мс | Кольцо сохранено |
| То же кольцо после unpin | 4.534 мс | Все 50 000 освобождены |
| Недостижимые строки, arena | 0.006 мс | 888 890 байт буферов остаются до уничтожения контекста |
| Те же строки, traced | 6.337 мс | 0 байт этих буферов после GC |

Это CPU-time, не гарантированная wall-clock пауза и не p95/p99. Малый контрольный
набор чувствителен к среде; значения не объявляются стабильной характеристикой
продукта. RSS измерен для целого процесса, включая runtime/аллокатор/буферы самого
теста; это не размер живой кучи. Сырые результаты поставляются отдельно от исходников.

Практический вывод: режим строк сам по себе существенно меняет удержание памяти.
Нулевая цена arena-сборки здесь означает, что строки не освобождались, а не что
этот GC лучше. Traced-режим уже существует; менять его по умолчанию без проверки
контракта borrowed strings нельзя.

## Граница аллокатора Inferno

Аллокатор можно заменить на libc malloc/free/realloc или другой backend, сохранив
контракт VM. Сохранять исторический алгоритм пулов для работы Dis не обязательно.
В проверенном upstream commit `3e3536578b969cf1a460210d8ec667713869ccfc`
файл `emu/Android/alloc-andr.c` уже содержит альтернативные тела `dopoolalloc`,
`poolfree` и `poolrealloc`, вызывающие libc. Аналогичная ветка есть в FreeRTOS.
Оба файла сейчас определяют `ORIG_ALLOC=1`: прямые libc-тела отключены, поэтому
наличие кода не означает, что полный runtime с ними проверен.

Разделять нужно механизм выделения и метаданные GC. Текущий `libinterp/gc.c:rungc`
перечисляет heap через `poolchain`, `Bhdr`, `B2NB` и `B2LIMIT`; `heap.c:hmsize`
использует `poolmsize`. При выделении отдельных блоков через malloc адаптер должен
учитывать их размеры и перечислять живые выделения либо GC должен получить новый
итератор. Цвета, типы, счётчики ссылок и карты указателей остаются частью VM.
Простое переключение макроса в Android-файле этого ещё не доказывает: например,
альтернативный `poolmsize` там возвращает ноль. Это задача тонкого слоя совместимости,
а не основание сохранять старый алгоритм распределения памяти.

Аудит текущих native-заголовков и настоящего `emu/port/alloc.c` выявил несовместимость
исторического кванта 32 с LP64: Btail по смещению 24 перекрывает csize по смещению 24;
свободный блок также не вмещает нативный заголовок. Поэтому производительность
этого аллокатора на данной модели нельзя использовать для сравнения GC.
Этот дефект относится к конкретному пуловому backend, а не к алгоритму GC Inferno;
проверенный malloc-backend является допустимым альтернативным путём сравнения.

Подготовлен отдельный patch для репозитория Inferno: квант выбирается по размерам
Bhdr/Btail, ILP32 остаётся 32, LP64/LLP64 получают достаточный размер. Тест моделей
ILP32/LP64/LLP64 с UBSan проходит; старый исходник является падающим отрицательным
контролем. Аудит исправленного commit `ae99aac` даёт PASS_LAYOUT_ONLY: перекрытие
устранено. Это ещё не полная приёмка аллокатора или всего 64-битного порта VM.

## Условие замены и выноса общего GC

Перед выбором нужны одинаковые графы и сроки снятия корней, рабочие аллокаторы,
сопоставимые финализаторы/строки, измерения общего CPU, wall-clock распределения
пауз, peak/retained bytes, фрагментации и освобождения арен на целевых платформах.
Нужны также те же проверки correctness/OOM/resurrection для обоих backend.

Если выигрыш подтвердится, общий механизм можно вынести в `gc/` с адаптерами
корней/полей/финализации для Dis и FlashVM. Объектные заголовки и native-представления
движков не должны смешиваться; аллокатор остаётся отдельным сменяемым портом.
Пока выбранный общий GC не выносился, GC FlashVM не заменён.
