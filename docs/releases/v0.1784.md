# v0.1784 — atomic collector pending-work consumption

Runtime0.86 consumes the actual hosted GC pending flag with one acquire/release
exchange-to-zero (or read/replace under portable registry mutex). It removes the
later reset that could erase a notification arriving after the earlier read.
The pinned source-view adapter retains normal serial collector behavior and
refuses drift. No vendor snapshot, native layout, shared Dis64 ID or file ABI
changes. General managed execution remains serialized by NativeWorld.

[Contract, precise integration and limits](../../disVM/runtime/GC-PENDING.md).

backends verify complete16000-token histories from8 OS writers, including writer
program order. Four pre-thread source controls require semantic10. Actual rooted
String32 Cycles/Fast verifies collector consumption with C/JIT and both polls;
old split-reset and omitted-consumption controls fail at explicit safe boundaries.
Native backends pass TSan and nonrecovering UBSan; actual collector positives pass
TSan, emitted JIT bytes uninstrumented. SDK and retained source pins verify.

Pending notifications still coalesce. Atomic scalar consumption is not a graph
barrier, epoch completion proof or source lifetime acquisition. Shared payload
and source cells, publication/root epochs, remaining JIT families, scheduler/
channels and code retirement still need their concurrency protocols.

IDs/layout stay unchanged. No independent FlashVM typed-call execution is claimed.
