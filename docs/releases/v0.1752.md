# v0.1752 — elastic native executor lifecycle

Runtime0.56.0 adds `--gc-worker --managed-workers auto`. Two OS executors
start initially; audited blocking native calls create replacements when runnable
Dis processes would otherwise lose their last executor. Individually allocated
slots retain stable addresses through TLS destruction and thread join. Native
completions already queued for heap admission suppress unnecessary growth.
The default runtime remains one executor; installed menu19 opts into automatic
mode. A positive fixed count is also accepted, including16; the old eight-worker
and128-process policy limits are removed. PID/count representation and actual
OS resources still bound the runtime.

Channel waiters retain logical Dis processes, not dedicated OS threads. Automatic
mode retains parked tasks after module init returns and parks a rootless console
controller on a native condition variable. Work, completed retirement and stop
publish wake generations to prevent missed notifications. An idle extra helper
retires after64 empty scheduler intervals; this is not a wall-clock deadline.
One helper and the controller remain. Any rootless executor can join completed
helpers outside the heap, even while the controller waits in native I/O. Stop
prevents registry removal before the controller traverses and joins it.

`--managed-workers-limit N` optionally bounds automatic live executors (N>=2).
Exhausting that limit or failing to create a required replacement is an explicit
fatal process error, NOT recoverable cancellation or graceful native-I/O cleanup.
Startup failures retain the existing partial-start join path. Native I/O still
requires cooperative completion. Debug interpreter builds also gain the missing
host `kgerrstr` export, copying the current logical process error without consuming
it, including the native builtin rollback path.

Tests exercise fixed16 with exact one-executor instruction conservation, two
waves of12 actually blocked writers with idle joins and regrowth,256 channel
receivers,64 constant senders surviving context retirement/reuse, entry-return
parking, stop while four helpers are blocked in native reads, and explicit cap
refusal. Console and graphical hosts exercise interpreter and JIT. The focused
ThreadSanitizer interpreter run covers elastic pressure/reaping and native-stop
lifecycle; it does not certify every VM, JIT or UI path. Local execution is Linux
x64. Upstream selected snapshots and shared Dis64 file admission are unchanged.

Managed heap mutation remains exclusive. This is real OS overlap for audited
native waits, with logical process migration; it is not parallel managed compute.
See [remaining multithreading work](../../disVM/runtime/MULTITHREADING-ROADMAP.ru.md)
and [runnable examples](../../disVM/examples/managed-workers/README.md).

Validation: all29 selected runtime tests passed (the editor native-read case
was retried after restoring the build executable permission); both final elastic
host tests passed again after native-completion accounting, plus automatic MDI
in C/JIT, installed graphical C/JIT elastic cases and the actual menu19 launcher.
The runnable-queue oracle passed20000 operations and eight active controls under
normal, nonrecovering UBSan and focused TSan builds. Both selected vendor
manifests, C++98 private-header syntax, Python/shell checks and whitespace checks
passed. The actual interpreter TSan pressure/stop run also passed after the final
native-completion change. No whole-VM race freedom is inferred from these runs.
