# `asinc`: внекадровые функции/блоки и текущий этап

[English](ASINC.md) · [Работающий Async.post](../flashVM/doc/ASYNC.md) ·
[Отдельная растеризация](../flashVM/doc/RENDER_ASYNC.ru.md)

Сохраняется написание **asinc**. Coco/R-парсеры AS1/AS2/AS3 распознают
`asinc function f(...) {...}`, `asinc {...}`, выражение `var task=asinc {...};`
и `var work=asinc function(...) {...};`. В AS2/AS3 поддержан синтаксис методов.
Обычные имена переменных/свойств/функций `asinc` и вызов `asinc(...)` остаются
допустимыми. Это контекстный префикс; сканер не резервирует слово повсюду.

**Исполнение нового синтаксиса ещё не подключено.** Парсер не строит замыкание и
не запускает потоки. Числовой компилятор в FIR выдаёт явную semantic-диагностику
о недостающем lexical-closure/task lowering, указывая5 байтов префикса. Существующий
выходной файл сохраняется. Синхронной подмены асинхронного блока нет.

Реально работает существующий Async.post / fvm_async_post: callback доставляется
владельцем VM на следующем poll, независимо от SWF-кадра и даже при неподвижных
часах. В новой проверке callback рисует настоящие MovieClip-контуры; после
уничтожения VM их отдельные копии дают побайтово ту же RGBA-картинку. Вызовов
продвижения кадра в проверке нет. Это доказательство публичного API, не уже
готового исполнения `asinc` и не параллельного выполнения AS на физических CPU.

Для полноценного расширения ещё нужны функции/значения замыканий в FIR,
анализ захватов, живущие в куче корневые ячейки переменных, результат/ошибка/
отмена задачи, lowering в SWF/Dis, правила типов и safe points. Объявление
`asinc function` должно откладывать тело при **вызове**, а не при определении.
Блок ставится в очередь при достижении. Сохраняются аргументы, this и лексическая
область. Захваты имеют отдельные версионируемые представления по правилам ниже;
это заменяет прежнее предложение общих изменяемых ячеек.

Работа с объектами VM и построение дерева команд идут через внекадровую очередь
владельца. Неизменяемые команды рисования обрабатывают отдельные растровые потоки;
они не ждут кадров и не обращаются к управляемой куче. Физические потоки могут
работать с отделёнными данными; совместное изменение захваченных AS-объектов
требует отдельной модели синхронизации/GC и сейчас не разрешено. Кадровые события
остаются источником совместимости, а не тактовым генератором всех скриптов.

Новых SWF/Dis64 IDs или calling ABI эта серия не назначает. Между VM передаются
типизированные значения и каналы, а не указатели замыканий в чужую кучу.
[Примеры и команды](examples/asinc/README.ru.md).

## Представления захватов и события изменений

Согласовано пользователем: перед началом вычисления кадра изменения захватов из
asinc поступают в кадр; после вычисления кадра изменения кадра поступают в asinc.
Передаются только переменные, изменённые после предыдущей передачи в данном
направлении. Получение версии не считается собственной записью: обратного эха нет.
Пока вычисляется кадр, задачи работают независимо в своих представлениях.
Публикация не должна затирать собственные изменения задачи, сделанные за это время.
Правило конфликтов нескольких писателей одной переменной/пути пока не определено.

Неизменённая память общая, отделение при записи — copy-on-write. Для объектов и
массивов нужны версии вложенных записей и сохранение отношений между ссылками.
Окружение захвата живёт в куче и переживает выход из функции. Само выполнение и
рисование остаются внекадровыми; для режима без кадров ещё нужна явная эквивалентная
граница обмена.

Запрошенная подписка: `variable.onChangeVarAsinc(callback)`. Она относится к
захваченной переменной как привязке, в том числе числовой, а не к методу числа.
Компилятор должен распознавать этот intrinsic до обычного поиска свойства.
Событие сообщает об изменении, опубликованном другим asinc/потоком. Обработчик
доставляется очередью владельца подписки после публикации, вне внутренних блокировок,
без ожидания отрисовки кадра. Он не выполняется в потоке писателя или рекурсивно
внутри присваивания. Собственные записи и неизменённые полученные версии события
удалённого изменения не создают.

Предлагаемый payload: идентификатор привязки, стабильный id_asinc и при наличии tid,
старое/новое опубликованное значение, версия публикации. Просмотр значений должен
возвращать отделённый read-only снимок `key: id_asinc/tid, val: var_val`.
Имя метода просмотра и handle отмены подписки пока не выбраны. Повторное использование
системного tid не должно смешивать разные задачи. Снимок содержит согласованные
последние опубликованные значения, а не живые указатели в чужую кучу или промежуточную
запись. Доставка каждого промежуточного присваивания не согласована: событие публикации
само по себе этого не обещает. Отмена подписки, завершение задачи и корни удерживаемых
снимков требуют явного управления временем жизни.

**Это контракт для реализации: синхронизация захватов и новое API пока не исполняются.**
