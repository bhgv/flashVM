# Общий бюджет подготовленных потоков в плеере

[English](PLAYER_STREAM_BUDGETS.md) · [нативный API памяти](STREAM_STORAGE.ru.md) · [воспроизведение](PLAYER_PCM_STREAMS.ru.md)

Плеер без mute теперь ограничивает подготовленные источники всей корневой
последовательности заголовков одним бюджетом. По умолчанию — 64 МиБ (67108864 байта),
[FVM_DESKTOP_AUDIO_PREPARED_BYTES](../frontend/common/audio_memory.h#L5) в [заголовке политики](../frontend/common/audio_memory.h)
без зависимости от SDL. Прежний предел 64 заголовка независим. Консольный help
печатает значение из того же заголовка. Публичные структуры player-host/VM не
изменяются; новой консольной опции нет.

В бюджет входят таблица [FVM_DesktopStreamSegment](../frontend/common/audio.h#L26), все удерживаемые объекты/индексы/
payload снимков и временное одновременное владение encoded+decoded следующего
ADPCM-снимка. Перед источником `i` проверяется
`таблица + retained(предыдущих) + peak(i) <= потолок`. После успеха вычитается
только retained: сжатое временное хранилище уже удалено. Пустой снимок также имеет
цену объекта/индекса. [Bounded API и наблюдение памяти](STREAM_STORAGE.ru.md)
проверяют часть снимка до выделения; runtime-предел payload остаётся независимым.

## Предварительная проверка, получение и освобождение

До открытия окна/устройства [fvm_desktop_audio_validate](../frontend/common/audio.h#L75) повторяет ту же арифметику
в порядке источников. Временно подготавливаются **и PCM, и ADPCM**, запрашиваются
размеры, временный снимок закрывается, его retained виртуально вычитается из остатка.
Поэтому последовательность, помещающаяся после полного раскрытия, но превышающая
потолок при временном раскрытии позднего сегмента, отклоняется до native endpoints.
Передаётся первый отказ проверки/бюджета/allocator. OUT_OF_MEMORY не означает,
что сам кодек либо формат SWF неизвестен.

При настоящем получении аудио проверяется политика заголовков, таблица учитывается
до `calloc`, снимки повторно подготавливаются из оставшегося общего бюджета.
Они удерживаются до join worker. При отказе позднего сегмента устройство/worker
ещё не открыты; обычный close освобождает все полученные записи и таблицу.
После успешного preflight реальный allocator всё ещё может отказать при получении;
действует обычная очистка ошибок. Скрытого удерживаемого preflight-кеша нет.
Копирование/индексация/декодирование намеренно повторяются при старте. Учёт,
аллокации, декодирование и обращения к VM в producer не добавляются.

Это предел **подготовленных потоковых источников**, не RSS процесса. Исключены
исходный SWF/VM, метаданные allocator, стек/retry-буферы, renderer, SDL и event voices.
Таблица учитывается здесь, хотя нативный API снимка её не включает. Бюджет не
меняет 9P `msize`, согласование S-record slots, пределы transport либо frame gates.
При mute снимков нет и этот потолок не применяется; core продолжает проверять
структуру и PCM alignment. Смешивание event/stream и прочие неподдержанные форматы
сохраняют прежнюю явную политику.

Для своего C/C++-приложения bounded core API принимает бюджет каждого вызова во
время выполнения, независимо от парсинга CLI. Готовый frontend использует политику
сборки; private build-time override должен быть одинаковым для audio/help и требует
отдельной проверки платформы. Здесь проверяются стандартная сборка и уменьшенный
потолок только в тестовом варианте.

## Примеры и независимые проверки

[Готовые PCM/ADPCM-примеры](../examples/player/pcm_stream/README.ru.md) сохраняют
файлы и команды: стандартного бюджета для них достаточно. Независимый
[C89-экспортёр](../examples/multimedia/swf_stream/README.md) демонстрирует один МиБ
и `--storage` после уничтожения входной VM. Новый codec SDK или привязанный к
консоли менеджер памяти не нужен.

[stream_budget.cpp](../frontend/tests/stream_budget.cpp) собирает настоящий driver с тестовым потолком 64 КиБ. Три
целых стерео ADPCM-источника помещаются; четвёртый отказывается до device/worker.
PCM-предшественник с последующим двухпакетным ADPCM помещается по итоговому retained,
но превышает потолок по одновременному раскрытию. Тест вычисляет размеры API,
требует одинакового результата preflight/acquisition и освобождает частичное владение
до teardown VM. Это dummy SDL/ownership-проверка, не приёмка физического устройства.

В static player-host сборке `flashvm_frontend_stream_budget_player` подключает
тот же уменьшенный driver и options-политику к настоящему CLI. [stream_budget.py](../frontend/tests/stream_budget.py)
проверяет help и обычное воспроизведение, затем задаёт недоступные video/audio
драйверы для превышения retained, временного peak и PCM. Все случаи должны
отказаться в root audio policy до открытия окна/устройства. Mute пропускает эти
корректные encoded-фильмы без аудиоустройства. Тестовый бинарник не устанавливается
как release player; для shared-host остаётся прямой C++-fixture и обычная регрессия.

```sh
cmake --build build --target flashvm_frontend_stream_budget flashvm_frontend_stream_budget_player
ctest --test-dir build --output-on-failure -R '^(flashvm_frontend_stream_budget|flashvm_player_stream_budget)$'
```

Требования — из [руководства сборки плеера](PLAYER_TEST_BUILDS.md). Малый CLI-target
требует tests, static player-host, desktop frontend и SDL audio; Python-harness
не включается при cross-сборке. Исполнение на других ОС/CPU — отдельная приёмка этапа 9.

## Область проверки

Прошли 111 выбранных нативных и 24 shared-host теста: малые бюджеты, настоящий CLI,
точный PCM/ADPCM, offscreen-встраивание и ресурсные каналы. Изменённые модули прошли
ASan/UBSan с обычным driver и вариантом 64 КиБ; отказы frontend изолировались до
бюджета 11, core/storage — отдельно до 4. Вся VM/SDL не инструментировались,
перечисление утечек процессов здесь недоступно. Прежние ошибки проверки комментариев
Windows speech из STREAM_ADPCM.ru.md не менялись; успешный общий прогон не заявлен.

Полные минимальные ядра и storage/C89/export-программы слинкованы для ARM64,
RISC-V64 и x86-64 Linux/musl. Обновлённый статический ARM64 SDL/AGG-плеер слинкован;
у всех тринадцати выбранных ELF проверены CPU и статическая загрузка. x86-64/musl
storage/allocation/C89-тесты и полный C-пример действительно выполнены здесь,
включая независимую PCM-сверку. Исполнение ARM64/RISC-V64 и приёмка физических
окон/динамиков не заявлены. Все этапы роудмапа остаются открытыми; логи, SDK и кеши
не включаются в отслеживаемые исходники.
