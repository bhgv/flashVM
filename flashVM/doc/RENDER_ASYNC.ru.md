# Фоновая нативная отрисовка

[English](RENDER_ASYNC.md) · [Публичный API](../include/flashvm/render_queue.h) ·
[Реализация](../src/render/render_queue.c) ·
[Запускаемый пример C89](../examples/embedding/parallel_render/README.ru.md) ·
[Кадр IDE](../../disVM/runtime/editor_raster.c)

[`fvm_render_queue_create`](../include/flashvm/render_queue.h#L32) создаёт 1–8 постоянных рабочих потоков платформы.
Графический редактор Dis/Flash использует **один фоновый поток растеризации**.
Раскладка текста, извлечение контуров глифов, исполнение AS, геометрия попаданий и GC
остаются у владельца VM. Рабочий поток получает независимые нативные контуры,
цвета и собственный RGBA-буфер. Загрузка SDL-текстуры, работа с окном и запись PPM
остаются у оконного владельца.

Настоящая растеризация контуров редактора вынесена из потока исполнения.
Раскладка и полный обход сцены пока не вынесены; один кадр ещё не разбивается
между несколькими рабочими потоками. Это не законченный асинхронный SWF-плеер.
Прямой путь Dis → типизированные каналы → Flash-контент сохраняется.

## Контракты очереди

| Операция | Владение и ожидание |
| --- | --- |
| [`fvm_render_queue_create`](../include/flashvm/render_queue.h#L32) | Проверяет callbacks и число потоков; передаёт очередь только при успехе. Частичный запуск откатывается с join уже созданных потоков. |
| [`fvm_render_queue_submit`](../include/flashvm/render_queue.h#L40) | Передаёт отдельное ненулевое задание при успехе. Не ждёт растеризации; удаляет прежние ожидающий/готовый кадры. При ошибке выделения владелец задания не меняется. |
| [`fvm_render_queue_take`](../include/flashvm/render_queue.h#L47) | При wait=0 возвращает NOT_FOUND до готовности последнего задания, не меняя выходы. При OK возвращает задание владельцу и отдельно статус его исполнения. wait=1 — явный барьер захвата/теста. |
| [`fvm_render_queue_destroy`](../include/flashvm/render_queue.h#L54) | Убирает ожидающее задание, дожидается исполняющихся и освобождает синхронизацию. Может блокировать; callbacks должны завершаться. Принимает null. |
| [`FVM_RenderExecute`](../include/flashvm/render_queue.h#L19) | Заимствует одно исключительно принадлежащее заданию нативное состояние; возвращает настоящий статус. Разные задания могут исполняться параллельно. |
| [`FVM_RenderRelease`](../include/flashvm/render_queue.h#L26) | Удаляет только собственные нативные данные; вызывается владельцем либо worker. Без VM/GC/SDL, повторного входа в очередь и сохранения указателей. |

Все публичные вызовы выполняет один владелец хоста; конкурентное уничтожение и
повторный вход из callbacks запрещены. Публикацию завершения защищает mutex/condition
из ports. Простаивающие потоки спят на condition, а не крутят spin-loop.
Используются существующие POSIX-порты Linux/Android/macOS и Win32-порт Windows.
В этой серии проверено исполнение только на Linux.

Очередь удерживает не более workers+2 заданий: исполняющиеся, одно заменяемое
ожидающее и один готовый результат. Устаревшее уже исполняющееся задание завершается
обычным образом и удаляется; принудительной остановки нет. Забрать можно только
последнее принятое задание. Освобождение выполняется вне mutex, но удаление заменённого
ожидающего/готового буфера занимает некоторое время владельца. Гарантии жёсткого
реального времени нет. Размер задания и число очередей должен ограничить хост.

## Подключение к редактору

Владелец завершает обработку Dis-конвертов и обновление AS-представления перед
подготовкой кадра. Контуры TextField/font после извлечения не зависят от жизни VM
или шрифта. В очередь передаются контуры и прямоугольники выделения, номеров строк
и панелей в порядке рисования. Ограничения кадра: 2048×2048 пикселей, 8192 пути,
262144 команды контуров. Превышение бюджета или нехватка памяти возвращают ошибку;
частичный кадр не отправляется.

При обычном опросе транспорта владелец забирает результат с wait=0. Кадр устаревшего
размера холста отбрасывается. Пока пиксели готовятся, нативный ввод остаётся в очереди
ОС: щелчок не попадёт в новую геометрию поверх старой картинки. Планирование Dis и
опрос каналов продолжаются. Воспроизведение событий продвигается после показа через опрос без ожидания.
Только `--capture` явно ждёт кадр для записи; этот барьер не блокирует обычную
интерактивную отправку или replay без захвата.
При остановке worker завершается до уничтожения шрифтов и обеих VM. Нативные
задания не содержат управляемых корней или общей кучи интерпретаторов.

## Проверки и ограничения

- [Регрессия очереди](../tests/async_render_jobs.c): два остановленных на условии
  worker не мешают владельцу добавлять задания и опрашивать результат без ожидания;
  проверены замена ожидающего, удаление устаревшего, ошибка и однократное освобождение.
- [Пиксельная регрессия](../../disVM/runtime/test_editor_raster.c): реальные пиксели
  AGG побайтно совпадают с синхронным исполнением. Независимо проверены цвета
  непрозрачного и полупрозрачного перекрытия и порядок рисования.
- Прежние графические сценарии проверяют Unicode, курсор, буфер обмена, изменение
  окна, номера строк, браузер и режимы интерпретатора/JIT. SDL dummy не подтверждает
  физические устройства или производительность Android/macOS/Windows.
- [Тест отказов синхронного исполнителя](../tests/render_jobs_failure.c) принудительно
  ломает каждый запуск. Остальные инициализированные участки выполняются ровно раз.

[`fvm_render_jobs_run`](../include/flashvm/render_jobs.h#L25) остаётся синхронным пакетным API с join. Его создание потоков
само по себе не делает вызов асинхронным: [оба режима](RENDER_THREADS.md).
