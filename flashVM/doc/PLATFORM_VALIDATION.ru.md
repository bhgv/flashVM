# Проверка платформ — v0.633

[English reference](PLATFORM_VALIDATION.md)

Стадия 9 требует настоящих сборок и запусков каждой ОС и приёмки стадий 1–8.
Добавлены повторяемые прогоны, а не доказательство готовности недоступных ОС.
Реализован только вывод HEADLESS. Архивы исходников/Git не создаются согласно
действующему указанию пользователя. Встроенные зависимости остаются статическими.

Для Windows, Linux или macOS нужны Python 3.8+, Git, CMake/CTest 3.26+ и нативный
компилятор. Из корня компонента запустите:

```sh
python scripts/validate_platform.py --profile all --jobs 4
```

Профили `cmake/profiles/{agg,cairo,minimal,minimal-jit}.defs` не меняют DEFS.txt. AGG/Cairo
включают шрифты, кодеки, SQLite, OS ports и render jobs; minimal отключает графику,
шрифты, кодеки и SQLite, сохраняя реальные потоки и сеть. minimal-jit включает
автоматический JIT для новых контекстов. Собираются Release,
все доступные тесты, примеры и reference runner. Assertions остаются включёнными.
Ошибка любой фазы останавливает прогон; отсутствие тестов считается ошибкой.
Существующая кросс-сборка не допускается к нативному запуску.

Параметры `--cmake`, `--ctest`, `--generator`, `--build-root` задают инструменты
и каталог результата. Поддержан Release для многоконфигурационных генераторов
Windows. Профили идут последовательно, `--jobs` задаёт параллелизм внутри профиля.
Каждая ОС требует собственного прогона.

В игнорируемом `build-platform/` сохраняются журналы фаз и JSON с версией,
коммитом, признаком незакоммиченных изменений, реальной ОС/CPU, путями компиляторов,
командами и результатами. Ошибка или прерывание не даёт общего статуса passed.
Журналы/JSON не коммитятся и не являются сертификатом завершения roadmap.

Для Android используйте NDK, SDK platform-tools с ADB shell-v2, устройство или
эмулятор API 24+ и совпадающий ABI. Полная команда приведена в английском
руководстве. Укажите `ANDROID_STL=c++_static` и задайте список
`CMAKE_CROSSCOMPILING_EMULATOR`: абсолютный путь Python, абсолютный путь
`scripts/android_test.py`, `--serial`, точный serial устройства, `--directory`,
`/data/local/tmp/flashvm-SESSION`, `--timeout`, `175`.

Затем выполните сборку и обычный CTest. Адаптер копирует каждый исполняемый файл,
переходит в выделенный каталог и запускает его на выбранном устройстве. Аргументы
экранируются, ошибки копирования/связи и код возврата программы передаются CTest.
Serial обязателен; устройство автоматически не выбирается. Для каждой сборки
нужен свой SESSION, общий для всех её тестов: это сохраняет файл между отдельными
writer/reader процессами. После прогона удалите только свой каталог SESSION.
После обрыва связи/таймаута проверьте оставшиеся процессы на устройстве.
CTest по-прежнему ограничивает обычный тест 30 секундами, отдельные — 180.

Python-сценарии нескольких процессов, сети, TZ и reference runner не регистрируются
при кросс-сборке: они запускают бинарники напрямую на хосте, обходя эмулятор CTest.
Их исполняемые компоненты доступны отдельно, но аналогичная оркестрация на Android
ещё нужна. CMake явно сообщает об исключении этих сценариев. Python на устройстве
не нужен. Кросс-сборка без адаптера запуска доказывает только сборку.

Локальные проверки ADB-адаптера используют имитацию транспорта; тест называется
`flashvm_android_adapter_host` и не считается запуском Android. Linux-подобные
ветки Android JIT сами по себе также не доказывают выполнение на устройстве.
Существующие ограничения JIT Windows/macOS сохраняются; interpreter fallback
не подтверждает наличие рабочего нативного backend этих ОС.

Приёмка: [RELEASE_ACCEPTANCE.md](RELEASE_ACCEPTANCE.md), [ROADMAP.md](ROADMAP.md).
Все стадии остаются открытыми до выполнения их реальных критериев.

## Дополнительная проверка сгенерированных инструкций — v0.361

При установленном Unicorn в выбранном Python:

```sh
python scripts/validate_platform.py --profile all --jit-emulator --jobs 4
```

Это дополнительное обязательное условие при указанном флаге. Команда генератора
flashvm_tests_jit_backends берётся из Release JSON CTest вместе с аргументами;
путь к исполняемому файлу не угадывается. Записывается версия Unicorn, в новом
каталоге создаются векторы и запускается check_jit_backends.py. Отсутствующая,
повторная или недоступная CTest-команда, отсутствие эмулятора, ошибка генератора
или эмуляции сохраняют статус failed. Старые векторы не переиспользуются.
Checker явно отклоняет Python с отключёнными assertions (-O/PYTHONOPTIMIZE).

Поле jit_encoder содержит область проверки, статус, версию и каталог векторов;
команды и полные логи остаются в игнорируемой сборке. Unicorn — необязательный
инструмент проверки, не зависимость runtime FlashVM и не bundled-библиотека.
Без флага обычная проверка его не требует. Новый CTest
flashvm_platform_encoder_host выполняет пять Python-тестов управления проверкой
без импорта Unicorn и не запускается в cross-сборке.

Проверяются синтетические адреса helper и инструкции x86/ARM/ARM64/RV32/RV64:
обычные/дальние переходы, Thumb, высокие 64-битные адреса, успех и ошибка.
Полная VM и GC на другой CPU не исполняются; приёмка Windows/macOS/Android
такими проверками не заменяется.

## Происхождение компиляторов — v0.496

Для каждого профиля `toolchains.C` и `toolchains.CXX` сохраняют результаты
определения компиляторов CMake: ID, версию, размер указателя в байтах, платформу,
архитектуру, frontend, target и simulate ID/version, если они заданы. Путь к
файлу метаданных сохраняется; отсутствующие необязательные поля остаются пустыми.
Значения не угадываются по архитектуре Python. Пути компиляторов и генератор
по-прежнему находятся в поле `compiler`.

Читаются только буквальные scalar set из каталога активной версии CMake в cache,
без выполнения CMake-кода. Нет метаданных языка, версии/ID/ABI, повреждена версия
cache или различаются размеры указателя C/C++ — прогон завершается ошибкой до
сборки. Устаревшие каталоги метаданных игнорируются. Десять host-тестов проверяют
сбор доказательств JIT и компиляторов; синтетические записи MSVC не означают
реального запуска Windows. Приёмка Windows/macOS/Android остаётся открытой.

### v0.519: отсутствующая команда CTest

этапа 9, но не завершает приёмку платформ.

Проверено: 9 unit-проверок ELF и 10 проверок encoder/host; по четыре проверки
конфигурации/версии/аудита в minimal, AGG и Cairo. Новый GNU readelf-аудит

## Параллельная загрузка Android — v0.526

Каждый вызов ADB-адаптера загружает исполняемый файл под уникальным именем.
Параллельные тесты одного target больше не перезаписывают работающий файл.
Рабочий каталог остаётся общим: пути и порядок межпроцессных файловых fixtures
сохраняются. После запуска или неуспешной загрузки удаляется только собственный
исполняемый файл вызова, тестовые данные остаются. Ошибка очистки не даёт
успешного результата и не заменяет ненулевой код завершения теста. Первичная
ошибка запуска/загрузки сохраняется при ошибке дополнительной очистки. После
принудительного завершения процесса хоста или потери устройства возможен
остаточный файл с уникальным именем, требующий ручной очистки.

Девять тестов транспорта на хосте проверяют одновременные запуски одного target,
экранирование аргументов, частичную загрузку, timeout, ошибки очистки и общий
каталог fixtures. Используется имитация ADB; запуск Android этим не подтверждён.

## Стабильность исходников (v0.633)

До запуска инструментов и перед успешным завершением runner вычисляет отпечаток
входных файлов компонента. Поля `source_start` и `source_end` содержат HEAD, SHA-256
и число файлов. Несовпадение или невозможность чтения делает весь прогон `failed`,
даже если отдельные профили прошли. При ошибке инструмента финального снимка может
не быть; отсутствие `source_end` не подтверждает стабильность.

Учитываются tracked и неигнорируемые untracked пути, байты рабочих файлов, бит
исполнения владельца, отсутствующие tracked файлы, имена целей символических ссылок
и записи индекса Git. Поля имеют префиксы длины, исключающие неоднозначное склеивание.
Разрешено начинать с dirty-дерева: изменение уже изменённого файла обнаруживается.
Проверяется только независимый компонент; соседние проекты и игнорируемые продукты
сборки исключены. Размещайте `--build-root` вне компонента или в игнорируемой папке
сборки, иначе созданные логи сами станут изменившимися входами. Каталоги submodules
и специальные типы файлов отвергаются; обычная поставка не требует submodules.

Это сравнение двух конечных состояний, а не блокировка или неизменяемая копия:
изменение с восстановлением между снимками может остаться незамеченным. Содержимое
внешних целей symlink, игнорируемые SDK/зависимости, бинарники инструментов и изменения
окружения не хешируются. Их приёмка требует отдельных сведений. Совпавший отпечаток
сам по себе не доказывает воспроизводимость, сравнение с оригинальным Player,
проверку устройства или завершение любой стадии. Схема отчёта остаётся 1 с новыми
полями; необходимо проверять общий `status`.

Изолированная host-проверка использует настоящие временные Git-репозитории и
имитацию инструментов сборки; она не подтверждает исполнение VM:

```sh
python3 scripts/test_platform_source.py
```
