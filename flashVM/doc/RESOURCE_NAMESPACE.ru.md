# Пространство ресурсов и диспетчер сообщений

[English](RESOURCE_NAMESPACE.md) · [Двоичные записи](SRECORD.ru.md) · [План](ROADMAP_STATUS.md).

Здесь закреплена принятая архитектура будущего управления FlashVM.
**Уже реализовано:** S-записи/привязки/приём порциями, ограниченный owner dispatcher,
права сессий на ресурсы, binary request/reply и первый player control adapter.
**Пока не реализовано:** общие GUI-методы, каталоги/subtree namespace, mount,
сервер 9P и полная семантика Inferno. [Dispatcher](RESOURCE_DISPATCH.ru.md). Прежняя
сериализация VM-каналов не изменена.

Независимые очереди наблюдателей и фильтрованный снимок реализованы: [RU](RESOURCE_EVENTS.ru.md). Это плоские ресурсы, а не семантика каталогов.

[Resource debugger / отладчик через ресурсы](RESOURCE_DEBUGGER.ru.md): actual stop/observe/resume; no network listener or mount.

[Hybrid UDP/TCP policy / политика](HYBRID_HEARTBEAT.ru.md): separate timers and authenticated hints; actual socket adapters remain open.

## Общий слой операций

Три слоя используют единую модель: типизированные C-вызовы; dispatcher запросов/
ответов/событий с полномочиями; адаптеры Limbo-каналов/IPC/сети/ФС. Локальному
C-хосту не требуется кодировать сообщения. Удалённый адаптер не обходит проверку
аргументов, владения и прав. Схемы задаются именем/версией, номера тегов локальны
для направления/сеанса. Имя схемы не разрешает динамически вызвать произвольную
C-функцию по имени.

| Предлагаемый путь | Назначение |
| --- | --- |
| `/scene/root/children/` | Каталоги дочерних ресурсов |
| `/scene/root/transform` | Снимок преобразования / типизированное изменение |
| `/scene/root/ctl` | Команды клипа с request/result ID |
| `/scene/root/events` | Независимая подписка каждого open |
| `/timeline/ctl` | Команды, реально поддерживаемые API владельца |
| `/audio/channels/17/ctl` | Разрешённое управление звуковым каналом |
| `/display/frame` | Завершённый кадр: metadata/chunks |
| `/input/events` | Явная инъекция ввода, не native-указатели |
| `/ui/windows/main/children/save/` | Каталог ресурса-виджета |

Виджет — каталог с value/properties/ctl/events/children по возможностям.
Обычное создание/удаление backing-каталога не должно неявно создавать/удалять
VM-объект. Discovery честно сообщает неподдерживаемые операции: имя seek/video/
filter не добавляет отсутствующую реализацию Flash API.

## Владение и конкурентное управление

Ресурс имеет устойчивый ID и поколение; путь служит для поиска, не вечной
идентичностью. Удаление/повторное создание не перенаправляет старый handle на
новый объект. Запрос несёт session request ID, target handle, схему операции,
аргументы и при необходимости expected version/deadline. Ответ различает
accepted/queued и committed/failed. Повтор требует ограниченного dedup либо
явного indeterminate после потери сеанса. Exactly-once при произвольных crash
не обещается.

Каждый ресурс имеет владельца исполнения. Сетевые/файловые workers разбирают,
проверяют клиента и ставят неизменяемые копии команд в очередь; они не входят
в VM/render/SDL с чужого потока. Поддеревья могут иметь разных владельцев,
включая процессы/машины. Операции одной VM исполняются последовательно у её
владельца в safe points. Пакет локальных изменений может быть атомарным после
проверки предусловий; распределённой атомарности нужен отдельный протокол.
Ожидание ответа не удерживает render-thread mutex.

[GC:] Удалённый handle — capability reference, не C-указатель/адрес объекта.
Pin/lookup/unpin выполняет владелец VM. Очередь хранит копии значений либо явные
owner-managed leases. Disconnect/timeout освобождают подписки/leases, старые
поколения отклоняются. Снимок графа сохраняет циклы/общие ссылки через ID;
живая удалённая ссылка явно остаётся capability. Окна/audio/socket требуют
схем ресурсов, не копии memory layout. Graph/lease machinery в этой серии ещё
не реализованы.

Права независимы от путей и внешне непредсказуемых ID. Клиенту экспортируются
разрешённое поддерево и операции: например, запись одной панели, audio только
для чтения, только подписка кадров. Traversal/aliases/binds не выходят за export.
Authentication, confidentiality, quotas и authorization принадлежат transport/
dispatch; короткая checksum их не заменяет.

## Обычные open/read/write

C-протокол принимает байты и буферы, поэтому адаптер может обрабатывать частичные
read/write независимо от границ пакетов и файловых вызовов. Будущая клиентская
библиотека предоставляет open/read/write/close-подобные handles на всех ОС.
Чтобы пути открывались произвольными программами через обычную ФС ОС, нужен
настоящий mount/redirector, например подходящий 9P/FUSE-адаптер. Codec и fopen
локального файла записей такой mount не создают.

Перед экспортом определить семантику endpoints:

- Properties читаются из стабильного снимка конкретного open; offsets и частичные
  чтения имеют определённый смысл. Refresh/reopen задаются явно.
- Control write собирает полную проверенную запись. Успех записи байтов означает
  принятие входа, не обязательно завершённый VM-эффект. Execution ack читается
  отдельно с request ID.
- Events — отдельный ограниченный поток каждого open, sequence/cancel и явное
  сообщение overflow/gap. Один читатель не забирает события другого.
- Frame/audio/video используют версии chunk-схем: stream ID, sequence, extent,
  единицы времени, discontinuity/end. Отдельные quotas/flow control для команд
  не позволяют media-потоку вытеснить STOP.
- Close/flush отменяет ожидающую доставку по объявленному состоянию; выполненная
  команда не откатывается. Повтор byte write не дублирует неидемпотентный эффект.

Отдельно от wire-адаптера подготовить per-client roots, attach/bind/mount/unmount,
union order/collisions, кодировку путей, ограничение .., permissions/stat/discovery,
handles при rename/unlink, cancellation и teardown mount. Для поведения Inferno
и сознательных отклонений нужна матрица и тесты до заявления совместимости.
Имена ФС и идентификаторы схем — разные сущности: ASCII-ограничение metadata
не определяет кодировку путей.

## Порядок реализации

1. Завершено в этой серии: framing, атомарные привязки, приём порциями, прямой
   C API и двоичные примеры в памяти/файле.
2. Owner dispatcher/request/reply/поколения/grants ресурсов реализованы.
   Далее — events, права поддеревьев и discovery.
3. Доставка pause/resume/step/stop подключена; далее frame, затем клипы,
   drawing/audio/input с проверками GC/cancel/errors.
4. Клиентский API файловых операций и адаптеры; реальные mount/9P после protocol
   conformance/native OS acceptance. Особенности Inferno — по явному контракту.
